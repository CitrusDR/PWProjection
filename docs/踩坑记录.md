## 1. 【最重要】UE4SS 的启用链路是两层的

**症状**：装好 mod、`mods.txt` 也写了，但按任何热键（包括原来能用的 F6）都没反应。

**根因**：Palworld 1.0 引入了**官方 mod 系统**。UE4SS 必须先在**游戏内**被启用，
它才会被注入到游戏进程；否则整个 UE4SS 都不存在，所有 Lua mod 一起失效。

```
第一层（环境层）: 游戏内 mod 菜单 → 启用 "UE4SS Experimental (Palworld)"
                  ↓ 官方系统才会部署 UE4SS 并注入
第二层（mod 层）: mods.txt 里注册你的 mod
```

**血的教训**：环境层断了的时候，折腾 mod 层完全是白费力气。
我们就在这上面浪费了一整轮排查。

### 诊断口诀

> **先按 F6。**
> - F6 能用（FirstPerson 切换成功）→ 环境层 OK，问题在 mod 层
> - F6 不能用 → 环境层断了，别碰 mod 层，先去游戏内启用 UE4SS

### 检查方法

```powershell
# 1. ActiveModList 是否为空（空 = 游戏内没启用）
Get-Content "D:\Steam\steamapps\common\Palworld\Mods\PalModSettings.ini"
#    期望看到: ActiveModList=UE4SSExperimentalPW

# 2. UE4SS.log 的时间戳是否是最近
Get-Item "D:\Steam\steamapps\common\Palworld\Mods\NativeMods\UE4SS\UE4SS.log" | Select LastWriteTime
#    如果停更很久 → UE4SS 从那时起就没启动过

# 3. 日志里有没有 "Starting Lua mod"
Select-String -Path "...\UE4SS.log" -Pattern "Starting Lua mod"
```

**判据**：`UE4SS.log` 的修改时间变成"刚刚"，才算真的启动成功。

## 2. 【重要】`mods.txt` 会被官方部署重置

**症状**：明明写好了 `PWRecon : 1`，重启游戏后 mod 又不见了。

**根因**：`mods.txt` 被 Palworld 官方 mod 系统列为**受管文件**。
见 `Mods\ManagedMods\UE4SSExperimentalPW\InstallManifest.json` 的 `Files` 列表，
里面包含 `Mods/NativeMods/UE4SS/Mods/mods.txt`。

**触发重置的时机**（任一）：
- 在游戏内勾选/取消 mod
- 创意工坊 mod 更新
- 游戏本体更新

**连带影响**：`UE4SS-settings.ini` 里的 `EnableHotReloadSystem` 也会被重置回 `0`。

**解决**：重跑注册脚本（幂等，可反复跑）：

```powershell
powershell -ExecutionPolicy Bypass -File "D:\dsh-workspace\palworld-litematica\mod\PWRecon\deploy-all.ps1"
```

**推论**：不要把 `mods.txt` 当成稳定配置。任何"改了没生效"的情况，
先怀疑它被重置了。

## 3. UE4SS 只加载 `mods.txt` 里列出的 mod

这个版本（`v3.0.1 Beta #0 / SHA 2281fa31`）**没有 `enabled.txt`**
（日志会提 `enabled.txt` 但文件不存在），`mods.txt` 是唯一注册处。

把 mod 文件夹放进 `Mods\` **不等于**会被加载，必须有一行：

```
PWRecon : 1
```

格式：`名字 : 0或1`，冒号两侧空格随意。

## 3b. 【最关键】`ForEachUObject` 不可用，`FindAllOf` 才可靠

这是本项目排查过程中**最重要的一条**，节省的时间最多。

### 症状

用 `ForEachUObject` 遍历全部 UObject 做类名普查，结果：

```
普查完成: 遍历 414600 个 UObject, 不同类名 298930 个
类名                                                         实例数
FNameUserdata: 00000275ACC59868                                       8
FNameUserdata: 00000275ACF54D58                                       8
FNameUserdata: 00000275ACC6258                                        8
...
```

**21 MB 的输出文件，29 万行，每一行的"类名"都是 `FNameUserdata:<内存地址>`。**

### 原因

`obj:GetClass():GetFName()` 在这条路径上返回的**不是 UObject 的类名**，
而是 **UE4SS 的 Lua 包装对象名**，格式为 `<类型>:<地址>`。

所以：
- 每个包装对象的地址都不同 → "类名"全都唯一 → 不同类名 29 万个
- 用任何真实关键字（`build` / `mapobject` / `camp`）过滤都命中 0 个

**注意：不是 `ForEachUObject` 枚举不到对象**（它确实遍历了 41 万个），
**而是拿不到可用的类名**。这个区别很重要——不要误判成"世界没加载"。

### 反证：`FindAllOf` 完全正常

同一次运行里：

```lua
FindAllOf("PalBaseCampModel")
```

返回 5 个真实实例，且 `GetFullName()` 输出格式完全正常：

```
PalBaseCampModel /Game/Pal/Maps/MainWorld_5/PL_MainWorld5.PL_MainWorld5:PersistentLevel
  .BP_PalGameStateInGame_C_2147477735
  .PalBaseCampReplicator_2147477732
  .PalBaseCampModel_2147452584
```

### ✅ 结论与工作流

| API | 是否可靠 | 用在哪 |
|---|---|---|
| `FindAllOf(类名)` | ✅ **可靠** | **所有功能** |
| `FindFirstOf(类名)` | ✅ 可靠 | 取单例（GameState、Manager 等） |
| `ForEachUObject(cb)` | ❌ **不可用** | **放弃** |

> **不要再试图用 `ForEachUObject` 做"类名发现"。**
> 这条路在本项目的 UE4SS 版本上是死路，已经实测验证过，不要重复尝试。

**替代的探索策略——"从已知对象往下挖"**：

既然无法枚举出类名，就换方向：从**已经能拿到的对象**出发，
顺着它的属性、Outer、以及已知的相关类名去发现。

```lua
-- 1. 已知起点：这些类名是实测能拿到的
local camps = FindAllOf("PalBaseCampModel")     -- 5 个实例

-- 2. 顺着属性挖：试各种可能的字段名
for _, p in ipairs({"MapObjectModel","BuildObjects","ModuleMap","RawData"}) do
    local ok, v = pcall(function() return camps[1][p] end)
    if ok and v ~= nil then print(p, type(v)) end
end

-- 3. 顺着 Outer 往上挖：看清对象层级
local cur = camps[1]
for i = 1, 5 do
    cur = cur:GetOuter()
    print(cur:GetFullName())
end

-- 4. 对候选类名逐个试 FindAllOf（这一步才安全）
for _, cn in ipairs({"PalBuildObject","PalMapObjectManager",...}) do
    local objs = FindAllOf(cn)
    print(cn, objs and #objs or 0)
end
```

**代价**：这条路要试更多次，但**每次都很便宜**（`FindAllOf` 是精确查找），
远比一次性遍历 41 万个对象再失败要好。

## 3b-2. 【关键】属性不存在时 UE4SS 返回占位对象，不报错

**症状**：猜了 30 个属性名去挖 `PalBaseCampModel`，**全部"读取成功"**，
但值都是 `<userdata>`。看起来像"字段存在但读不出内容"。

**真相**：`obj.不存在的属性名` 在 UE4SS 里**不报错、不返回 nil**，
而是返回一个 **userdata 占位对象**。

**后果**：**不能靠"读取不报错"判断字段是否存在。**

```lua
-- ❌ 错误做法：这样判断会把所有不存在的字段都当成存在
local ok, v = pcall(function() return obj["MapObjectModel"] end)
if ok and v ~= nil then print("字段存在!") end   -- 永远成立，包括字段根本不存在

-- ✅ 正确做法：用 ForEachProperty 枚举真实属性名
obj:ForEachProperty(function(prop)
    local name = prop:GetFName()
    print(name, obj[name])
end)
```

**这个陷阱让我浪费了一轮**：30 个猜测字段名全部"命中"，
我还以为是"字段存在但类型不认识"，实际是一个都没命中。

**判据**：如果**每一个**猜测的字段名都返回非 nil 的 userdata，
那基本可以断定**全都没命中**——真实的属性表不可能包含所有你猜的名字。

## 3b-3. 【成功案例】"逐个试类名"是有效策略

在同一轮里，`FindAllOf` 逐个试类名**非常成功**：

```
PalBaseCampModel        -> 5 个      ✅
PalMapObjectManager     -> 1 个      ✅  ← 管理器单例
PalBuildObject          -> 649 个    ✅  ← 建筑部件！
PalMapObjectModel       -> 5459 个   ✅
PalBaseCamp             -> 0 个      ❌ 不存在
BP_PalBaseCampModel_C   -> 0 个      ❌ 不存在
```

**对比**：
- `ForEachUObject` 全量枚举 → 29 万行垃圾，**0 收获**
- `FindAllOf` 逐个试类名 → **一轮就拿到了建筑类**

**方法论**：既然枚举不可用，就用"**候选名单 + 逐个精确查询**"。
每次 `FindAllOf` 都很便宜（毫秒级），试 20 个类名远比遍历 41 万对象划算。

**候选名单怎么来**：
1. 从存档侧源码分析（本项目已从 `palworld-save-tools` 得到
   `PalBuildObject` / `PalMapObjectConcreteModelBase` 等线索）
2. 按 UE 命名习惯组合（`Pal` + `MapObject` + `Model`/`Manager`/`Replicator`）
3. 从已找到对象的 `GetClass():GetFullName()` 反推命名空间（`/Script/Pal.xxx`）
4. 顺 `GetOuter()` 链看父对象是什么类

**命名空间线索**：`Class = "Class /Script/Pal.PalBaseCampModel"`
说明真实类路径是 `/Script/Pal.<类名>`，可以据此推测同类命名。

---


**实测反例**（来自 `FindAllOf` 的真实结果）：

| 类名 | 实例数 | 看起来是否合理 |
|---|---|---|
| `PalBaseCampModel` | **5** | 真实存在 |
| `PalBaseCamp` | **0** | 看起来合理，但不存在 |
| `BP_PalBaseCampModel_C` | **0** | 看 UE 惯例似乎该存在，但不存在 |

而用关键字 `build` / `mapobject` / `structure` / `basecamp` / `palbox` /
`stage` / `spawner` 过滤 38 万个 UObject，**命中 0 个**。

**结论：Palworld 的类名无法靠命名习惯推断。**

**正确做法——先普查再精确查询**：

```lua
-- 第 1 步：普查，拿到真实类名（不依赖任何猜测）
local counts = {}
ForEachUObject(function(obj)
    local ok, n = pcall(function() return obj:GetClass():GetFName() end)
    if ok and n then
        local name = tostring(n)
        counts[name] = (counts[name] or 0) + 1
    end
end)
-- 遍历 counts 打印出来，人工/分析找出建筑类

-- 第 2 步：拿到真实类名后，改用精确查询（快且安全）
local objs = FindAllOf("真实类名")
```

**性能取舍**：

| 方法 | 速度 | 是否需要预先知道类名 |
|---|---|---|
| `FindAllOf(类名)` | 快 | **需要** |
| `ForEachUObject(cb)` | 慢（38 万对象约 2~3 秒，游戏会卡顿） | **不需要** |

普查用 `ForEachUObject`，正式功能用 `FindAllOf`。**别搞反**。

**热路径优化**：`ForEachUObject` 回调里只做最便宜的操作
（`obj:GetClass():GetFName()`），不要在里面做字符串匹配、
不要调 `IsDefaultObject()`、不要收集 `GetFullName()`。
把这些移到遍历之后，能大幅缩短卡顿时长。

## 3c-3. ★ 建筑类型的组织方式（重大发现）

`PalBuildObject` 的转储结果揭示了 Palworld 建筑系统的组织方式：

```
FullName : BP_BuildObject_MedicalPalBed_02_C
Class    : BlueprintGeneratedClass
           /Game/Pal/Blueprint/MapObject/BuildObject/BP_BuildObject_MedicalPalBed_02.BP_BuildObject_MedicalPalBed_02_C
Outer    : Level ...:PersistentLevel
```

**关键结论**：

1. **每个建筑类型 = 一个独立的蓝图类**
   路径规律：`/Game/Pal/Blueprint/MapObject/BuildObject/BP_BuildObject_<类型>_C`

2. **`PalBuildObject` 是所有建筑蓝图的父类**
   `FindAllOf("PalBuildObject")` 返回全部子类实例（649 个）——
   说明 UE4SS 的 `FindAllOf` **匹配子类**，不只是精确类名。

3. **建筑类型 ID = 类名，不需要找 ID 字段**
   从 `GetClass():GetFullName()` 就能提取出 `MedicalPalBed_02`。
   **不需要**去猜 `MapObjectId` 之类的字段。

4. **`StaticMeshComponent` 用属性名 `StaticMesh` 直接访问**
   ```lua
   local smc = buildObj.StaticMesh            -- StaticMeshComponent
   ```

5. **`MapObjectModel` 属性指向真实对象**
   ```
   MapObjectModel = OBJ: PalMapObjectModel
     ...:BP_PalMapObjectManager_C_2147479223.PalMapObjectModel_2147443064
   ```
   → 管理器在 `BP_PalMapObjectManager_C` 下

### ❌ 属性枚举仍然失败

`obj:ForEachProperty` / `class:ForEachProperty` 都返回
`FNameUserdata:<地址>` 作为属性名和类型——**和 `ForEachUObject` 同一个毛病**。

`prop:GetFName()` 返回的是 UE4SS 内部 wrapper 名。
**还没找到能拿到真实属性名的 API**（v0.4 里试 `prop:GetFullName()`）。

### ⏳ 仍未解决：Transform

`obj.Transform` / `obj.Location` / `obj.Rotation` 全是占位对象。

**原因**：UE 里 Actor 的位置**不在属性里**，而在
`RootComponent` 的 `ComponentToWorld`。所以要试的是：
- `obj:K2_GetActorLocation()` / `GetActorLocation()`
- `obj.RootComponent:GetComponentLocation()`
- `obj.RootComponent.ComponentToWorld`

v0.4 的 F7 就是系统性测试这些方式。

## 3c-4. ★★ 取坐标/朝向的正确 API（阶段 0 最后一块拼图）

**这是整个侦察最关键的一条。** 猜属性名完全行不通，必须用**函数调用**。

### ✅ 可用

```lua
local loc = actor:K2_GetActorLocation()   -- 返回 FVector，读 .X/.Y/.Z
local rot = actor:K2_GetActorRotation()   -- 返回 FRotator，读 .Pitch/.Yaw/.Roll

-- 等价备选（同样可用）
local loc2 = actor.RootComponent:K2_GetComponentLocation()
local rot2 = actor.RootComponent:K2_GetComponentRotation()
```

实测输出（`BP_BuildObject_Wood_Foundation_C`）：

```
K2_GetActorLocation     X=-160904.88 Y=-62645.07 Z=-942.94
K2_GetActorRotation     Pitch=-0.00 Yaw=-28.69 Roll=0.00
RootComponent:K2_GetComponentLocation()  X=-160904.88 Y=-62645.07 Z=-942.94
```

### ❌ 不可用（未绑定的方法返回 TrivialObject）

```lua
actor:GetActorLocation()      -- attempt to call a TrivialObject value
actor:GetActorRotation()      -- 同上
actor:GetActorTransform()     -- 同上
actor:GetComponents()         -- 同上
actor:ForEachProperty()       -- 同上
actor:GetActorBounds()        -- UFunction expected 4 parameters
```

**注意 `K2_` 前缀**：UE 里带 `K2_` 的是暴露给蓝图的版本，
**在这个 UE4SS 版本上只有 `K2_` 版本被正确绑定**。

### ❌ 属性读法全部失效

```lua
actor.Transform        -- 占位对象
actor.Location         -- 占位对象
actor.Rotation         -- 占位对象
actor.StaticMeshComponent  -- 占位对象（要换属性名）
```

**原因**：UE 里 Actor 的位置**不在属性里**，而在 `RootComponent` 的
`ComponentToWorld`（没绑定）。所以只能用 `K2_*` 方法。

### ⚠️ 判断返回值时的陷阱

UE4SS 返回的 `FVector` / `FRotator` 是 **keyed table，不是数组**：

```
type(v)  = table
#v       = 0                          -- ❌ 没有数字下标，所以 # 得到 0
.X/.Y/.Z = -161481.006 / -63697.722 / -942.938   -- ✅ 正确读法
数字下标  = [1]=nil [2]=nil [3]=nil [4]=nil       -- 确实没有数组下标
pairs    = Y=... Z=... X=...                       -- 是 keyed table
```

**所以绝对不要用 `#v == 0` 判断空值**——它不是空表。直接试读 `.X` / `.Pitch`。

（我第一轮就是因为 `tryCall` 里用 `#` 取长度得到 0，
把可用的向量误判成"空数组"，白绕了一整轮。）

### ✅ RootComponent 路线（备选，也拿到真结构）

```lua
local root = actor.RootComponent       -- SceneComponent，真对象
root.RelativeLocation                   -- ScriptStruct /Script/CoreUObject.Vector
root.RelativeRotation                   -- ScriptStruct /Script/CoreUObject.Rotator
root.RelativeScale3D                    -- ScriptStruct /Script/CoreUObject.Vector
```

实测值与 `K2_GetActorLocation()` **完全一致**（因为 Root 无父级偏移）：

```
RootComponent.RelativeLocation = X=-161481.01 Y=-63697.72 Z=-942.94
RootComponent.RelativeRotation = Pitch=-0.00 Yaw=-28.69 Roll=0.00
RootComponent.RelativeScale3D  = X=1.00 Y=1.00 Z=1.00
```

**症状**：`UE4SS.log` 里中文全变成 `宸插姞杞?` 这种乱码。

**原因**：UE4SS 把 `print()` 的输出按**系统 ANSI 代码页（GBK）**写进日志。
Lua 字符串本身是 UTF-8 字节，按 GBK 解释就乱码了。

**注意**：**写文件不受影响**（用 `io.open(path,"wb")` + 手动写 UTF-8 BOM）。

**解决**：控制台只输出 ASCII，完整中文写文件。

```lua
local function toAscii(s)
    s = tostring(s)
    local b = {}
    for i = 1, #s do
        local c = s:byte(i)
        if c >= 32 and c <= 126 then b[#b+1] = string.char(c)
        elseif c >= 128 then b[#b+1] = "?" end   -- 多字节字符占位
    end
    return table.concat(b)
end

local function out(s)
    table.insert(lines, s)             -- 文件：完整中文
    print(TAG .. " " .. toAscii(s))    -- 日志：纯 ASCII
end
```

**代价**：日志里中文变 `?`，但**结构化数据（类名/字段名）本来就是 ASCII**，
所以排查不受影响。真要读中文说明就看输出文件。

  （`BeginDeferredActorSpawnFromClass` / `FinishSpawningActor` / `World::SpawnActor`）。

### 📌 对渲染原型的影响（结合用户实测的半透明机制）

用户实测补充（重要）：

## 3f-6. ★★★ 第五轮实测定论（2026-09-26，PWRecon v0.8e）——自建 actor 基本不可行

**最小 Spawn 实验**（渐进式）结果：第 1 步就报了决定性错误：

```lua
km:RandomFloat(0.0, 100.0)   -- KismetMathLibrary 的 2 参数静态函数
--> [UFunction::setup_metamethods -> __call]
    UFunction expected 0 parameters, received 2
```

**关键结论**：不是"调用不通"（UFunction 的 `__call` 元方法确实触发了），
而是**多参数 UFunction 传参被 UE4SS 拒绝** —— 它认为这个函数期望 0 参数、却收到 2 个。

**参数个数规律（本项目 UE4SS 版本）**：
| 函数 | 参数数 | 调用结果 |
|---|---|---|
| `KismetMathLibrary.RandomFloat` | 2 | ❌ expected 0, received 2 |
| `Mesh:GetNumMaterials()` | 0 | ✅ 成功（recon_material） |
| `Mesh:GetMaterial(slot)` | 1 | ✅ 成功（recon_material） |

→ **这个 UE4SS 版本对 UFunction 只可靠支持 0/1 参数调用**。
而 spawn 必须的 `BeginDeferredActorSpawnFromClass` 有 **5-6 个参数**
（WorldContext, UClass, Transform, Collision, Owner, Instigator）——
**即使链路能触发，多参数传参也注定失败**。

**★ 定论**：**运行时创建新 actor/HISM（自建渲染）在这套 UE4SS+LuA 栈上基本不可行**。
不是代码问题，是 UE4SS 该版本的 UFunction 反射对多参数支持严重受限。
→ 想要"世界空间创建实体投影"，需要换机制（见下）。

**已确认可用的渲染相关 API**：`GetNumMaterials()`(0参) / `GetMaterial(i)`(1参)。
**无法确认/不可用**：`ForEachProperty` / `ForEachFunction`（TrivialObject）、
多参数 UFunction（spawn/SetMaterial 若需多参则存疑）。

### 📌 投影路线的现实重构

投影 = 在世界里画出"蓝图中的、尚不存在的"建筑，需要**新建渲染对象**。
既然自建 actor 不可行，剩下可考虑的方向（需用户决策）：

| 方向 | 可行性 | 说明 |
|---|---|---|
| **升级 UE4SS 版本** | ⚠️ 待测 | 换能正常传多参 UFunction 的版本，看 `SetupUFunction`/参数绑定修复是否解决。但 Palworld 专用编译版本有限，且升级有稳定性风险（踩坑记录 §8） |
| **换 mod 机制（PMK/C++）** | ⚠️ 大改 | 能从根本创建对象，但违背"纯 Lua + AI 可开发"的既定路线 |
| **近似投影（不画实体）** | ✅ 现约束下可做 | 用 Lua **读蓝图+算坐标**，输出玩家可参考的**提示**（如准星/坐标/小地图标记），不做半透明实体 |
| **游戏原生"放置预览"** | ❌ 单例 | 一次只能预览一个建筑，撑不起整蓝图投影 |

## 3f-7. ★ 第六轮侦察实测（2026-09-26，PWRecon v0.8f）——推翻"多参不可用"，定论渲染方向

**环境**：进世界先按 F9（recon_multiparam.txt），再开建造菜单按 F8（recon_preview.txt）。

### ✅✅ 重大反转：多参 UFunction「其实可用」——之前下错定论

上一轮（3f-6）基于 `RandomFloat` 报 "expected 0, received 2" 判定"多参不可用"，**错误**。

第六轮用更全面的引擎函数测试，**推翻**：

```lua
km:FMin(5.0, 3.0) -> ok=true, val=3.0    ✅ 2参可用!
km:FMax(5.0, 3.0) -> ok=true, val=5.0    ✅ 2参可用!
km:RandomInteger(10) -> ok=true          ✅ 可用
km:RandomFloat(0, 100) -> ❌ 失败         ← 只有这一个特殊（疑似 UE4SS 对该函数的绑定 bug）
```

**结论**：`RandomFloat` 的失败是**个别函数的绑定问题**，不代表多参 UFunction 不行。
`FMin`/`FMax` 这类 2 参数 double 函数**完全正常**。
→ **`BeginDeferredActorSpawnFromClass` 等 spawn 函数「可能真的能调用」**，
  3f-6 的"自建 actor 不可行"定论**撤销**。唯一未知：**FTransform(struct) 参数能否正确传入**。

> ⚠️ 教训（重要）：**不能基于单个函数推断 API 能力**。多参是否可行必须用多个函数交叉验证。
> 前一轮只测 RandomFloat 就下结论，导致 3f-6 出现错误定论，浪费了对方向的误判。

### ❌ 放置预览对象：Lua 彻底抓不到（用户建议的"复用游戏预览"路线堵死）

```
所有预览/建造菜单/UI 类（PalBuildPreview/PalBuildMenu/PalBuildObjectPreview/
BP_BuildObject_C/WBP_BuildMenu 等 ~19 个）-> 全部 0 个
PlayerController / Pawn 上的 BuildPreview/BuildSystem 等字段 -> 全空
```

**结论**：游戏的"放置预览"半透明幽灵**不在地图 Actor/对象枚举里，也不是 PalBuild* 类**。
它是 UMG UI 元素或玩家持有的临时渲染对象，Lua 通过 `FindAllOf` **抓不到、控制不了**。
→ 用户提出的"用游戏已有放置预览"**不可行**（Lua 无法操纵它）。

### ✅ 顺带确认的结构层级（PalBuildProcess 归属）

```
PalMapObjectManager_C_xxx
  └─ PalMapObjectModel_xxx          (5715 个)
       └─ PalBuildProcess_xxx       (5715 个，挂在 Model 下)
```
→ `PalBuildProcess` 是 manager→model→process 三层中的最内层，仅状态容器（3f-3 已证）。

### 🔑 渲染方向的最终定论

| 路线 | 结论 | 依据 |
|---|---|---|
| **自建 actor/HISM** | ✅ **重新可行**（多参可用） | FMin/FMax 证明多参调用正常；唯一待验证 FTransform(struct) 传参 |
| **复用游戏预览** | ❌ 不可行 | 预览对象 Lua 抓不到 |
| **复用 ImposterChunk** | ❌ 不可行 | 那是真实建筑 |

→ **当前最佳路线：自建 actor/HISM + 半透明材质**。
   下一步先验证 **FTransform(struct 参数) 能否传给 UFunction**（用 `KismetMathLibrary.MakeTransform`
   构造后传一个接受 transform 的函数，或用 spawn 真试一次）。若 struct 传参通 → 渲染可行，开写渲染原型。

## 3f-8. ★★ 第七轮（方法论纠正 + 决定性实验设计）

**背景**：前两轮出现了「错误结论 → 反转 → 但反转也不够严谨」的连锁。
本节记录**怎么才算严谨地验证 API 能力**。

### ❌ 3f-6 的错误在哪

只用一个函数 `km:RandomFloat(0.0, 100.0)` 失败，就断言
"多参 UFunction 全不可用、自建渲染不可行"。

**错在**：`RandomFloat` 报的是 `expected 0 parameters, received 2` ——
这是 **UE4SS 对该函数的参数元数据缺失**（同理 `GetActorBounds` 报
`expected 4 parameters, received 0`）。**这是个别函数的绑定缺陷，不是普遍规律。**

> **不能基于单个函数推断 API 能力。**

### ⚠️ 3f-7 的反转也不够严谨

用 `km:FMin(5,3)=3` / `km:FMax(5,3)=5` 反转，说多参可用。

**问题**：返回值 3 和 5 **无法区分**两种情况：
1. 真的调用了 `FMin` 并传入两个参数
2. 函数桩返回了某个默认值 / 碰巧等于期望

**单点验证永远无法排除"巧合"。**

### ✅ 严谨的验证方法：用「算错就会得到明显不同结果」的函数

| 测试 | 期望 | 为什么能判别 |
|---|---|---|
| `FClamp(3, 0, 5)` | **必须 = 3** | **3 不是任何边界值**，参数没传进去不可能刚好得 3 |
| `FClamp(10, 0, 5)` | 必须 = 5 | 上界截断 |
| `FClamp(-3, 0, 5)` | 必须 = 0 | 下界截断 |
| `FClamp(7, 2, 4)` | 必须 = 4 | 换一组区间，排除"硬编码 5" |
| `Lerp(0, 10, 0.25)` | 必须 = 2.5 | 非整数、非端点 |
| `FMin(2, 9)` / `FMax(2, 9)` | 必须 = 2 / 9 | **交叉验证参数顺序**——若参数顺序错乱，FMin 会得 9 |

**关键原则**：
- **多个用例，期望值互不相同** —— 参数没真传进去不可能全部命中
- **包含非端点、非整数值**（如 2.5、3）—— 排除"返回默认值碰巧对了"
- **交换参数语义**（`FMin(2,9)` vs `FMin(9,2)`）—— 排除"参数顺序被忽略"

**这就是第七轮脚本（v0.9）实验 1 的设计。**

### 第七轮还要验证的（按重要性）

| 实验 | 验证 | 为什么重要 |
|---|---|---|
| 2 | **`FTransform` struct 能否传入**（`km:BreakTransform(transform)` 解出 Translation.X 是否=100） | ★ **spawn / AddInstance 的唯一拦路虎** |
| 4 | **`HISM:AddInstance` 是否绑定** | ★ 比 spawn actor 更优：游戏自己就用 HISM 画结构件，**加实例不需要创建 actor** |
| 5 | `Mesh:SetMaterial` 是否绑定 | 若能改材质，"用现有建筑当投影"可行 |
| 3 | struct 传出（`GetActorLocation` vs `K2_GetActorLocation` 对比） | 基线对照 |
| 6 | `SetActorTransform` 是否绑定 | 移动 actor 的能力 |

脚本：`mod/PWRecon/Scripts/main.lua` v0.9，按 **F8** → `recon_multiparam2.txt`

### 📌 一条通用的排查原则（本轮最大收获）

> **验证 API 能力时，不要只看"调用是否成功"或"返回值是否合理"，
> 要设计「错误输入会得出明显不同结果」的用例。**

这条同时解释了为什么之前的多个误判：
- 只测一个函数 → 误判"全部不可用"
- 只看返回值合理 → 无法排除巧合

## 3f-9. ★★★ 崩溃事故复盘（2026-09-26 16:58）——最重要的一课

### 事故现象

按 F8 → 没生成 `recon_multiparam2.txt`；再按 F7 → **游戏崩溃**
（`EXCEPTION_ACCESS_VIOLATION`，调用栈只有 `UE4SS` + `Palworld_Win64_Shipping`，
**没有 Lua 脚本栈**）。

### 根因：一次"去重"编辑误删了函数定义

UE4SS.log 里其实写得清清楚楚：

```
[Lua::call_function] lua_pcall returned LUA_ERRRUN =>
  main.lua:816: attempt to call a nil value (global 'playerPawn')
```

我为了精简脚本，用脚本从旧文件里"切出导出段 + 拼上第七轮代码"，
**去重逻辑误删了 `playerPawn` 的定义，但调用处还在**。
Lua 抛错误 → UE4SS 处理不当 → 游戏崩溃。

### ❌ 我的验证方法为什么没拦住它

事故前我做了"校验"，但**两个手段都是假的**：

| 手段 | 为什么无效 |
|---|---|
| 括号配平检查 | `playerPawn` 缺失**不影响括号平衡**，照样全绿 |
| 手写的"关键函数存在性列表" | **偏偏漏了 `playerPawn`**——手写清单本质上是不可靠的 |

> **教训：用一个手工维护的列表去验证代码完整性，等于没验证。**
> 必须**从代码本身反向推导**出"被引用了什么"，再去核对"定义了没有"。

### ✅ 正确做法：`tools/luacheck.py`（已实现）

静态提取**所有被调用的标识符**，反查是否定义过、或属于已知安全全局：

```powershell
& $py tools\luacheck.py mod\PWRecon\Scripts\main.lua
```

它会报告：
- **未定义的被调用标识符**（就是这次的事故类型）
- 括号/关键字配平
- 重名函数定义（编辑事故的典型症状）
- `pcall(StaticFindObject, "arg")` 危险写法
- `print()` 里的中文（会导致日志乱码）

**已回归验证**：用它扫崩溃那一版，准确报出
`playerPawn 行 [816]`；扫修复版则全绿。

> ★ **硬性规矩：任何改动 main.lua 之后，部署前必须跑 luacheck，且必须全绿。**

### 🔴 第二个坑：`pcall(StaticFindObject, "路径")` 会崩

对比两种写法：

```lua
-- ✅ 之前 6 轮一直能用（有闭包包裹）
pcall(function() return StaticFindObject("/Script/Engine.Default__KismetMathLibrary") end)

-- ❌ 我写的（直接传函数引用 + 字符串参数）
pcall(StaticFindObject, "/Script/Engine.Default__KismetMathLibrary")
```

后者的调用栈是 `UE4SS → Palworld_Win64_Shipping ×N` 的**原生层访问违例**。
**结论：`StaticFindObject` 必须用闭包包裹。**

（注意：`pcall(FindAllOf, "类名")` 这种写法实测**可用**，前 6 轮都这么写。
只有 `StaticFindObject` 有这个毛病。）

### 🔴 第三条：运行时探测引擎函数 = 高风险

今天因为"运行时调用引擎函数"崩了不止一次。区分清楚：

| 操作 | 风险 |
|---|---|
| **读**属性 / 读方法引用（`obj.Foo`） | ✅ 安全 |
| **读**已知安全的 getter（`K2_GetActorLocation`、`GetNumMaterials`） | ✅ 安全 |
| **调用**未验证的引擎函数（`StaticFindObject`、spawn、`AddInstance`） | 🔴 **高风险，可能崩** |
| **调用**会改世界状态的方法（`SetMaterial`、`SetActorTransform`） | 🔴 高风险 + 污染世界 |

**所以侦察脚本必须遵守"只读原则"**：

1. 只读属性和方法引用，**不调用**任何可能改状态的方法
2. 调用引擎函数一律用 `pcall(function() ... end)` 闭包包裹
3. 想验证"能不能调用"，先只探测**方法引用是否存在**（读属性是安全的），
   把真正调用留到风险可控、有回滚手段的单独一轮

### 🚑 崩了之后怎么快速恢复

**如果 mod 一装就崩，最快的禁用方式**（不需要进游戏）：

```
改 D:\Steam\steamapps\common\Palworld\Mods\NativeMods\UE4SS\Mods\mods.txt
把 "PWRecon : 1" 改成 "PWRecon : 0"
```

或直接改名目录：

```
...\UE4SS\Mods\PWRecon  ->  PWRecon.off
```

### 一句话总结

> **编辑代码用脚本自动化很好，但自动化本身必须被真正的静态检查兜住。**
> "括号平衡"和"手写清单"都拦不住"函数被误删"。

## 3f-10. ★★★ 第二次、第三次崩溃 + 方向决策（2026-09-26 17:05）

### 事故经过

修好 `playerPawn` 后重试，**按 F8 又崩了**。崩溃日志：


对照 UE4SS.log 时间线：

### 关键教训：读操作也不一定安全

之前我把"只读"当成安全边界，**这个假设是错的**：

| 操作 | 在稳定状态下 | 在**世界重载**期间 |
|---|---|---|

## 3i. ★ mesh 同一类型的不同实例可用性不一致 → 必须按类型聚合

> 注：本节之后接第 4 节（热键 API）。

**这条是在处理真实导出数据时发现的，容易踩。**

### 现象

同一个建筑类型 `MedicalPalBed_02`：

| 数据来源 | `Mesh` 可读? |
|---|---|
| `recon_alltypes.txt` 采样（主基地实例） | ✅ `SM_PalBedPrimitive` |
| `buildings_raw.tsv` 框选（另一个据点实例） | ❌ 读不到 |

**即：`obj.Mesh` 的可读性在不同实例间不一致。**

### 后果

如果"逐实例取 mesh"，生成的蓝图里同一类型会**时有时无**：

```
base2 蓝图（逐实例取）:
  有 mesh: FarmBlockV2_Berries → SM_FarmGround
           ItemChest           → SM_ChestWood
           ItemChest_03        → SM_ChestIron
  无 mesh: MedicalPalBed_02 / CampFire / Spa / PalBoxV2 ...  ← 但它们在别处能读到
```

### ✅ 正确做法：按类型聚合

**不要逐实例决定 mesh，要在生成蓝图时按类型聚合** ——
扫描该类型的所有实例，取**第一个有值的**作为该类型的代表网格：

```python
# tools/blueprint.py build_blueprint()
type_mesh = {}
for e in entries_m:
    t = e["type"]
    mesh = e.get("mesh")
    if mesh and not type_mesh.get(t):
        type_mesh[t] = mesh          # 该类型第一次读到 mesh 就记住

# 实例自己没有 mesh 时回填类型的代表网格
mesh = e.get("mesh") or type_mesh.get(e["type"])
```

**好处**：
- 同一类型在蓝图里 mesh 一致（不会有的有、有的没有）
- 任何蓝图文件里的类型表都尽量完整
- 即使某个据点里读不到，只要**任意一个实例**能读到就能补上

### 数据实测（某存档两个据点）

| 蓝图 | 建筑数 | 类型数 | mesh 覆盖 |
|---|---|---|---|
| 主基地（300 米筛选） | 358 | 64 | — |
| 第二据点（框选 200 米） | 35 | 11 | **3/11** |

**结构件（墙/地板/屋顶）永远没有 mesh** —— 它们大概率是 ISM 批量渲染的。
所以 mesh 覆盖率天然偏低，这是正常的，不是 bug。

### 待办

**建一张"类型 → mesh 资产"的完整映射表** `data/type_map.json`。
做法：从多次不同据点的导出中**累积** `type → mesh`，逐渐补全。
写入蓝图格式文档的第 7 节。

## 4. 热键 API：不要用 `RegisterKeyBind`

**症状**：mod 加载成功（日志有"已加载"），但按键无反应，
日志显示 `F7 注册失败:` 后面跟着一个**空的错误信息** + traceback。

**根因**：UE4SS 的现代 API 不是 `RegisterKeyBind`。

看 `Mods\Keybinds\Scripts\main.lua` 里官方自己的写法：

```lua
-- 正确写法（Key 枚举 + 修饰键表）
RegisterKeyBindAsync(Key.J, {ModifierKey.CONTROL}, Callable)

-- 判断是否已占用
IsKeyBindRegistered(Key.J, {ModifierKey.CONTROL})
```

我最初写的 `RegisterKeyBind("F7", fn)`（字符串键名 + 旧 API）**会失败**。

**另一个关键观察**：FirstPerson 已经**弃用** `RegisterKeyBind`，
改成注册**游戏原生可重映射的 Player Action**（所以 F6 能在游戏"控制设置"里改键）。
它源码里的注释：

```
- 移除 fp_config.lua 热键字段（KeyFP/KeyRidingFPMod）与 RegisterKeyBind
[FP-KEY] native actions registered (F6 / unbound)
```

**另一个关键观察**：FirstPerson 已经**弃用** `RegisterKeyBind`，
改成注册**游戏原生可重映射的 Player Action**（所以 F6 能在游戏"控制设置"里改键）。
它源码里的注释：

```
- 移除 fp_config.lua 热键字段（KeyFP/KeyRidingFPMod）与 RegisterKeyBind
[FP-KEY] native actions registered (F6 / unbound)
```

### ✅ 已实测确认（2026-09-26，由 PWKeyTest 探测）

**环境**：UE4SS `v3.0.1 Beta #0 / Git SHA 2281fa31`

存在的全局符号：

| 符号 | 类型 |
|---|---|
| `RegisterKeyBind` | function |
| `RegisterKeyBindAsync` | function |
| `IsKeyBindRegistered` | function |
| `Key` | table（枚举） |
| `ModifierKey` | table（枚举） |
| `UnregisterKeyBind` | **不存在** |

`Key` 枚举的实际值（Windows VK 码，已实测）：

```
Key.F1=112  Key.F5=116  Key.F6=117  Key.F7=118  Key.F8=119
Key.F9=120  Key.F10=121 Key.F11=122 Key.F12=123
Key.J=74    Key.K=75    Key.L=76    Key.H=72    Key.N=78
Key.M=77    Key.B=66    Key.G=71    Key.R=82    Key.T=84
Key.Y=89    Key.U=85
```

**注册签名实测结果**：

| 写法 | 结果 |
|---|---|
| `RegisterKeyBind("F7", fn)` | ❌ **失败**（字符串键名不行） |
| `RegisterKeyBind(Key.F8, fn)` | ✅ 成功 |
| `RegisterKeyBindAsync(Key.F9, {}, fn)` | ✅ 成功 |
| `RegisterKeyBindAsync(Key.F10, {ModifierKey.CONTROL}, fn)` | ✅ 成功 |
| `RegisterKeyBindAsync("F11", {}, fn)` | ❌ **失败**（字符串还是不行） |

### 🔑 结论

> **热键必须用 `Key` 枚举，不能传字符串。**

推荐写法（按优先级）：

```lua
-- 首选：和内置 Keybinds mod 完全一致的写法
RegisterKeyBindAsync(Key.F7, {}, handler)

-- 也有同步版可用
RegisterKeyBind(Key.F7, handler)
```

**健壮的注册辅助函数**（PWRecon 里已实现，可复用）：

```lua
local function tryBind(label, fn)
    if pcall(RegisterKeyBindAsync, Key[label], {}, fn) then return true end
    if pcall(RegisterKeyBind, Key[label], fn) then return true end
    return false
end
```

### ⌨️ 键位分配表（重要，别再踩）

按键是稀缺资源，实际可用的很少。**实测确认的占用情况**：

| 按键 | 状态 | 被谁占用 |
|---|---|---|
| `F1`–`F4` | ❌ 不可用 | UE4SS 自己（`GuestKey` / 控制台切换） |
| `F5` | ❌ 已占用 | FirstPerson mod（FOV） |
| `F6` | ❌ 已占用 | FirstPerson mod（第一人称切换） |
| `F7`–`F9` | ✅ **本 mod 使用** | PWRecon |
| `F10` | ⚠️ 未验证 | 可能被 Steam 覆盖层占用 |
| `F11` | ❌ **系统占用** | 游戏/系统：全屏 ↔ 窗口化切换 |
| `F12` | ❌ **系统占用** | **Steam 自带截图** |
| `Ctrl+X` | ❌ **不可用** | 游戏把 Ctrl 绑给了**翻滚**动作 |
| 字母键 | ⚠️ 未知 | Palworld 用 UE5 Enhanced Input，**键位不在 ini 文件里**，无法从文件判断哪些空闲 |

**结论：只用 `F7`–`F9`。** 加修饰键（尤其 Ctrl）会在游戏里触发别的动作，
比不用还糟。

**踩过的坑**：曾经把诊断功能绑到 `F11` / `F12`，结果和系统功能冲突——
按 F11 会切窗口模式，按 F12 会触发 Steam 截图。**不要再绑定 F10 以上的键。**

**因此：功能要往 F7-F9 三个键里塞，塞不下就合并或删掉无用功能。**
不要为了"多一个入口"去占 F10+ 或加 Ctrl 组合。

### ⚠️ `IsKeyBindRegistered` 的结果不可靠

实测发现它和实际注册状态不一致：

```
IsKeyBindRegistered(Key.F8,  {}) = true    ← 确实注册了
IsKeyBindRegistered(Key.F9,  {}) = true    ← 确实注册了
IsKeyBindRegistered(Key.F10, {}) = false   ← 但注册是成功的，按键也真的能触发
```

所以**不要用 `IsKeyBindRegistered` 判断注册是否成功**——用它做冲突检测会误判。
判断注册成功要看 `pcall` 的返回值。

### ⚠️ F 键可能被游戏占用

`UE4SS-settings.ini` 里的 `GuestKey` 等设置可能占用 `F1-F4`。
内置 `Keybinds` mod 默认用了 `Ctrl+J / Ctrl+H / Ctrl+N / Ctrl+数字`，与 F 键不冲突。
但如果某次按 F7 有别的反应（比如打开控制台），说明被占用了，改用 `Ctrl+F7`。

### 💡 备选：注册为游戏原生 Player Action

FirstPerson 走的路——注册成游戏的 Player Action，好处是：
- 能在游戏原生"控制设置"菜单里**改键**
- 由游戏的 `KeyConfigSettings` 持久化
- 不会和其它 mod 抢键

代价是代码复杂得多（要操作 `KeySettings`、`WBP_*_Settings` 等 UMG 对象）。
**先用 `RegisterKeyBindAsync`，只在必要时才走这条路。**

## 4b. 另外两个实测确认的坑

### `io.open` 按 ANSI 写文件，中文会乱码

UE4SS 里 `io.open(path, "w")` 的编码跟系统 ANSI 代码页走（这里是 GBK）。
直接写中文会变成乱码，而且 Windows 记事本可能识别错。

**解决**：以二进制模式写，并手动加 UTF-8 BOM：

```lua
local f = io.open(path, "wb")
f:write("\239\187\191")   -- UTF-8 BOM = EF BB BF
f:write(text)
f:close()
```

### `FindAllOf` 需要准确的类名

`FindAllOf("PalBuildObject")` 这种精确匹配很高效，但**前提是你知道类名**。
而项目早期恰恰不知道。

**两条路**：

| 方法 | 优点 | 缺点 |
|---|---|---|
| `FindAllOf(类名)` | 快、安全 | 必须先知道类名 |
| `ForEachUObject(cb)` | **不依赖类名**，能直接暴露真实类名 | 要遍历上百万对象，会卡顿 |

**策略**：早期用 `ForEachUObject` 做一次"发现"，拿到真实类名后，
正式功能全部改用 `FindAllOf`。
（PWRecon 的 F7 用前者，F10 是专门的深度扫描）

**性能技巧**：`ForEachUObject` 的回调里，先做最便宜的判断（取类名比字符串），
不匹配立刻 `return`，能大幅降低开销。跳 CDO 的 `obj:IsDefaultObject()`
要放在关键字匹配**之后**才调用。

## 6. PowerShell 5.1 的三个坑

这个环境是 Windows PowerShell **5.1**（没有 `pwsh` 7）。写脚本时注意：

**坑 1：含中文的 .ps1 必须带 UTF-8 BOM**

PS 5.1 对无 BOM 的文件按 ANSI(GBK) 读，中文会变乱码。
用 `edit`/`write` 工具编辑后 BOM 可能丢失，需要补：

```powershell
$f="路径.ps1"
$txt=[System.IO.File]::ReadAllText($f,[System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($f,$txt,(New-Object System.Text.UTF8Encoding($true)))
```

**坑 2：`->` 会破坏双引号字符串**

`->` 在 PowerShell 里是重定向符，写在双引号字符串里也可能导致
"字符串缺少终止符"的诡异错误。用 `到:` 或 `=>` 代替。

**坑 3：单引号字符串里嵌套双引号会提前结束字符串**

```powershell
Bad '  例如 "D:\path"'     # ← 错，会解析出错
Bad "  例如 $($path)"       # ← 对
```

**这些错误的报错行号会漂移**，很难定位。建议改完就做静态语法检查：

```powershell
$txt=[System.IO.File]::ReadAllText($f)
$e=$null;$t=$null
$null=[System.Management.Automation.Language.Parser]::ParseInput($txt,[ref]$t,[ref]$e)
if($e){ $e|ForEach-Object{ "L$($_.Extent.StartLineNumber): $($_.Message)" } } else { "OK" }
```

> ⚠️ 注意：如果诊断代码用 `Get-Content` 读文件，会按 GBK 读导致**假错误**。
> 必须用 `[System.IO.File]::ReadAllText($f)`（会自动识别 BOM）。

**`[exit code: 1]` 不一定是真失败**
Windows 下被强制终止的进程会以 exit 1 结束但没有信号标记。
如果命令是被中断的，当作"被打断"而不是"命令失败"。

**pip 可能长时间无输出**
`pip install` 有时会卡住不动（遇到过 120s+）。可以换解释器重试，
或改用别的方案。`ooz` 包在 PyPI 上不存在，别浪费时间。

**游戏 log 位置**
`C:\Users\<用户名>\AppData\Local\Pal\Saved\Logs\` —— 但里面主要是 `cef3.log`（网页组件），
游戏本体日志不在这里，调试 mod 一律看 `UE4SS.log`。

**UE4SS 崩溃转储**
`Mods\NativeMods\UE4SS\crash_*.dmp`，0 字节表示崩溃时没来得及写内容。
老版本 UE4SS 有 FText 相关的崩溃 bug（官方 release 说明确认）。

**UE4SS 版本管理与版本脱节**

```
已安装(旧):  16.5MB dll  2026-08-08  experimental-palworld-5
创意工坊(新): 20.0MB dll  2026-09-05  2281fa31
游戏本体:    Palworld-Win64-Shipping.exe  2026-09-15
```

游戏 8 月到 9 月更新了两次，UE4SS 就彻底失效了。
**这个项目的维护成本主要在跟版本，不在写功能。**

下载 UE4SS 必须用 `Okaetsu/RE-UE4SS`（Palworld 专用编译），
**不是** `UE4SS-RE/RE-UE4SS`。因为 Palworld 0.4.1.5 引入了引擎改动。

**官方明确警告**：创意工坊版和手动安装版**不能同时存在**，否则游戏必定崩溃
（会尝试加载两份 UE4SS）。

## 10. PWProjection 阶段的新坑（2026-09-26 深夜）

用户决定**自己写 mod**（SBB 只作架构参考）之后，新踩到的几条。
每一条都是"如果不知道就会浪费一整轮"的那种。

### 10-1 ★ 读别人代码得出的"架构理解"必须标不确定度

**我犯的错**：分析 Simple Building Blueprints 时我写下了

> "核心手法是**锚点复用**：借一件已放置建筑当宿主，
> `AddComponentByClass` 挂幽灵组件，用完 `restore_transform` 恢复"

这个结论**写进了交接笔记**，而它是错的。

后来为了照抄这个模式，我重新精读源码，才发现：

| 我当时的理解 | 实际情况 |
|---|---|
| 借一件**已放置的建筑**当宿主 | 用 `world:SpawnActor(session_class, {}, {})` 生成**它自己的**会话 Actor，类来自它自带的 pak |
| "锚点" = 被借用的建筑 | 代码里的 anchor 是**用户在蓝图里选中的锚点建筑**，是数据概念 |
| `restore_transform` 是"用完把建筑放回去" | 是锚点代理的校准逻辑 |

**代价**：如果我没重读，`PWProjection` 会照着一个不存在的手法去设计。

**规矩**：读源码得出的结论要写清楚**依据到哪一层**——
"我看到了这一行调用"是事实，"所以我推断整体是这么运作的"是假设。
两者必须分开写，否则错误理解会被下一个会话当成事实继承下去。

### 10-2 ★ AI 新写的 .ps1 必须带 UTF-8 BOM

**症状**：`deploy.ps1` 用 UTF-8（无 BOM）写出来，运行报

```
At deploy.ps1:164 char:89
The string is missing the terminator: '.
At deploy.ps1:74 char:34
Missing closing '}' in statement block or type definition.
```

**但第 164 行只有 25 个字符，第 74 行的花括号明明配平。**

**原因**：Windows PowerShell 5.1 读 `.ps1` 时，**没有 BOM 就按 ANSI(GBK) 解码**。
文件里的中文被当成 GBK 字节解，某些中文字的第二个字节正好是 `0x27`(`'`)
或 `0x5C`(`\`)，于是**吞掉引号、破坏语法树**——
报错行号是解析器"晕了之后"的位置，不是真凶。

**解法**：

```powershell
$enc = New-Object System.Text.UTF8Encoding($true)   # $true = 带 BOM
[System.IO.File]::WriteAllText($path, $text, $enc)
```

**规矩**：用工具新生成的任何含中文的 `.ps1`，写完立刻补 BOM 并跑一次 `-DryRun`
验证能解析。`tools/cleanup.ps1` 当时是手工建的所以有 BOM，
`mod/PWProjection/deploy.ps1` 是 AI 写的所以没有 —— 差别就在这里。

**★ 2026-09-27 补充：不只是"新建"，【修改】也会把 BOM 弄丢。**
用编辑器/补丁工具改一行 `deploy.ps1`（哪怕只改了个提示文字），
保存后 BOM 可能就没了 —— 之后玩家一跑就报上面那种"莫名其妙"的语法错。
所以规矩要升级成：

```powershell
# 改完任何含中文的 .ps1，都查一次（.NET API 记得用绝对路径）
$p = (Resolve-Path ".\mod\PWProjection\deploy.ps1").Path
$b = [System.IO.File]::ReadAllBytes($p)[0..2]
"{0:X2} {1:X2} {2:X2}" -f $b[0],$b[1],$b[2]   # 期望 EF BB BF

# 丢了就这样补回来（读的时候按 UTF-8，写的时候带 BOM）
$text = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($true)))
```

> 顺带：`[System.IO.File]::ReadAllBytes("相对路径")` 在 PowerShell 里
> **按进程 CWD 解析**，不是按 `Set-Location` 之后的目录 ——
> 所以上面用 `Resolve-Path` 转成绝对路径。这个坑也踩过（第 6 节）。

### 10-3 ★ "字符串里嵌引号"是词法错误，引号配平查不出来

```lua
return true, "可用（游戏自带的"可放置"材质）"
```

Lua 会把它切成 `"可用（游戏自带的"` + 标识符 `可放置` + `"材质）"`。
**全局引号数量是偶数，括号也配平** —— 老的 luacheck 全部通过。
真跑起来就是"attempt to call a nil value"级别的运行期错误。

**解法**：把 `tools/luacheck.py` 从"正则+计数"升级成**真正的 Lua 词法器**：

1. 逐字符扫描，正确处理注释 / 长注释 / 长字符串 / 短字符串 / 数字 / 标识符
2. **短字符串跨行 → 报错**（Lua 不允许）
3. **代码区出现非 ASCII 字符 → 报错** ← 这条直接抓住上面那个 bug
   （因为 `可` 不是合法 Lua 标识符字符，必然落在代码区）
4. **块结构平衡**：`function`/`if`/`for`/`while`/独立 `do`/`repeat`
   与 `end`/`until` 配对（`for ... do` 的 `do` 不重复计数，靠"待配对 do"计数器）

### 10-4 ★ 检查工具本身必须被测试

老 luacheck "通过"过一次，然后游戏崩了（`playerPawn` 被误删）。
**一个没被测过的检查工具，它给的"通过"没有意义。**

所以加了 `tools/luacheck_selftest.py`：用 7 个"已知会崩"的样例
反向验证 luacheck 真的能抓到，再用 3 个"已知正确"的样例确认不会误报。

当前 **10/10 通过**。这 7 个坏样例里有两个是本项目**真实出现过**的：

- `embedded_quote.lua` —— 就是 10-3 那个 bug
- `undefined_global_call.lua` —— 就是那次崩溃的 `playerPawn`

**误报和漏报一样有害**：如果工具总是误报，人就会开始忽略它。
所以 `good_module.lua` / `good_blocks.lua` / `good_long.lua`
专门覆盖"模块表 + 点号函数 + 参数 + 中文字符串 + 各种块嵌套"，
确保正常代码不会被误伤。

### 10-5 ★ `pcall(原生函数, 参数)` 这个模式要一律封死

`pcall(StaticFindObject, "路径")` 崩过游戏（见 3f-9）。
但 `pcall(FindAllOf, "类名")` 和 `pcall(LoadAsset, 路径)` 一直没事，
所以很容易觉得"只有 StaticFindObject 特殊"。

**正确的态度**：不去猜哪个原生函数安全，**统一改成闭包形式**：

```lua
-- 不要
local ok, v = pcall(FindAllOf, "PalBuildObject")
-- 要
local ok, v = pcall(function() return FindAllOf("PalBuildObject") end)
```

成本几乎为零，换来的是"这一类风险整体消失"。
luacheck 现在会对"直接把大写开头的原生函数交给 pcall"给出**提示**。

### 10-6 ★ 分步探测要记"开始"而不是"结束"

PWRecon 的 `worldcheck` 是每步做完写一行。问题是：
**如果第 K 步崩了，文件里最后一行是第 K-1 步的结果**，
只能推断"崩在第 K 步"，遇到"第 K 步没输出但也没崩"就说不清。

`pwpr_probe` 改成**执行前先写 `STEP n START` 并落盘**：

```
[17/28] START spawn_host  (生成宿主 Actor（第一个会创建对象的步骤）)
       类型: write
```

**文件里最后一条 START 就是崩溃点**，没有歧义。

再加一条：即使 `probe_max_step` 让中途停下，**只要已经创建过宿主，
销毁步骤也会补跑**（`always = true`）—— 不会留下残留 actor 在存档里。

### 10-7 ★ 游戏主线程上做几万次 `GetFullName()` 会卡住游戏

`FindAllOf("StaticMesh")` 在有大基地的存档里能返回**几万个**对象。
对每个调 `GetFullName()` 是原生调用 + 字符串分配，跑完要 1~3 秒，
**而这是在游戏线程上跑的 → 画面直接冻住**。

更糟的是后续的"类型 → 网格"名字匹配：79 个类型 × 3 万条注册表
= 数百万次 `string.find`。

**解法**：按"材料词"（类型名的第一个词，如 `Wood`/`Stone`）**预先分桶**。
桶是惰性建的，建一次之后每次匹配只扫几百条而不是三万条。

用法上的规矩：这类"会卡一下"的操作要在日志里**明说**
（`mesh_registry` 那一步的标题就写了"可能要几秒，会卡一下"），
否则用户会以为游戏卡死了。

## 11. 崩溃归因方法论（2026-09-26 18:02 那次崩溃的复盘）

用户报："我刚跳了一下就崩了，不确定 Y 键有没有按下去"。

**先别改代码，先读日志。** 下面这套顺序能在 10 分钟内把"是不是我们的锅"定下来。

### 11-1 第一步：证明"我们的 Lua 到底跑了没有"

关键认识：**`Log.emit` 是先写控制台（`print`）再进缓冲的**。
所以只要某个热键回调进来了，`UE4SS.log` 里就一定有 `[PWPR]` 开头的内容 —— 
**即使它随后崩溃、`pwpr.log` 一个字都没落盘。**

查 `UE4SS.log`：

```
[18:02:21.4748142] [Lua] [PWPR] ??????: 0 ???   ...
[18:02:21.4751259] [Lua] [PWPR] bound: F7=help, F8=reload-cfg, Y=capture-near, ...
（之后一直到 18:02:53 崩溃，没有任何一条 [PWPR]）
```

**结论：Y 没按下去。** 我们的 19 个回调一次都没进。
（帮助键 F7 会打 ASCII，也没有 → 确实一个键都没按。）

### 11-2 第二步：读崩溃栈，定位"崩在谁的地盘"

`C:\Users\<你>\AppData\Local\Pal\Saved\Crashes\UECC-...\CrashContext.runtime-xml`
里有多个 `<CallStack>`，**别只看第一个**。真正有用的是 `<PCallStack>` —— 那是崩溃线程的帧指针链。

**从下往上读**（最下面是调用者）。这次是：

```
KERNEL32 → ntdll
Palworld + 0xb82704              ← 引擎调进来
UE4SS   + 0x4206d5               ← 进入 UE4SS
Palworld + 0x3669fb5 ... 0x52771dc   ← UE4SS 又调了一长串引擎函数
UE4SS   + 0x420e77               ← ★ 崩在这里
```

`UE4SS + 0x420xxx` 两次夹着一长串引擎帧 —— 这是 **UE4SS 的钩子/回调分发路径**
（它作为 detour 替游戏函数转发调用）。所以：**崩在 UE4SS 的钩子机制里，不在我们的 Lua 里。**

配合两个时间戳证据：

| 证据 | 值 |
|---|---|
| `SecondsSinceStart` | 56 |
| 崩溃前最后两条日志 | `[FOV] released \| world reload reset` / `[FOV] apply ... \| world reload` |

→ 崩在**世界加载完成那一刻**。

### 11-3 第三步：和历史崩溃比对

`docs/踩坑记录.md` 里记过 crash #2/#3：

| | 那时（17:05，PWRecon） | 这次（18:02，PWProjection） |
|---|---|---|
| 异常 | `EXCEPTION_ACCESS_VIOLATION` | 同 |
| `SecondsSinceStart` | 40 | 56 |
| 栈形 | `UE4SS` + 一串 `Palworld_Win64_Shipping` | 同 |
| 触发时机 | 世界重载 | 世界加载完成 |

**而 PWRecon 当时一个钩子都没注册**（只注册了热键）。
→ 这说明**这个崩溃在我们写 PWProjection 之前就存在**，是世界加载期的既有问题。

**共同点在场的第三方**：`FirstPerson`（每次都出现 `[FOV] ... world reload`）、
SBB 的 `BlueprintResearch.pak`（只装了 pak、没装 Lua，ModActor 仍在每个关卡生成）。

### 11-4 但仍然做了减法（"不是我们的锅"不等于"什么都不用改"）

即使归因到别处，只要发现自己在**高风险时刻**做了**没有收益**的动作，就该删掉：

| 改了什么 | 为什么 |
|---|---|
| `LoadMapPre` 钩子改成**默认关闭**（config `hook_load_map_pre`） | 世界加载期是最不该有额外动作的时刻，而投影还没解锁，这钩子收益为零 |
| 启动期不再 `os.execute`/`io.popen` | 那是**在游戏启动过程中 spawn 一个 cmd.exe**。索引文件由 `Library.save` 自己维护，没必要扫 |
| 建目录改成**按需**（保存时才建） | 同上，启动期不该有文件系统副作用 |
| 每个热键加 `>> label` / `<< label` ASCII 标记 | `>>` 在**按键那一刻**同步打印 → 以后不用再猜"键按下去没有" |
| 采集时每 500 件落一次盘 | 下次真崩在采集中间，也能看到"扫到第几件" |

### 11-5 通用规矩

1. **任何"启动期额外动作"默认关闭**，需要时再开。启动期是全局最脆弱的时间窗。
2. **回调入口先同步打一条标记**，再做任何事。这样"键有没有进来"永远是可判定的，
   不需要靠用户回忆。
3. **诊断通道要独立于数据通道**：控制台打印是"立刻可见"的，文件缓冲是"完整但可能丢"的。
   两者都要有，别只留一个。
4. **崩溃归因先读日志，再动代码。** 这次如果直接去改代码，会白改（因为我们本来就没跑）。
5. **关掉自己的 mod 是最便宜的一次实验。** 所以 `deploy.ps1 -Disable` 只改 `mods.txt`
   的 `1→0`，不复制不删除 —— 保证"关/测/开"三步之间不引入新变量。

## 12. PWProjection 第一次实机运行（2026-09-26 18:15）—— 收获与教训

这次运行**信息量极大**：`Y` 采集成功、`J` 加载成功、
能力探测 28 步里前 **27 步全部通过**，只崩在第 28 步。

### 12-1 ★ "记开始不记结束"的探测设计，第一次实战就救了一场

`pwpr_probe.txt` 里 1–27 步都有 `结果: OK`，第 28 步只有 `START` 没有结果：

```
[27/28] START destroy_host  (销毁宿主 Actor)
        结果: OK  已销毁

[28/28] START hud_print  (屏幕文字 ...)
        类型: write
        ← 文件到此为止
```

**崩溃点一次锁定，零推断。** 如果按"做完再记"的老写法，
只能知道"崩在第 28 步附近"，还要猜。

### 12-2 ★ 同时暴露了一个设计缺陷：结果只在最后落盘

能力表原来是**全部跑完才写** `pwpr_capabilities.json`。
第 28 步一崩 → **前 27 步的结论全丢了**，用户白跑一轮。

**改法**：每一步之后都写一次能力表。
**通用规矩**：长流程的**中间结论必须增量落盘**，
不能"全成功了再一次性保存" —— 那等于把风险和收益绑在一起。

### 12-3 ★ `PrintString` 在 Shipping 构建里是【必崩】，不是"可能不支持"

```
[28/28] START hud_print  →  EXCEPTION_ACCESS_VIOLATION
```

原因：Palworld 是 Shipping 构建，UE 把
`UKismetSystemLibrary::PrintString` 里"画到屏幕上"那段用
`#if !(UE_BUILD_SHIPPING || UE_BUILD_TEST)` 编译掉了。
**函数体没了，但 UFunction 的反射信息还在**，
UE4SS 按反射去调 → 参数栈对不上 → 访问违例。

**教训**：`FindAllOf`/反射能"看到"一个函数，**不代表它在这个构建里能调**。
Shipping 构建里所有 `DrawDebug*` / `PrintString` 这一类都要先当成"可能被编译掉"。

**反面价值**：这条现在被永久记录在 `pwpr_hud.lua` 的头部注释里，
并明确写了"不要顺手再试一次" —— 否则下一个人会再崩一次游戏。

### 12-4 ★ `IsValid()` 会把好对象误判为无效

PWRecon 读建筑网格用的是"**能调通 `GetFullName` 就算有**"，实测 26/79 种类型能读到。
我重写时"更严谨"地加了 `Util.valid(comp)` / `Util.valid(asset)` 判定，
结果同一个存档一个 35 件的基地只有 4 件读到网格。

**修正**：判据改回 `GetFullName`，同时把 `IsValid` 的返回值**记进诊断**
（`pwpr_meshes.txt` 第 3 节），这样下次能看清"IsValid 到底骗了我们多少"。

**规矩**：`IsValid()` 不是万能判据。对 **UClass / 组件 / 资产** 这类对象，
UE4SS 上要用"反射能不能调通"来判断。
**而且：不要在没有证据的情况下去"加固"一段已经被验证过的代码。**

### 12-5 ★ 让游戏自己把数据导出来，比任何猜测都值钱

`pwpr_meshes.txt`（2310 个网格的完整路径清单）这一次直接解决了结构件映射：

- 全库只有 **150 个**在 `/Architecture/` 下，其中结构件只有 **8 个**
  （`SM_Floor_Wood` / `SM_Wall_Wood` / `SM_WallWindow_Wood` / `SM_WallGate_Stone`
  / `SM_Roof_Wood` / `SM_Stair_Wood` / `SM_Door_Wood` / `SM_Doorbase_Wood`）
- 于是"类型 → 网格"这个本来要靠猜的问题，变成了**在 8 个候选里对号入座**
- 并且立刻发现：**Palworld 的"地基"叫 `SM_Floor_Wood`，不叫 Foundation**

**规矩**：与其猜命名规则，不如让游戏把真实清单导出来。
导出的成本是几百 KB 的文件，收益是把"不确定"变成"确定"。

### 12-6 ★ 启发式匹配规则必须能在【离线】验证

`tools/meshmatch_sim.py` 把 Lua 的匹配算法在 Python 里**原样实现**，
然后：

1. 输入 = 游戏导出的 **2310 个真实网格** + **79 个真实类型名**
2. 标准答案 = recon 时 actor 上**直接读到的 26 个真实网格**
3. 输出 = 命中数 / 误匹配数 / 未匹配清单

第一次跑就抓出两个严重问题（见 12-7）。
**改 Lua 之前先在模拟器上验证** —— 否则每次验证都要进一次游戏，
而且崩了还不知道为什么。

### 12-7 ★ "放宽一点"的启发式 = 制造垃圾

我一开始给匹配加了"放宽一轮"（严格匹配失败时只要求第一个关键词），
模拟器立刻显示：

```
HatchingPalEgg   -> SM_PalSpa      ← 蛋孵化器和温泉有什么关系？
FarmBlockRecipe  -> SM_IceBlock    ← 农田和冰块？
BaseCampWorkHard -> SM_Campfire    ← 据点工作台和篝火？
```

**放宽 = 用"看起来像"换"大概率错"。** 删除 relaxed 轮之后，
宁可返回 nil（这一件画不出来），也不要张冠李戴。

同时加了三条硬约束，都是模拟器跑出来的：
1. 候选必须在 `/Architecture/` 目录下（否则会匹到 `SM_IceBlock` 这种）
2. 严格命中所有关键词
3. 同分并列取最短名；长度也一样 → **放弃**

**规矩**：启发式规则宁可"少给答案"，也不要"给错答案"。
错答案会让人去 debug 一个不存在的问题。

### 12-8 ★ "按了没反应" ≠ "功能没生效"

用户按了 `J`，觉得"好像没什么反应"。查日志发现**`J` 完全正常工作**，
蓝图加载并打印了完整摘要。

真正的原因是：**UE4SS 的控制台默认是关的**
（`ConsoleEnabled = 0`），而我们把所有反馈都写进了控制台和日志文件。
用户看不到那个窗口，自然觉得"没反应"。

**规矩**：做工具时要问一句"用户靠什么看见结果"。
如果一个功能的反馈渠道默认是关闭的，那它等于没有反馈。
要么把渠道打开（写进文档的**第一步**），要么换一个默认可见的渠道。

### 12-9 ★ 日志必须能回答"键到底按下去没有"

这是上一个崩溃留下的问题（用户："不确定 Y 键有没有按下去"）。
这次给每个热键加了两个 ASCII 标记：

- `>> 名字` —— 在**按键那一刻**同步打印（在调度之前）
- `<< 名字` —— 处理函数跑完后打印

于是三种情况可区分：

| 日志 | 含义 |
|---|---|
| 只有 `>>` 没有 `<<` | 崩在这个处理函数**里面** |
| `>>` 和 `<<` 都有 | 这次按键**正常跑完了**，崩溃与它无关 |
| 两个都没有 | **键根本没按到**（或绑定失败） |

**规矩**：不要设计需要用户"回忆自己按了什么"的排查流程。
把不确定性变成日志里可判定的事实。

## 14. "功能按了没反应"的两个典型成因（2026-09-26 深夜）

玩家反馈："`Ctrl+←`（换投影材质）按了**投影直接没了**，按多次也不出现，
只有 `Ctrl+→`（放/收）才能弄回来。是不是绑错了？"

不是绑错，是**两个 bug 叠在一起**。两个都很典型。

### 14-1 状态守卫 vs. 状态转换的顺序错了

```lua
local function rebuild_ghost(reason)
    if not Ghost.visible then return true end   -- ← 守卫
    ... Ghost.fill(...)                          -- fill 才会把 visible 设回 true
end

-- 调用方:
Ghost.clear()          -- 把 visible 设成 false，并销毁宿主
Ghost.prepare(Config)  -- 重建宿主
rebuild_ghost("换材质") -- ← 在这里被守卫挡住，直接 return
```

**`clear()` 先把状态清成"不可见"，然后守卫就以"不可见"为理由拒绝恢复。**
于是投影永久消失 —— 因为整个程序里只有 `fill()` 会把 `visible` 设回 `true`，
而 `fill()` 被守卫挡住了。

**规矩**：当一个动作是"销毁 → 重建"时，**不能用"当前是否可见"当守卫**。
要么传一个显式的 `force`，要么把守卫判断放在销毁**之前**（先记下 `was_visible`）。
"我先把状态清了，然后检查状态"是自相矛盾的。

### 14-2 参数在两步之间被另一处覆盖

```lua
Ghost.cycle_material()      -- 改了 Ghost.material_mode
...
Ghost.prepare(Config)       -- 里面: Ghost.material_mode = config.get("ghost_material")
```

`prepare()` 每次都会**从配置里读值覆盖内存里的模式**，
所以刚 `cycle` 出来的新模式立刻被打回原值 —— **就算投影没消失，材质也不会变。**

**规矩**：一个"设置"如果同时存在**内存态**和**持久化态**，
就要明确谁是权威。这里的修法是：改动后**立刻写回配置**，
让两者同步（顺带好处：选择跨重启保留）。

### 14-3 顺带：修饰键要避开游戏自己的功能键

`Ctrl` 在 Palworld 里是**闪避**。修饰键是"按住"的，
所以每次换材质角色都会翻滚一下。

**规矩**：选修饰键前先查游戏自己绑了什么。
本项目最终选了 `Alt`（游戏未占用），并把 `Ctrl` 只留作注册失败的备份。
`Shift` 也可用，但它在 Palworld 里是冲刺 —— 所以只用于"抬高/降速/旋转"
这类**不需要按住走位**的动作。

## 13. Lua 的 local 声明顺序陷阱（2026-09-26 22:14）

### 13-1 现象

用户按 `K`（投影），控制台报：

```
[Lua] [PWPR] >> ghost-toggle
[Lua] [PWPR] !! ghost-toggle ERROR: .../pwpr_meshmap.lua:84:
             attempt to index a nil value (global 'SYNONYMS')
[Lua] [PWPR] << ghost-toggle
```

### 13-2 原因：local 只对【声明之后】的代码可见

我在重构匹配算法时，把新函数 `type_keywords`（第 75 行）写在了
`local SYNONYMS`（第 115 行）**前面**。

Lua 的 `local` **不是**函数级提升，只对词法上出现在它之后的代码可见。
所以在 `type_keywords` 里面，`SYNONYMS` 被解析成**全局变量** —— 它是 `nil`，
于是 `SYNONYMS[words[1]]` 就炸了。

**这个坑很毒的地方在于它不报错在声明处，也不报错在加载时** ——
只有真正执行到那一行才炸。所以 mod 加载完全正常、按 `N` 探测也正常
（探测不走匹配），直到按 `K` 才暴露。

### 13-3 所有已有检查都放过了它

| 检查 | 为什么放过 |
|---|---|
| 词法分析 | 语法完全合法 |
| 块结构平衡 | `end` 配平正确 |
| 未定义**被调用**标识符 | `SYNONYMS[words[1]]` 是**索引**，不是调用 |
| 跨模块接口 | 它只看 `Mod.func(` 形式 |
| 动态检查（进游戏） | 只有走到 `K` 才触发 |

**四个静态检查全绿，功能却是坏的。**

### 13-4 ★ 于是加了第五个检查：local 声明顺序

`tools/luacheck.py` 新增 `check_use_before_local`：
收集所有引入局部名字的地方（`local` 赋值、`local function`、
**函数参数**、**for 循环变量**），然后对每一次"使用"检查
是否存在"在它这一行或之前"的声明。没有 → 报出来。

### 13-5 ★ 但这个检查的调试过程本身很有教育意义

第一版（只看列 0 的 local）：误报 **2** 处
→ 因为 `do_help` 里有个缩进的 `local gate_ok`，它遮蔽了文件级同名变量。

第二版（加缩进比较近似作用域）：误报 **61** 处
→ 因为**函数参数和 for 变量**没被当成声明，
于是 `lo` / `hi` / `x` / `y` / `z` / `i` / `k` / `v` 全部被当成"提前使用"。

第三版（补参数和 for 变量、去掉缩进比较）：误报 **11** 处
→ 因为把**表构造的键**当成了使用（`local bp = { meta = ..., size = ... }`
里的 `meta` / `size` 是键名，不是变量）。

第四版（跳过 `name = ...` 形式）：误报 **1** 处
→ 因为 for 变量的正则写成 `(?:=|in)\b`，
而 `\b` 在 `= ` 之间不成立（两边都不是单词字符），整个匹配失败。

第五版：误报 **0**，且 `tools/luacheck_selftest.py` 里的
`use_before_local.lua` 这个真实样例仍被抓住（自检 14/14）。

**规矩**：检查工具必须**双向**验证 ——
既要用"已知错误"证明它能抓（漏报测试），
也要用**真实代码**证明它不乱报（误报测试）。
一个总在误报的检查，人会开始忽略它，那它比没有更糟。
所以每加一个检查，都要先把它跑到"真实项目 0 误报"为止。

### 13-6 顺带印证了 12-9 那条规矩

定位这个 bug **完全没花时间** —— 日志里 `>> ghost-toggle` /
`ERROR` / `<< ghost-toggle` 三行直接给出了文件、行号和变量名。

对比第一次崩溃时用户要回忆"我到底按了 Y 没有"：
**把不确定性变成日志里可判定的事实，收益是复利的。**

## 15. 屏幕提示（待办 1）：可用通道与已经证实的坑（2026-09-27）

**背景**：`PrintString` 必崩（12-3），所以"屏幕上显示文字"必须换通道。
官方文档（`pwmodding.wiki` 的 Palworld Modding Kit / UE4SS 分类）**只有安装配置指南，
没有任何 UI / 通知的 API 参考** —— 只能实测。

### 15-1 ★★ 先在本机找实机证据，比猜类名强一个数量级

本机 UE4SS 目录里就躺着两个**金矿**（都是别人写的、正在用的东西）：

| 文件 | 价值 |
|---|---|
| `Mods\FirstPerson\Scripts\main.lua`（179 KB） | 一个**实机在用**的 Palworld Lua mod。它怎么构造文本、怎么拿 UMG 库、哪些写法崩过，全在注释里 |
| `Mods\ConsoleCommandsMod\Scripts\dump_object.lua` | UE4SS **官方**控制台命令，示范了完整反射枚举怎么写 |
| `UE4SS.dll` 字符串扫描 | 判断某个 API 到底存不存在（`ForEachFunction` 有、`CreateWidget` 没有——后者是 UE 函数名不是 UE4SS API 名） |

> **教训**：卡在"某个 API 到底行不行"时，先去本机**已装的其他 mod**里搜证据。
> 这比翻文档、比猜类名都快，而且是**实机验证过的事实**。

### 15-2 ✅ `FText("中文")` 可用（有实机证据）

`FirstPerson` 里就是 `TextBlock:SetText(FText("第一人称"))` —— 中文能进去、能显示。
另有一条兜底：`UEHelpers.GetKismetTextLibrary():Conv_StringToText(s)`
（纯转换函数，**不是** `PrintString` 那条崩掉的路）。

### 15-3 ✅ 反射枚举可用 —— 所以**不要猜函数名，去枚举**

`UE4SS.dll` 里能扫到 `ForEachFunction`；`dump_object.lua` 用的是
`ForEachProperty` + `GetSuperStruct` 遍历类链。

```lua
cls:ForEachFunction(function(f)
    -- f:GetFName():ToString()  -> 函数名
    -- f:ForEachProperty(...)   -> 该函数的【参数列表】（返回值也在里面）
end)
```

**这条把"猜接口"这个风险从根上消掉了**：
把 `PlayerController` 的函数名连同参数签名（`(StrProperty S, NameProperty Type,
FloatProperty MsgLifeTime)` 这种）打出来，照着签名写调用。

### 15-4 🔴 hook UI 会崩，直接调用 UI 不会

`FirstPerson` 的注释记了**两次**崩溃 dump，都指向 `TextBlock:SetText` 的 **hook**；
它最后把那个 hook 删了。而它现在仍然在**直接调用** `SetText`，一切正常。

| 做法 | 风险 | 为什么 |
|---|---|---|
| `RegisterHook("/Script/UMG.TextBlock:SetText", ...)` | **高** | 游戏每次调用都进我们代码，**包括控件正在销毁的那一刻** |
| `widget.SomeText:SetText(FText("..."))` | 低 | 我们自己发起、对象是我们挑的、时机是我们选的 |

⇒ **本 mod 永远不 hook UI。**

### 15-5 ★ 看得见看不见，可能是 `GraphicsAPI` 的问题，不是代码问题

`UE4SS-settings.ini` 默认 `GraphicsAPI = opengl`。
opengl 后端把调试 GUI 渲染到**独立窗口**（`imgui.ini` 里的 `Backend_Window`），
**不盖在游戏画面上** —— 于是玩家的感受是"我得去翻日志"。

想让它盖在游戏上：`GraphicsAPI = dx11`（游戏也跑 DX11）后重启游戏。

> **教训**："功能没生效"和"你看不见它生效"是两件事（12-8 那条的同类）。
> 排查"没反馈"时，先确认**反馈通道本身可见**。

### 15-6 🔴 新功能不许动"已验证那条路"的凭据

S9 探测（按 `O`）第一版里也调了 `Probe.save_capabilities()` ——
而那个文件是**投影渲染门禁**的凭据（`Ghost.check_gate` 读它）。
结果：**按一次 `O` 就把渲染门禁覆盖成只剩 `s9_*` 几条**，
`K` 会突然拒绝渲染，得再按一次 `N` 才恢复。

修法：`run_ui` **完全不写**那个文件（S9 结论只进 `pwpr_ui.txt`）。
并且 S9 **故意不接进** `STEPS`（按 `N` 的渲染门禁），
免得"新探测失败"看起来像"渲染门禁失败"。

> **规矩**：加新功能时，**先问它会不会碰到老功能的判定依据**。
> 会碰 → 隔离成独立的文件/列表/开关。

## 16. Lua 保留字当字段名 = 语法错误（2026-09-27）

### 16-1 现象：整个 mod 一行日志都不打，直接 `init failed`

`pwpr_notify.lua` 里写了：

```lua
function Notify.repeat()   -- ❌ repeat 是保留字
```

`t.repeat` / `t.end` / `obj:for(...)` 都是**语法错误**：
Lua 的 `t.xxx` 里 `xxx` 必须是标识符，**保留字不行**。
因为语法错误发生在**解析阶段**，所以：

* **不是**"运行到那行才报错"
* 而是**整个文件加载不了** → `require` 失败 → `main.lua` 的 pcall 接住 →
  打印 `init failed` → **整个 mod 静默失效**

### 16-2 检查器先报的是别的东西（这点最有教育意义）

`tools/luacheck.py` 当时报的是：

```
[2] 块结构平衡: 结束时深度 = 1
    [严重] 有 1 个块没有闭合 —— 大概率是少写了 end
```

看着像"少写 `end`"，其实一个都不少 ——
**`repeat` 被词法器当成块起始关键字**（`repeat...until`）多算了一层。
追下去才发现真正的错是"保留字当函数名"。

### 16-3 ✅ 于是加了第 10 项检查 + 3 个自检样例

* `luacheck.py` 新增 `check_keyword_as_field()`：
  检查 `[.:]` 后面紧跟保留字（且在**清洗掉字符串/注释之后**的文本上查，
  避免把 `"x.end"` 这种字符串误报）。
* `luacheck_selftest.py` 加了 3 个样例：
  `keyword_as_field.lua`（必须报错）/ `keyword_as_method.lua`（必须报错）/
  `good_keyword_not_field.lua`（**必须不报错** —— 名字里含 `for`/`end`
  和字符串里的 `.end` 都不该误报）。自检 **16 → 19 项全过**。

### 16-4 还剩的缺口（诚实记录）

我们的检查器是**自己写的近似 Lua 语法**，不是真 Lua 解释器。
本机**没有独立的 Lua 可执行文件**（`lua` / `luajit` 都没有），
所以"文件能不能被真 Lua 解析"最终只能在游戏里验证。
第 10 项检查就是为了缩小这个缺口 —— 但缺口没有消失。

## 17. 🔴🔴 反射枚举把游戏打崩，而文档里早就写过它不能用（2026-09-27）

**这是本项目里最该被批评的一次错误 —— 不是"没想到"，是"没查自己写的文档"。**

### 17-1 事故

按 `O` 跑 S9 屏幕提示探测，第 1 步 OK（拿到 `BP_PalPlayerController_C`），
**第 2 步一进去就崩**：

```
---------- [2/8] START s9_pc_funcs (枚举 PlayerController 的函数名 + 参数签名) ----------
<文件到此为止>
```

崩溃上下文：`EXCEPTION_ACCESS_VIOLATION reading address 0x00000000ff010011`，
调用栈 **80 帧全在 `UE4SS` 里**（后面才是 Palworld 自己的帧）。

### 17-2 我用的是什么

```lua
cls:ForEachFunction(function(f)          -- ❌ 崩
    local nm = f:GetFName():ToString()
    f:ForEachProperty(function(p) ... end)  -- ❌ 更可疑
end)
```

### 17-3 为什么说"该被批评"

**`docs/踩坑记录.md` 里已经记过两次这个接口不可用**：

| 位置 | 当时的结论 |
|---|---|
| 3c-3「属性枚举仍然失败」 | `obj:ForEachProperty` / `class:ForEachProperty` 返回的是 `FNameUserdata:<地址>` 假对象，拿不到真属性名 |
| 3f-2「✅ `ForEachProperty` 确认不可用」 | `attempt to call a TrivialObject value (method 'ForEachProperty')` —— **实证确认未被绑定** |

当时的处理是"记下来"，**但没有做成检查项** —— 于是几个月后又被踩了一次，
而且这次代价是**崩游戏**（比"返回空"严重得多）。

### 17-4 更根本的误判：**"能扫到字符串" ≠ "能安全调用"**

我当时的推理是：

```
UE4SS.dll 里扫得到 "ForEachFunction"（3 次）  →  这个 API 存在  →  可以用
```

**中间那一步是错的。** 本项目的 `PrintString` 就是同一个模式：
函数体被 Shipping 编译掉了，**反射信息还在**，所以"扫得到名字"完全
不代表"按反射去调它安全"。`IsValid()` 也是同类（能调，但结果不可信）。

**规矩**：判断一个引擎接口能不能用，**只看实机证据**，
不看"字符串扫到了/反射里有/别人代码里写了"。

### 17-5 修法（两层，缺一不可）

1. **代码层**：删掉 `s9_pc_funcs` / `s9_all_classes` / `s9_live_widgets`
   三个推测性步骤，换成 `s9_candidates`：
   用**候选名单 + 存在性检查**（`obj.方法名` 查询、`FindAllOf("精确类名")`）——
   这两种操作本项目已经安全用了几个月。
   候选名单里**故意放三个"已知存在"的对照类**（`WBP_Graphic_Settings_C` 等），
   这样"全是 0"时能立刻区分"查询方式不管用"和"游戏里真没有"。
2. **工具层**：给 `tools/luacheck.py` 加第 **11** 项检查 ——
   出现 `ForEachProperty` / `ForEachFunction` / `ForEachUObject` 直接判错，
   并在 `luacheck_selftest.py` 里配了正反样例（**22/22**）。
   > 原则：**踩过的坑要么变成检查项，要么会再踩一次。**

### 17-6 顺带确认的好消息

同一次运行里，**屏幕提示（策略层 + 控制台通道）是好的**：
`pwpr.log` 里生成了 **12 条** `> ` 开头的提示
（采集完成 / 已加载蓝图 / 投影已放置 / 分层 / 方向键模式…），
`F7` 的按键表也正确输出了。也就是说**崩溃与我这次要做的主功能无关**，
是"顺手多做的一步探测"闯的祸。

> **附带教训**：探测步骤应当**按风险从低到高排序**，
> 把"可能崩"的放最后。当时第 2 步就放了最危险的那个，
> 结果后面 6 步（FText 中文测试、通道探测…）一条都没跑到。
> **现已重排：零风险的四步在前，高风险的最后。**

## 18. S9 第二次实测（2026-09-27）：四条新的硬事实

第二次按 `O`（把反射枚举删掉之后）**没崩**，六步全过。产出了四条以后必须记住的事实。

### 18-1 ★ `t.方法名` 不存在时返回的是 **userdata 占位对象，不是 nil**

19 个"通知函数"候选（含 `ClientMessage`、`GetHUD`、`ShowSystemMessage`…）
**全部**返回 `type=userdata`：

```
占位/未绑定: ClientMessage   type=userdata
```

⇒ 所以 **`fn ~= nil` 完全不能证明"这个方法存在"**。
这是"属性读取坑"（3b-2 / 3c-4"未绑定的方法返回 TrivialObject"）在**方法**上的同款表现。

### 18-1b 🔴 但紧接着第二版判据也错了：`userdata` **不等于**"不可调用"

我据此写下"`type == "function"` 才算存在"，并拿它判出
"19 个候选全部未绑定 ⇒ ClientMessage 这条路走不通"。
**这个结论是错的**，因为对照组当场打脸：

```
GetControlRotation  type=userdata   ← 我们每帧都在用它读视角，百分百可用！
GetWorld            type=function   ← 这个才是 function
```

**真相**：UE4SS 把 UFunction 包成 **带 `__call` 的 userdata**，
所以 `obj:Method()`（= `obj.Method(obj)`）能调通，但 `type()` 报的是 `userdata`。
几个绑定走的路径不同（`GetWorld` 是 function），于是 `type()` **根本分辨不出**
"真方法"和"占位对象"。

**⇒ 由此得出两条硬规矩**：

1. **判据不能写死，要用"已知能用的东西"当基准反推。**
   现在 `s9_candidates` 先量对照组（`GetControlRotation` / `GetPawn` / `GetWorld`），
   收集三个信号（`type` / `mt.__call` / `Util.usable`），再拿这个标准去判候选。
   对照组不通过时，报告**直接写"结论本身不可信"**，而不是硬给答案。
2. **凡是我写下的"XX 不可用"结论，都必须先问：对照组是什么？**
   这已经是同一个坑的第三次（`IsValid` / 占位属性 / 占位方法），
   每次都是"没有对照组就下结论"。

### 18-1c ⚠️ 那"名字不存在"到底怎么判？——**别判，去调用并接住错误**

实测证据（3f-2）：调一个未绑定的名字 → **可被 pcall 捕获的 Lua 错误**
（`attempt to call a TrivialObject value`），**不是崩溃**。
所以在**参数个数已知**的前提下，最可靠的判据就是
"**直接调用，用 pcall 接住结果**"：

* 没绑定 → 拿到 Lua 错误，无害；
* 绑定了 → 正常执行。

这正是 `notice_text` / `client_message` 两条通道现在的做法
（`SetText` / `SetVisibility` / `ClientMessage` 的参数个数都是公开已知的）。
**"先去猜它存不存在"本身就不必要。**

### 18-2 ⚠️ `FindAllOf` 无匹配时返回 **nil**，不是空表

第一版把 `type(lst) ~= "table"` 一律报成"查询失败"，
结果 18 个类名全是"查询失败"，看起来像"查询功能坏了"。
实际上它们是**真的没有存活实例**。已改成区分三种情况：
`数量 > 0` / `0 个（FindAllOf 无匹配）` / `抛错: <原因>`。

### 18-3 ⚠️ UMG 控件是**按需创建**的 —— 所以"对照组"不能用它们

第一版把三个 `WBP_*_Settings_C` 当对照组，说"如果它们也是 0 就说明查询方式不管用"。
**这个推理是错的**：设置页控件只在**打开设置菜单**时才存在，平时本来就查不到。
⇒ **对照组必须是"此刻一定在"的东西。**

### 18-4 ✅ 但"类名查询"这条路本身是通的 —— 而且挖到了金矿

```
★ WBP_Notice_C    1 个   例: WBP_Notice_C /Game/Pal/Blueprint/UI/Log/
                             WBP_NoticeLog.WBP_NoticeLog_C:WidgetTree.WBP_Notice
```

**`WBP_Notice_C` 活着**（1 个实例），而且全名暴露了两件事：

1. Palworld 自己的**通知系统叫 `Notice`**，资产在 `/Game/Pal/Blueprint/UI/Log/WBP_NoticeLog`；
2. **`FindAllOf` 确实能查到 UMG 控件**（它是 UObject，不在地图 Actor 列表里也一样能查到）。

同时确认：
* `FText` 中文**完全可用**（`构造 OK / 回读: 蓝图投影`）；
* UMG 静态库可用（`lib:Create 存在`）。

⇒ **游戏内中文提示的路线就此明确**：展开 `WBP_Notice_C` 的控件树
（读 `UWidgetBlueprintGeneratedClass.WidgetTree.AllWidgets` —— 属性读取 + 数组下标，
**不是**反射枚举），找到那个 TextBlock，再 `SetText(FText("中文"))`。

### 18-5 ⚠️ 改配置文件后**必须重读**，否则改了等于没改

玩家把 `notify_try_client_message` 改成 `true` 后直接按 `O`，
探测里那条通道仍显示"默认关" —— 因为配置是**启动/按 `F8` 时**读进内存的。

**修法（比写文档更靠谱）**：让 `O` 自己重读一次 —— 探测开始时调
`Config.load()`（和 `F8` 干的是同一件事），并在报告里写明"本步已自动重读配置"。

> 通用教训：**"让用户记住多做一步"通常不如"让程序自己多做一步"。**
> 如果某一步忘掉会让功能看起来坏了，就把它自动化掉。

### 18-6 ★ 高风险的探测要"边查边写盘"，不能只在最后写

`s9_notice_widget`（展开控件树）是全流程风险最高的一步。
如果按原来的写法（最后统一 `ui_write`），崩在第一个候选上就**一条都留不下**。
现已改成**每查一个类、每读一层就立刻 append** ——
崩了也能看到"查到哪儿了"。

## 19. 🔴 "已发=8 失败=0 但屏幕上一个字都没有" —— CDO 不是画面上的控件（2026-09-27）

### 19-1 现象：一切"成功"，就是看不见

`notice_text` 通道接上后，玩家进游戏按 `Y`/`J`/`K`/`F9`/`L`，
**屏幕上没有任何文字**。而探测报告写着：

```
选中通道: notice_text ... [找到 1 个候选文本控件，例: BP_PalTextBlock_C
   /Game/Pal/Blueprint/UI/UserInterface/InGame/Notice/WBP_Notice.WBP_Notice_C:WidgetTree.BP_PalTextBlock_C_84]
屏幕提示: 开   通道=notice_text   已发=8  失败=0
```

**`SetText` 没报错、`pcall` 全通过、8 条全"成功"** —— 于是症状看起来像
"文字写进去了但没显示"，很容易往"控件被隐藏了/被覆盖了"那边猜。
**真正的错因在目标本身挑错了。**

### 19-2 根因：CDO（类默认对象）里的控件**不在画面上**

看报告里那份"文本控件清单"，两种全名长得完全不一样：

| 类型 | 全名形态 | 在画面上吗 |
|---|---|---|
| **CDO / 设计期控件** | `/Game/Pal/Blueprint/UI/.../WBP_Notice.WBP_Notice_C:WidgetTree.BP_PalTextBlock_C_84` | ❌ **不在**（这是"设计稿"里的预览控件） |
| **活实例** | `/Engine/Transient.PalGameEngine_2147482588:...WBP_PlayerUI_C_2147443706.WidgetTree_2147443705...Text_MaxHP` | ✅ 在 |

判据很简单：**活实例一定在 `/Engine/Transient` 下面**（带实例编号
`WidgetTree_<数字>`）；CDO 的全名是**资产路径 + `:WidgetTree.`**。

第一版按名字过滤 `WBP_Notice` 挑控件 —— 而**平时根本没有活的 `WBP_Notice`
实例**（Palworld 只在要弹通知的那一刻才创建），于是唯一匹配上的就是那个
**CDO 里的设计期控件**。往它 `SetText`：

* 它是**合法 UObject** → 不报错；
* 它**不在任何视口里** → 永远不可能显示。

⇒ **"调用成功"和"真的生效"是两件事**（12-8 那条的第七次变体）。

### 19-3 修法（两层）

1. **加判据 `Hud.is_live()`**：只认全名含 `/Engine/Transient` 的控件。
   借用路线现在强制 `only_live = true`，**CDO 一律忽略**。
2. **不借游戏的了，自己造一个**：`WBP_Notice_C` 的类 → `WidgetBlueprintLibrary:Create`
   → `AddToViewport`（等价于蓝图里的 "Create Widget" + "Add to Viewport" 两个节点，
   参数个数公开已知，`Create` 在本机 `FirstPerson` 里就是实机在用的）。
   这样**不依赖游戏什么时候弹通知**，而且不会改坏别人的 UI。
   显示 `hud_seconds` 秒后用 `SetVisibility(1)`（Collapsed）收起来。

### 19-4 顺带修掉的一个性能坑

"扫描全部文本控件"会遍历 **5322 个对象**并逐个 `GetFullName()`。
而发送提示是**按一次键一次**的 —— 不缓存就会**每按一次卡一下**
（正是玩家报的"卡了一下"）。
现已加扫描缓存（`notify_textblock_cache_s`，默认 5 秒），
并且**新建自己的控件后主动让缓存失效**（否则新控件不在旧缓存里，会误判"里面没有文本控件"）。

> 这条也印证 `踩坑记录` 10-7：**在游戏主线程上做几千次 `GetFullName()` 是能感觉到的。**
> 凡是"每次按键都要扫一遍全场"的设计，先问一句"能不能缓存"。

### 19-5 教训（写给以后的自己）

1. **写进一个对象之前，先问"这个对象在不在画面上"** ——
   `IsValid` / `GetFullName` / "调用没报错"都回答不了这个问题。
   能回答的是：**它的全名在不在 `/Engine/Transient` 下**（运行时对象）
   或者是资产路径（设计期对象）。
2. **凡是"成功但没效果"，第一件事是回读**：我们写进去的字，用
   `TextBlock:GetText()` 能不能读回来？读得回来 ⇒ 写对了，问题在"显示"；
   读不回来 ⇒ 根本没写到目标上。这次连"回读"都还是对的
   （字确实在 CDO 里），所以**回读还不够 —— 还要问"这个对象可见吗"**。
3. **挑目标时不要只按名字过滤**，要把"是不是活实例"一起当条件。

### 19-6 第二层：**"字写对了、在视口里、也有尺寸，却还是看不见"**

自建控件之后，加了"发送实况"telemetry，第一次就把问题**从"写"缩小到"渲染"**：

```
自建控件=WBP_Notice_C /Engine/Transient...WBP_Notice_C_2147366451
挂载方式=AddToViewport 在视口里=true 可视性=1 期望尺寸=456x40 新建文本控件=1
文本控件=...WBP_Notice_C_2147366451.WidgetTree_2147366450.BP_PalTextBlock_C_84
SetText=true 回读=「PWPR 测试文字 —— 能看见这行就说明通道可用」 控件可视性=4
采用路线=own
```

逐条读出来：**控件建了、挂上了、在视口里、尺寸 456x40、文字回读完全一致** ——
也就是说**"写"这件事一点问题都没有**，问题在"渲染"。于是只剩三个嫌疑：

| 嫌疑 | 依据 | 处理 |
|---|---|---|
| **自动隐藏把窗口错过了** | 读到的 `可视性=1`（Collapsed）是上一次发送安排隐藏的结果 | `notify_autohide` **默认改成 false** —— 排查阶段不能有"是不是刚好错过那 4 秒"这种不确定性 |
| **`RenderOpacity` = 0** | WBP 的动画初始姿态常把透明度设成 0，靠 `PlayAnimation("Show")` 才显示；我们**凭空 Create 的实例没人给它播动画**，就停在初始姿态 | 写完后强制 `SetRenderOpacity(1)`（控件 + 文本框都做） |
| **z-order 被游戏 UI 盖住** | 我们用 `AddToViewport(0)`；游戏 HUD 是一个全屏布局控件（`WBP_PalOverallUILayout_C`） | 改成 `AddToViewport(1000)` |

> **方法论收获**：telemetry 的价值不在于"多打日志"，而在于
> **把"很多种可能"一次性砍成"少数几种"**。
> 这次一条实况就把"是不是写错了/挑错控件了/没挂上"全部排除，
> 剩下的只有渲染层 —— 而渲染层是可枚举的（可见性 / 透明度 / 层级 / 位置）。

### 19-7 同一轮里的第二个实验：**两条路线一起测**

自建控件那条路"什么都对但看不见"，而**借用**的是一个**正在被游戏渲染**的
控件（位置、透明度、层级全都是游戏自己调好的）。
所以在按 `O` 的诊断里**同时测两条**：

* 路线 A: 自建控件（`Create` + `AddToViewport`）
* 路线 B: 直接写游戏**活着的**通知文本框

两者结果一对比，就能区分"**是自建控件的问题**"还是"**我们写字的方式有问题**"。
手动诊断步骤里覆盖掉游戏当下那行通知是可接受的代价。

### 19-8 🔴🔴 事故：浮层让**整个游戏的菜单点不动了**（必须记住的一课）

**现象**（玩家报）：进游戏后 `Esc` 菜单**所有按钮都点不动**，连"返回标题"也点不了，
只能 `Alt+F4` 强制退出。

**根因：我在自建控件上写了 `SetVisibility(0)`。**

UMG 的"可见性"有 5 档，**"渲染"和"吃输入"是两件独立的事**：

| 值 | 含义 | 渲染 | 吃鼠标/键盘 |
|---|---|---|---|
| **0** | `Visible` | ✅ | **✅ ← 浮层绝对不能用这个** |
| 1 | `Collapsed` | ❌ | ❌ |
| 2 | `Hidden` | ❌ | ❌ |
| **3** | `HitTestInvisible` | ✅ | ❌ ← **只显示文字的浮层就该用这个** |
| 4 | `SelfHitTestInvisible` | ✅ | ❌（子控件仍可交互） |

我那个控件：
* 是 `AddToViewport(1000)` 加进去的 → **z-order 1000，在所有 UI 之上**；
* 尺寸铺满屏幕（UMG 加到视口的控件默认吃满全屏）；
* 可见性 `0` → **hit-testable**。

于是它变成了一块"**看不见但会吃掉所有点击**"的玻璃板，盖在游戏菜单上面。
我们改成 `RenderOpacity(1)` 之后连"透明"都不是了 ——
它可能就在画面上渲染着（只是内容是一堆空文本框），而**鼠标全被它截走**。

**修法（两层）**：

1. 所有"我们自己造的 UI"一律用 **`SetVisibility(3)`**（渲染，不吃输入），
   并补 `SetIsFocusable(false)` 防止抢键盘焦点。
   已封成 `Hud.force_display()`，**不要再用 `SetVisibility(0)` 显示浮层**。
2. **凡是盖在游戏 UI 上的东西，必须留一个"一键收回"的出口**：
   新增小键盘 `1` = 紧急收回提示控件（`RemoveFromParent`）；
   另外把配置里 `notify_try_notice_text` / `notify_own_widget` 改成 `false` 后
   按 `F8` 也会自动收回。

### 19-9 同一轮里暴露的第三个问题：**"借用测试"根本没在测借用**

报告里"借用路线测试"的目标写着：

```
目标: ...WBP_Notice_C_2147375273.WidgetTree_2147375272.BP_PalTextBlock_C_84
覆盖前显示: 「PWPR 测试文字 —— 能看见这行就说明通道可用」
```

——**那就是我们自己的控件**。因为自建的也是 `WBP_Notice_C`，
`filter = "WBP_Notice"` 一样匹配得到，于是"借用测试"写的是自己的文本框，
**等于没有做独立验证**。修法：借用路线**必须先排除我们自己的控件**。

> **教训**：设计"对照实验"时，要先确认两组的**取值集合真的不相交** ——
> 否则对照组就会被处理组污染，测了个寂寞。

### 19-10 线索：Create 一个通知控件会带出 **11 个**文本控件

```
新建文本控件=11
文本控件=...WBP_Notice_C_2147375273.WidgetTree_2147375272.BP_PalTextBlock_C_84
```

一个通知控件里有十几个文本框（标题/正文/时间…）。
第一版**只挑了名字前缀匹配到的第一个** —— 而那个**很可能不是显示正文的那个**：
于是"写进去了、回读也对、可见性也不透明度都正常"，屏幕上却什么都没有。

**修法：分不清哪个是正文，就全写。** `Hud.find_own_textblocks()` 返回**全部**，
`send` 对每一个都 `SetText`。这样无论正文是哪一个，都会显示出来。

### 19-11 ⚠️ 下一个嫌疑：**"外层可见" ≠ "里面可见"（根控件）**

把 11 个文本框全写了之后**还是看不见**。于是怀疑转移到
**UUserWidget 的"根控件"**：

```
UUserWidget（我们 Create 的那个壳）
   └── WidgetTree.RootWidget   ← ★ 真正画东西的是这一层
          └── ... 一堆文本框
```

UMG 里 `SetVisibility` 作用在**壳**上；而设计师为了"默认隐藏、需要时显示"，
经常把**根控件**设成 `Collapsed`，靠代码或动画去切它。
**我们是凭空 Create 的实例，没有任何代码去切它** ——
于是外面看什么都正常（`IsInViewport=true`、可视性 0/3、不透明度 1.0、尺寸 456x40），
**里面整棵树都不渲染**。

已处理：`Hud.root_widget()` 取根控件（`GetRootWidget()`，退回 `WidgetTree.RootWidget`），
`force_display()` 把它**连根一起**设成可见 + 不透明；
telemetry 里也把根控件的可视性/不透明度/期望尺寸一起打出来。

> 这条给了一个通用的检查顺序（**"浮层看不见"时的排查阶梯**）：
> **① 有没有写进去（回读）→ ② 在不在视口（IsInViewport）→ ③ 外层的可见性/不透明度
> → ④ 根控件的可见性/不透明度 → ⑤ 位置/尺寸（是不是被排到屏幕外）**。
> 前四步都能用代码读到，只有第五步需要人眼。

## 21. 🔴 `ClientMessage` 会闪退：**"能解析" ≠ "能调用"**（2026-09-27，第三次被反射误导）

### 21-1 事故

按 `O` 时探测的第 9 步（"真的发一行测试文字"）选中了 `client_message` 通道，
调用 `pc:ClientMessage(text, "Event", 4.0)` →
**`EXCEPTION_ACCESS_VIOLATION reading address 0x0000000000000070`** → 游戏闪退。
（那一步的留档文字正好写着"如果本文件到此为止，就是这一步" —— 一语成谶。）

### 21-2 我为什么会开它 —— 以及那个推理错在哪

上一轮我发现配置项没迁移、`ClientMessage` 压根没被测过，
于是从 `s9_candidates` 的信号里推出"它存在"：

```
GetControlRotation   usable=true    ← 对照组（每帧在用，肯定是真的）
ClientMessage        usable=true    ← 据此判定"它是真的方法" → 打开
```

**`usable` 只能证明"这个名字对应一个真的 UFunction"，
完全不能证明"UE4SS 用这几个参数调它是安全的"。**

这已经是本项目**第三次**被"反射里存在"误导：

| 次数 | 东西 | 反射说 | 实际 |
|---|---|---|---|
| 1 | `IsValid()` | 有 | 会把好对象判成无效 |
| 2 | `ForEachProperty` / `ForEachFunction` | UE4SS.dll 里扫得到 | **调用崩游戏** |
| 3 | `ClientMessage` | `usable=true`，参数个数公开已知 | **调用闪退** |

> **规矩（第 3 次强调，这次写成硬性检查流程）**：
> 判断一个引擎接口能不能用，**只看实机调用证据**；
> "能扫到字符串 / 反射里有 / 签名公开 / 别人代码里写过"**都不算证据**。

### 21-3 修法（照 `PrintString` 的处理方式：**留档 + 永不调用**）

1. `client_message` 通道加 `never_call = true` —— 连探测的"真发一行测试文字"
   都会**拒绝调用**它（`s9_send_test` 里明确判断）。
2. `probe`/`send` 直接返回失败并写明原因，**代码里不再有那行调用**。
3. 配置版本 4 → 5，**迁移把 `notify_try_client_message` 改回 `false`**
   （否则玩家按任何键都会闪退）。
4. `README` 的通道表把它标成"已知会崩，永久禁用"。

> 这就是 `S3` 里 `hud_print`（PrintString）的同款处理:
> **把一个已知会崩的调用变成一个只用于留档的条目**，
> 而不是删掉了事 —— 删掉的话，下一个人会再试一次。

### 21-4 同一轮里浮层方案的部分成功（重要）

`ClientMessage` 崩之前，第 7 步 `s9_overlay` 已经跑完并落盘：

```
--- [1] WBP_Warning_LowMemory_C / Text_Warning ---
  类: WidgetBlueprintGeneratedClass /Game/Pal/Blueprint/UI/WBP_Warning_LowMemory.WBP_Warning_LowMemory_C
  挂载=AddToPlayerScreen 在视口里=true 期望尺寸=0x0
  GetWidgetFromName(Text_Warning) -> nil
```

**读法**：
* ✅ `Create` + `AddToPlayerScreen(50)` **成功了**（`在视口里=true`）——
  SBB 那套挂载机制在我们这里也能用；
* ❌ `GetWidgetFromName` 取不到子控件；`期望尺寸=0x0` 也很可疑
  （一个警告条不该是 0 尺寸）。

两个改进（已写进代码）：
1. **取子控件改成 SBB 的两步顺序**: **先直接读属性**（`instance.Text_Warning`
   —— UMG 会把设计器里命名的子控件暴露成同名属性），
   不行再 `GetWidgetFromName`。SBB 就是把属性读取放在前面的。
2. 加一个**判定性问题**: "这个新建的控件下面**有没有**活文本控件"。
   * 有 → 控件树建出来了，只是名字没对上 → 继续调名字即可；
   * **一个都没有 → 控件树根本没被复制出来** ⇒ 克隆任何游戏自带控件都不会有效，
     那时唯一剩下的路就是**像 SBB 那样自带一个 UMG 控件 pak**（要 UE 编辑器/打包工具链）。

## 22. 🔴 提示通道把游戏搞崩：**Lua 造的 UObject 会被 GC 回收**（2026-09-27）

### 22-1 现象
旋转投影时闪退（两次），`EXCEPTION_ACCESS_VIOLATION reading address 0x000000fc000001e7`
（**垃圾地址**，不是空指针）。

### 22-2 定位过程（靠"细粒度标记"，不是靠猜）

第一轮只在按键处理函数外面加了 `>>` / `<<` 标记，结论只是"崩在两次旋转之间" —— 不够细。
于是在**投影变换那一段**和**发提示那一段**各插了落盘标记，第二次崩溃直接给出答案:

```
>> arrow-left
[step] apply_transform 开始
[step] apply_transform 完成        ← 引擎变换没问题（1 毫秒）
（"投影已移动（旋转）"）
                                   ← 没有 "[step] 提示已发送"
```

⇒ **崩在 `Notify.show` 里面**，与投影/旋转无关。

> **可复用的经验**：排查"按键就崩"，`>>`/`<<` 只够定位到"哪个按键"；
> **必须在可疑的那一段里再插几个落盘标记**（`Log.emit` + `Log.flush`），
> 下一次崩溃时日志的最后一行就是崩点。这比继续读代码猜快得多。

### 22-3 崩因（主嫌）: **Lua 持有的 UObject 引用不是 UPROPERTY**

我们自己 `CreateWidget` 造出来的控件，Lua 里只是一个引用 ——
**引擎的垃圾回收看不到它**（不在任何 UPROPERTY 里，也不在 GC 根集合里）。
于是它可能在任意时刻被回收，之后 Lua 手里就是个**野指针**，
再调用 `SetText` / `SetVisibility` → 访问违例（垃圾地址）。

* 这与"**提示一开始能用、过几秒/几次操作后突然崩**"完全吻合（GC 需要时间凑上来）；
* 也与"第一次旋转成功、第二次崩"吻合（同样的不确定性）。

**修法（三层）**：
1. **`AddToRoot()`** —— UE 标准做法，把控件加进 GC 根集合；销毁时配 `RemoveFromRoot()`。
   （失败路径也要撤根，否则废控件永不回收 = 内存泄漏）
2. **不再缓存"文本框对象"**：每次发送都用属性/`GetWidgetFromName` **重新取一遍**。
   缓存的旧对象同样可能已被回收。
3. **样式创建失败就"拉黑"一段时间**（`notify_style_retry_s`），
   并**把失败的半成品控件从画面撤掉**（`RemoveFromParent`）——
   留个坏控件在视口里，引擎每帧都要处理它。

### 22-4 同时补上的安全阀

* 游戏内通道发送失败时**自动退回控制台** —— 玩家不会"什么反馈都没有"；
* 配置里的 `notify_own_widget = false` = 只走控制台、完全不碰 UI（崩得没法玩时的应急开关）；
* 发提示每一步都有 `[ns]` 落盘标记 —— 万一还崩，**下一份日志直接指出崩在哪一步**。

## 23. 🔴 「回标题 → 重进世界 → 按 Y」必崩：**检查顺序错了 + `usable()` 会撒谎**

### 23-1 现象与定位

玩家: 操作几下 → 回标题 → 再进世界 → **按 Y 采集 → 闪退**。

这次靠 `[ns]` 细粒度标记直接钉死:

```
[ns] 开始
[ns] FText 好了
[ns] 取控件[normal]
[ns] 取控件[normal] 结束: 有        ← ★ 复用了"上个世界的旧控件"
[ns] 找文本框[normal]: 1 个         ← 拿到的是上个世界的文本框
                                   ← 然后 SetText → 访问违例
```

### 23-2 两个错，都在我这边

**错 1: 检查顺序反了。** `ensure_own_widget` 里"世界变了就丢掉旧控件"的判断，
写在了"旧控件还能用吗"的**后面**:

```lua
if st.widget ~= nil and Util.usable(st.widget) and Hud.is_live(st.widget) then
    return st.widget, nil            -- ← 从这里就 return 了
end
local wt = Hud.world_tag()           -- ← 世界检查根本没机会执行
```

**错 2: 而 `Util.usable()` 在已销毁的对象上会返回 true。**
本项目 `Util.usable` 的注释里**早就写了这个风险**
（"一个已经被销毁的 Actor，GetFullName() 有时仍然能调通"），
但真正踩到是在这一次: 内存还没被复用 → `GetFullName` 调通 →
代码以为对象还好好的 → 拿它 `SetText` → 崩。

> ⇒ **`usable()` 是"这个对象看起来像对的"，不是"这个对象还活着"。**
> 生命周期判断不能靠它。

### 23-3 修法与规矩

1. **世界检查必须排在所有"摸对象"的动作之前** ——
   连 `usable()` / `is_live()` 都算"摸对象"。
2. **判断对象有效性唯一安全的办法: 别碰对象，改比"世界标签"这个字符串。**
   `Util.world_tag()` = 当前世界的全名；换世界/回标题后会变。
   世界变了 → 旧对象一律当废品**丢引用**。
3. **同一个坑在投影那边也堵上**: `Ghost.apply_transform` / `hide` / `clear`
   全部先查 `Ghost.stale_world()`；世界变了就 `Ghost.forget()`
   （**只丢引用，绝不 destroy** —— 在引擎析构之后再调 `K2_DestroyActor`
   就是和引擎抢析构，那是更早一次崩溃的成因）。
4. `ensure_own_widget` 建控件时**现场取 PlayerController**，
   不用缓存里的 `ctx.pc`（缓存的那个也是上个世界的对象）。

> **可复用的规矩（写给未来的自己）**:
> 任何"跨帧长期持有的引擎对象引用"，都要配一个**字符串形式的世代标记**
> （世界名 / 关卡名 / 存档名），并在**第一次触碰这个对象之前**先比世代。
> 因为"这个对象还在吗"这个问题**问不出来** —— 问的过程本身就可能崩。

## 24. 🔴 **不要用 `UEHelpers.GetWorld()`**：它内部在撒谎的 `IsValid()` 上

### 24-1 现象

「启动游戏 → 进世界 → Y/J/K 全正常；**回标题 → 再进世界 → Y/J/K**，
按 K 崩」，崩溃地址 `0x0000000100000008`（垃圾值 = 访问已销毁对象）。

最后一次的日志只到「==== 投影 ====」，连材质行都没有 ⇒ 崩在
`do_ghost_toggle` 里很早的位置（世界检查那几行）。

### 24-2 根因：读了 UE4SS 自带库的源码才看出来

`Mods\shared\UEHelpers\UEHelpers.lua`:

```lua
function UEHelpers.GetWorld()
    local PlayerController = UEHelpers.GetPlayerController()  -- 内部用 IsValid() 过滤
    if PlayerController:IsValid() then                        -- ★ IsValid() 会撒谎
        return PlayerController:GetWorld()                    -- ★ 在废 PC 上调用 → 崩
```

* `GetPlayerController()` 用 `IsValid()` 挑对象，而 **`IsValid()` 在已销毁对象上
  也可能返回 true**（本项目第 1 号老坑）；
* 于是"回标题 → 重进世界"之后，它会拿**上个世界的废 PlayerController**
  去调 `GetWorld()` → 访问违例（垃圾地址）；
* `Util.world_tag()` 正好调用了它 ⇒ 崩在我们自己的"世界检查"里，
  而且**时好时坏**（取决于对象表里那个废 PC 还在不在）。

### 24-3 修法：绕开 UEHelpers，自己用"不依赖 IsValid"的查找

```lua
function Util.find_world()          -- FindFirstOf 不走那层 IsValid 过滤
    local w = nil
    pcall(function() w = FindFirstOf("World") end)
    ...
end

function Util.world_tag()           -- 世代标记 = 对象地址 + 全名
    local w = Util.find_world()
    return tostring(w) .. "|" .. (Util.full_name(w) or "")
end
```

* `tostring(obj)` 读的是 **Lua 侧 userdata 里的地址，完全不碰引擎** ⇒
  对已销毁对象也安全；而世界对象每次读档都会新建 ⇒ 地址必然改变，
  正好当"世代"信号。
* 同样改掉两处同源问题:
  * `acquire_host` 建宿主 Actor 时改用 `Util.find_world()`；
  * `Hud.find_pc` 改成**先** `FindAllOf("PlayerController")` + `Util.valid`
    （本项目的严格判据），UEHelpers 只当兜底 —— 否则它会把废 PC 交给我们，
    拿去 `CreateWidget` 同样是野指针。

> **规矩（补第 23 节）**：**不要相信 `IsValid()`**，也不要直接用基于它封装的
> `UEHelpers.Get*()`；生命周期判断一律走 `Util.valid`，
> 跨世界的世代判断一律走 `Util.world_tag()`。
> 另外：能读源码就去读（这次是靠读 `UEHelpers.lua` 才看到真相，
> 继续猜我们自己的代码只会越猜越远）。

## 25. ✅ 「回标题 → 重进世界 → 闪退」的正解：**换地图用事件，不要轮询**

### 25-1 三个阶段（每一阶段的失败方式都值得记）

| 阶段 | 做法 | 结果 |
|---|---|---|
| ① 无保护 | 复用缓存的世界内对象（HUD 控件、投影宿主/组件） | 重进世界后**碰废对象** → `EXCEPTION_ACCESS_VIOLATION` |
| ② 轮询世界标记 + 不符就销毁 | 每次操作前比一下"世代标记"，不同就 `forget` 重建 | 标记**抖动**时把**刚建好的投影**整个丢掉 → 日志 `apply_transform: 世界已切换` → `组件=0` → **玩家看到"每次 0 件"**；通知控件也反复重建 ⇒ 旧提示堆屏 |
| ③ **事件驱动**（最终） | `LoadMapPre` 钩子里**只清 Lua 引用**（一个引擎接口都不碰）；轮询降级为**纯诊断** | 换地图时权威、及时、不误伤；轮询只写一行日志，**永不销毁** |

### 25-2 为什么轮询注定不可靠

* 我们需要的信号是"**这张地图的生命周期结束了**"；
  而"世界标记"是我们自己**拼**出来的近似值（PC 地址 / World 对象名），
  它可能在**同一张地图内**发生变化（对象被替换、有多个候选、取到不同的那一个）
  ⇒ 一旦依它做**破坏性动作**（丢引用/销毁），就会误伤正常状态。
* 而 `LoadMapPre` 是**引擎自己发的**事件：只在真的换地图时触发，**不会误报**。
* 结论：**破坏性动作只能由事件触发；轮询只能用来"跳过 / 记日志"。**
  （对任何"跨生命周期缓存"都成立：UE 的 Actor/Component、Unity 的场景对象同理。）

### 25-3 实现要点（代码位置）—— ★ 那是中间版本，**最终版见 25-4**

| 位置 | 做了什么 |
|---|---|
| `pwpr_hud.lua` → `Hud.drop_world_refs(reason)` | 清掉两种样式的控件/文本框引用、失效扫描缓存、作废待补发的提示、`hide_gen++`（让排队中的自动隐藏全部失效）、清掉缓存的 PlayerController。**不调用** `RemoveFromParent`/`RemoveFromRoot`（那是碰引擎） |
| `pwpr_ghost.lua` → `Ghost.forget(reason)` | 已有函数，同样"只丢引用" |
| `main.lua` → `RegisterLoadMapPreHook` | 回调里 `Ghost.forget` + `Hud.drop_world_refs` + `Session.deactivate`，全部 `pcall`，只写日志；注册一次（F8 重载不会重复注册） |
| `pwpr_ghost.lua` → `Ghost.stale_world()` | 降级为**诊断**：发现标记不符时**只写一行警告并跳过本次操作**，**不再 `forget`**（`apply_transform` / `hide` / `clear` 三个调用点都已改） |
| `pwpr_hud.lua` → `ensure_own_widget` | 标记不符时**拒绝本次操作**（返回 nil + 原因）⇒ 调用方退回**控制台通道**：屏幕上不显示，但日志/控制台有，且**绝不碰可能失效的对象** |
| `pwpr_config.lua` | `hook_load_map_pre` 默认 **true**（v8 迁移把老文件里的 false 拉回来）；`world_guard_enabled` 标为**已废弃** |

### 25-4 ★ 第三阶段又被实测推翻：轮询标记**连"跳过"都不能做**

按 25-1 的第 ③ 阶段做出来之后，玩家反馈了三条现象，日志一次把它们解释清楚:

```
[hook] LoadMapPre: 已丢弃投影与提示控件的引用（不碰引擎）        ← 钩子每次都正确触发 ✔
[hud] 世界标记变了但控件还在: AActor: ...FAF8 -> AActor: ...5758  ← 标记【每次调用都在变】
[ns] 取控件[normal] 结束: 世界标记已变，跳过屏幕提示              ← 所以第 2 条起提示全被拒
[ghost] 注意: 世界标记与投影建立时不同 —— 本次操作跳过            ← 所以投影没上变换
> 投影已放置: 374 件                                            ← 件数对，但全留在宿主原点
```

**标记为什么不稳定**（都在这台机器上验证过）:
* 世界里存在**多个** `PlayerController`，`FindAllOf("PlayerController")` 返回顺序不定；
* `IsLocalPlayerController` 在 UE4SS 里**取不到**（调不通）；
* 于是"挑本机 PC"退化成"挑第一个"，每次拿到不同的对象 ⇒ 用它的地址当标记必然抖动。

**教训（比 25-2 更硬的一条）**:
> 一个"近似信号"如果不可靠，**不只是不能用来做破坏性动作 —— 连"跳过"都不能做**。
> 跳过会让功能静默失效（提示没了、投影不显示），而且**很难查**
> （看起来像"功能坏了"，其实是判断本身在误报）。
> ⇒ **不可靠的信号只能写日志；一切行为分支只允许依赖权威事件。**

**最终实现**:
* `Ghost.apply_transform` / `hide` / `clear`：**删掉**所有世界标记检查（跨世界清理由钩子负责）；
* `do_ghost_toggle`：删掉"标记不符就重建"的分支（钩子已保证换世界后 `visible=false`），
  回到最简单的"显示中就收起、否则放置"；
* `ensure_own_widget`：删掉"标记不符就拒绝"的分支；
* `Ghost.stale_world()` 保留函数但**没有任何调用点**（只作诊断备查）；
* `Util.find_pc_strict()` 的判据从"`IsLocalPlayerController`"换成
  **"这个 PC 有没有 Pawn"**（只有玩家自己的才有），并加上名字排序的确定性兜底 ——
  它只用于"拿一个能用的 PC / 它所在的世界"，**不再派生任何世代标记**。

### 25-5 为什么"钩子里做额外动作"这次是安全的

早先默认关掉这个钩子的理由是"世界加载期是最不该有额外动作的时刻"。
那个理由针对的是**碰引擎**；而现在的回调里：

* 只赋值 Lua 表/变量（`Ghost.host = nil`、`st.widget = nil`、`Hud.tb_cache = nil`…）；
* 一个引擎接口都不调（连 `IsValid` / `GetFullName` 都不调）；
* 每一步都包在 `pcall` 里，出错也只写日志。

⇒ 它的风险等级和"在 Lua 里把几个变量置空"相同，**不是**"在加载期操作引擎对象"。

## 26. 🔴 从世界取"组件类"取到了**植被组件**，拿它造组件直接崩

### 26-1 现象与定位（细粒度标记一次命中）

投影放置时**偶发**崩溃；有时同一个蓝图前面几次都成功、下一次就崩。
`[fill/ism]` 标记给出决定性一行:

```
[fill/ism] 组件类 OK 来源=live:InstancedStaticMeshComponent 类=Class /Script/Pal.PalFoliageISMComponentBase
[fill/ism] 准备 AddComponentByClass: 宿主有效=true 根有效=true 骨骼=false
           ← 崩在 AddComponentByClass 本身
```

### 26-2 根因

`new_ism` 拿组件类的方式是 **"向世界要一个现存同类组件的类"**
（这样能避开 `StaticFindObject` 拿到 TrivialObject 的问题 —— 见第 6 节）。
但 `FindAllOf("InstancedStaticMeshComponent")` 返回的**第一个**实例，
可能是 Palworld 的**植被**实例化组件 `PalFoliageISMComponentBase`（草/树用的专用变体）。

* 拿这个类去 `AddComponentByClass` 给普通 Actor 造组件 → **崩**；
* **为什么偶发**: "世界里第一个 ISM 是哪个"取决于玩家站位与当时加载的内容
  —— 站在草地附近就容易先撞上植被组件。

### 26-3 修法

1. **按类名排除专用变体**（`CLASS_DENY = Foliage / Hierarchical / Landscape / Spline / Grass`）：
   挑选时跳过它们，并把"跳过了哪些"记进日志；
2. 一次 `fill` 里**只向世界要一次类，之后复用**（`Ghost.fill_ism_cls` / `fill_skel_cls`）——
   第一次成功的类一定来自**本世界活着的组件**，反复要类只是反复暴露风险；
3. 全部候选都被排除时走路径兜底；仍不行就**干净失败**（"找不到可用的类"）而不是崩。

> **通用教训**：**"从世界里挑一个同类对象、拿它的类"这种做法必须带黑名单。**
> 引擎/游戏会为特殊用途派生大量子类（植被、地形、样条、水……），
> 它们不是"随便造一个"的合法目标 —— 而 `FindAllOf` 的"第一个"是**随机**的。

## 27. 🔴 `FindAllOf` 会遍历**全局对象表** —— 刚销毁的世界留下的死对象会让它崩

### 27-1 玩家给出的复现步骤（很精确，值得记下来）

1. 进 **新存档**（1.0），不做任何操作 → 回标题；
2. 进 **旧存档**（1.0 之前，基地很大）→ `Y`/`J`/`K` **全部正常**，多次 `J` 切蓝图再 `K` 也正常；
3. 回标题 → 再进 **新存档** → 按 `Y` → **崩**。

⇒ 与"存档版本"无关（旧存档里功能一切正常），真正相关的是:
**"刚离开一个内容很多的世界"** 这件事。

### 27-2 日志证据

```
[hook] LoadMapPre: 已丢弃投影与提示控件的引用      ← 切存档正常
==== 采集：玩家附近 ====
中心 (-1004.8, 416.2, 7.8) 米   半径 150 米
>> 开始扫描引擎对象（这一步会短暂卡顿）
   ← 崩在这里，而且**连一条 [scan] 都没打出来**
```

"连一条 `[scan]` 都没有"是关键: 说明崩在**枚举本身**，或最前面几个对象上
（当时 `[scan]` 每 25 行才刷盘，前 24 行被缓冲吞了 —— 这也是个教训，见 27-4）。

### 27-3 机制与修法

* `FindAllOf("PalBuildObject")` 遍历的是**全局对象表**，对每个对象都要
  **解引用它的类**来判断继承；
* 而刚被销毁的世界（旧存档那个大基地有 2454 个 actor）会在表里留下
  **已被释放的对象** ⇒ 遍历到它们 = `EXCEPTION_ACCESS_VIOLATION`；
* **修法**: 改用**当前关卡自己的 Actor 列表**
  `world.PersistentLevel.Actors`（引擎维护的"本关卡活着的 Actor"数组，不含死对象），
  再用 `UClass.SuperStruct` **读属性**沿继承链判断类别（不调 `IsA()`，因为它的可用性没验证过）；
* 拿不到关卡列表时才退回 `FindAllOf`，并在日志里写明来源
  （`[scan] 枚举到 N 个建筑（来源: PersistentLevel.Actors（关卡共 M 个 Actor））`）。

> **通用教训**：**枚举对象优先用"容器自己维护的列表"（关卡 Actor 数组、
> 组件的 AttachChildren、UI 的 WidgetTree），而不是全局对象表。**
> 全局表里混着"已销毁但还没被清理"的对象，而任何一次解引用都可能是致命的。

### 27-4 附带的排查教训

`[scan]` 这类"每 N 个刷一次盘"的写法，在**崩点位于开头**时会**把证据吞掉**
（缓冲没落盘）。⇒ 这类细跟踪应当**开头逐个刷**（现在改成"前 50 个逐个刷，之后每 25 个"）。

> ## ⚠️ 2026-09-29 更正：上面 27-2 的"日志证据"**是无效的**
>
> 做建筑吸附时顺手核对了一下，发现 **`pwpr_capture.lua` 里那些 `[scan]` / `[cap/name]`
> 跟踪行从来就没写出来过** —— 原因是它们用的 `Log` 是一个**不存在的全局变量**
> （详细根因见下面 §34）。实测: 部署目录里 1.7 MB 的 `pwpr.log` 里
> `[scan]` 出现 **0 次**，连带"`[scan] 枚举到 N 个建筑（来源: …）`"也一次都没有。
>
> ⇒ 也就是说: **"连一条 `[scan]` 都没打出来"当时并不能证明"崩在枚举本身"**
> （那几行代码根本没生效）。
> 结论本身（改用关卡 Actor 列表）现在依然是对的、也确实修好了崩溃，
> 但当时的**推理链里有一环是空的**。
>
> **通用教训（比这个 bug 本身更重要）**：
> 拿"日志里没有 X"当证据之前，**先确认"X 真的会被打印出来"** ——
> 最省事的办法就是**故意触发一次已知路径**，看到那行确实出现再拿它当证据。
> 这属于"取证工具本身也要取证"。

## 28. 🔴 换存档投影**缺件**：蓝图只存了短名，而短名解析依赖"当前加载了什么"

### 28-1 现象与玩家的一句话

换了存档不再崩之后，玩家发现: **在另一个存档投影出来的东西有缺失**，
并指出"**采集的存档肯定是建好了的，导出蓝图绝大多数情况都是到不同存档使用**"
—— 也就是说，这个问题不解决，整个模组就失去意义。

### 28-2 根因（代码链）

* 蓝图记录里只存网格**短名**（`pwpr_bp.lua`: `b.mesh = r.mesh`，如 `SM_Floor_Wood`）；
* 投影时用 `MeshMap.lookup_short(短名)` 查路径，而那张表 (`MeshMap.by_short`)
  是用 **`FindAllOf("StaticMesh"/"SkeletalMesh")`** 建的 ——
  **只包含当前世界里已经加载的资产**；
* 在**采集的那个存档**里，那些建筑都在场 ⇒ 资产全加载 ⇒ 全部能解析；
* 换到**另一个存档**，蓝图里的大量资产根本没被加载 ⇒ 查不到 ⇒ `resolve_all` 返回 nil
  ⇒ `Ghost.fill` 里 `skipped_no_mesh + 1` ⇒ **不画**。

### 28-3 修法

1. **采集时把完整路径写进蓝图**：`read_one` 把 `diag.mesh_full`（从 actor 网格组件读到的
   全名，本来就有）带出来 → `pwpr_bp.lua` 写成新字段 **`mesh_path`**，
   并在 `meta.meshCoverage.withPath` 里统计覆盖率；
2. **投影时优先用它**：`MeshMap.resolve_all` 里加了"路径优先"分支 ——
   在**多网格覆盖表之后**（那扇门 = 门框 + 两片门扇，是人工确认过的完整构成，
   必须优先）、在短名解析之前；直接 `LoadAsset(路径)`，与加载状态无关；
3. **诊断可见**：投影报告新增按类型的缺件清单
   （`缺网格: Wood_DoorWall 2 件` …），一眼看出还缺谁、该补哪条映射。

### 28-4 对旧蓝图的影响（要跟玩家说清楚）

旧蓝图没有 `mesh_path`，跨存档仍可能缺件 ⇒ **回源存档重采一次**即可。
这一点写进了 `mod\PWProjection\已知限制.md` 第七节。

> **通用教训**：**"把运行时状态当作可移植数据"是个陷阱。**
> 蓝图是**要跨会话、跨存档使用**的产物，所以它必须自带**自足**的信息
> （完整路径），而不是依赖"当前进程里恰好加载了什么"。
> 采集那一刻我们知道得最多 —— **采集时就该把该记的都记下来**。

## 29. 🔴 `mesh_path` 修复**完全没生效**：`Util.full_name` 带类名前缀，我却按"首字符是 /"判断

### 29-1 现象与排除过程

玩家反馈"换存档投影还是缺件"，并且**重采了很多次**（我到游戏目录看了文件:
文件时间 02:42、`meta.createdAt` 02:42 —— 确实是刚采的）。
而我上一条修复（把网格完整路径写进蓝图 `mesh_path`）看起来"应该已经生效"了 ——
文件明明是新采的，字段却没写进去。

**⇒ 结论: 不是"旧蓝图"的问题，是我那条修复有 bug。**
教训: 用户说"我重采过了"时，**先去核对文件内容**（我这次核对了 ✔），
不要靠"应该生效了"来推断。

### 29-2 根因（一行判断写错）

```lua
-- 我原来写的（错）
if type(r.mesh_path) == "string" and r.mesh_path:sub(1, 1) == "/" then
```

而 `Util.full_name(obj)` 返回的是 **`"StaticMesh /Game/Pal/.../X.X"`** ——
**带类名前缀**（游戏日志里每一行 `全名=StaticMesh /Game/...` 都是这个格式）。
⇒ 首字符是 `S` 而不是 `/` ⇒ **每一条记录都被挡掉** ⇒
蓝图里**一个 `mesh_path` 都没有**，而我那段"跨存档修复"等于没上线。

**修法**: 先把 `/` 之后的部分抠出来再用:

```lua
local only = r.mesh_path:match("(/.*)$")
if only ~= nil and only:find("/Game/", 1, true) ~= nil then
    b.mesh_path = only
end
```

投影端（`MeshMap.resolve_all`）也做了同样的"防御性提取"，
万一字段里还带前缀也能用。

### 29-3 加了"当场喊出来"的自检（防止同类问题再躲过去）

这个 bug 最恶劣的地方是: **采集日志一切正常**（"有网格 475"），
只有翻蓝图文件才看得出路径没写。所以现在采集结束时:

* 报告里固定打一行 `网格覆盖: 有网格 N / 有完整路径 M / 共 T 件`；
* 若 `有网格 > 0` 但 `有完整路径 == 0`，日志打 `!!` 并弹屏幕提示
  （`meta.meshPathWarn`）。

### 29-4 顺带：蓝图文件名现在带**易读的采集时间**

玩家要求"重采不要覆盖 / 或用易读时间区分"。现在文件名是:

```
base_-1620_-609_2026-09-28_1430.blueprint.json
```

* 好处: 每次采集都是新文件，能分辨"哪份是哪次采的"；
* 代价: 同一基地反复采集会攒文件（按 `J` 切换会逐个经过）；
* 想回到"按基地名覆盖、只留一份": 配置里把 `blueprint_name_with_time` 设为 `false`。

> **通用教训（第三次栽在同一个坑上了）**：
> **改代码时不要"想当然地"假设某个工具函数的返回值格式 —— 去日志里看它真实长什么样。**
> `Util.full_name` 的返回值在日志里出现过几百次（都带 `StaticMesh ` 前缀），
> 我却按"纯路径"来写判断；而这类错误**不会报错、只会静默失效**，
> 所以每次做这种"格式假设"都要顺手加一条**覆盖率自检**。

## 30. 🔴 「高科技建筑（球体工厂/武器工厂/磨粉机…）堆在帕鲁终端上面」—— 骨骼网格被误判成静态

### 30-1 玩家描述（很关键的三个细节）

* 高等文明帕鲁球工厂、高等文明武器工厂这些东西**堆在帕鲁终端的上面**；
* **哪怕同一个存档**也会出现；
* 只有「**重新按 Y 采集**、并且在**同一个存档**里加载投影」才不会出现。

### 30-2 日志证据（新加的 dump 一次命中）

```
[ghost/dump] 放置点=(-99590, 39976, 1010) 宿主=(0.0, 0.0, 0.0) 组件=44 骨骼=0 模式=local
    …/StoneMill/SK_StoneMill         组件世界=放置点 距放置点=0 厘米 实例(我们/引擎)=0/nil
    …/FrozenCrusher/SK_FrozenCrusher 组件世界=放置点 距放置点=0 厘米 实例(我们/引擎)=0/nil
    …/Pulverizer/SK_Pulverizer       组件世界=放置点 距放置点=0 厘米 实例(我们/引擎)=0/nil
  [ghost/dump] 核对完成: 组件 44 个，其中距放置点 >50 厘米的 0 个
```

* `骨骼=0`（`skel_list` 是空的）、那三个 `SK_` 组件的 `实例=0/nil`
  ⇒ 它们**被当成静态实例化**处理了；
* 而它们的**组件世界坐标 = 放置点**（玩家站的位置，通常就在终端旁边）
  ⇒ 玩家看到的就是"这些东西堆在终端上面"。

### 30-3 根因：把"运行时注册表"当成了权威判据

```lua
-- pwpr_ghost.lua（分组时）
if MeshMap.is_skeletal(mesh) then   -- ← 查的是"当前已加载资产"注册表
```

`MeshMap.is_skeletal` 原来**只**查 `FindAllOf("SkeletalMesh")` 建出来的注册表，
而那张表**只包含当前世界里已经加载的资产**。于是:

| 时机 | 注册表里有没有 | 判定 | 结果 |
|---|---|---|---|
| 刚采集完（资产都在场） | 有 | 骨骼 ✔ | 正常 |
| 换存档 / 刚启动直接加载旧蓝图 | **没有** | **静态** ✗ | 分组不带序号、走 `AddInstance`（在骨骼组件上必失败 ⇒ 0 实例）、**不进 `skel_list`** ⇒ 组件停在放置点 ⇒ 「堆在终端上面」 |

这也正好解释了玩家观察到的"只有重新按 Y 采集 + 同存档才正常"
—— 那条路径下资产刚被加载过，注册表里有它们。

### 30-4 修法

1. **`MeshMap.is_skeletal` 加名字约定兜底**：Palworld 的骨骼网格资产一律 `SK_` 开头

## 34. 🔴 采集模块的"崩溃取证"跟踪**从来就没生效过**：`Log` 是个不存在的全局变量

### 34-1 怎么发现的（2026-09-29，做建筑吸附时顺手核对）

做吸附要复用采集的"列出本关卡建筑"函数，顺便去游戏目录看了一眼部署版的日志，
想确认 `[scan]` 跟踪长什么样（好照抄格式）。结果:

```powershell
Select-String pwpr.log -Pattern "\[scan\]" | Measure-Object   # → 0
Select-String pwpr.log -Pattern "\[cap/name\]" | Measure-Object # → 0
```

**1.7 MB 的日志里，这两类跟踪一次都没出现过。**

### 34-2 根因（一行 require 少了）

`pwpr_capture.lua` 里所有跟踪都写成:

```lua
-- pwpr_capture.lua（错）
local Util = require("pwpr_util")
local BP   = require("pwpr_bp")
-- ← 这里少了 local Log = require("pwpr_log")
...
if Log ~= nil then Log.line("[cap/name] " .. ...) end   -- ← Log 是【全局】变量
```

而**本项目里没有任何地方定义过全局 `Log`**（其他 5 个模块都是
`local Log = require("pwpr_log")`）⇒ `Log` 恒为 `nil` ⇒
`if Log ~= nil` 这个"防御性判断"**把所有跟踪静默跳过了**。

* 保护性写法（`if Log ~= nil`）本身没错，错的是**变量来源**：
  它把"Lua 全局作用域"当成了"模块作用域"。
* 这类 bug **不报错、不影响功能**，只是"证据链是空的" —— 而它恰好长在
  **专门用来取证的那段代码**上，最阴。

**修法**: 补上 `local Log = require("pwpr_log")`（见 34-3 的验证方式）。

### 34-3 怎么避免再犯

1. **"日志里没有 X" 不能直接当成证据** —— 先用一条已知路径确认 X 会打印
   （这条也回头修正了 §27-2 的推理，见那里的更正框）；
2. 新增/复用"取证型"代码后，**去部署目录 `grep` 一次**看它是否真的产生输出
   （`Select-String` 几秒钟的事）；
3. 本项目后来给吸附模块写日志时直接 `local Log = require("pwpr_log")` +
   在关键阶段 `Log.flush()`，并在**第一个游戏内测试**里就核对这几行是否出现。

## 35. 🔴 建筑吸附最大的坑：**"投票"会被格状对称骗走**（错一格，还特别自信）

### 35-1 背景

待办 2（放置吸附）要解决的问题: 投影原点在"玩家脚下"，
和原基地差着一截，手动一格一格挪太累 ⇒ 一次按键算出偏移。

第一版算法（直觉版）：**每条记录找最近的同类真实建筑 → 每一对都给出一个
"投影原点该在哪"的候选 → 候选按 25 厘米分格投票 → 票数最高的就是答案。**

### 35-2 这个算法在合成数据上**立刻露馅**（还没进游戏就抓到了）

本机**没有 Lua 解释器**（UE4SS 内嵌的那个没法单独调），
所以我把算法**复刻成 Python**（`tools\snap_sim.py`），拿合成基地跑。
结果（差 17.5 米时）:

```
与真值的偏差: (0.0, -800.0, 0.0) 厘米     ← 偏了整整 2 格（格距 400 厘米）
对上 98/152 件；朝向 90° 应该纠回 0°，却仍然输出 90°
```

**根因（值得记住）**:
基地的地基/墙是**格状排列**的。设真偏移 `T`、当前偏差 `e`，则地基那一件
"最近的同类建筑"往往是**隔壁那一格** ⇒ 它给出的候选是 `T + v`
（`v` = 离 `e` 最近的格向量）—— 而**所有地基都会给出同一个 `T + v`**！
于是投票高峰落在 `T + v`（几千票），真正的 `T` 只有稀疏的设施那几十票。

**⇒ 格状对称把"票数"这个信号彻底污染了。**
而且它错得非常"自信": 错一格的对齐里，地基照样全部对上，复核分也不难看。

### 35-3 正解：候选由"**最不可能认错的那几对**"决定，票数只当补充

改后的算法（`pwpr_snap.lua`）:

1. **可信对生成候选**: 按"这个类型在附近有几个参照"**升序**排序，
   取最可信的若干个配对，每一对**直接**给出一个精确候选 ——
   唯一的那台机器，它最近的同类只可能是它自己 ⇒ 这一对给的候选就是真偏移（误差 0）；
2. **投票高峰也留一份当候选**（万一基地里全是重复件、没有稀缺类型，那它是唯一线索）；
3. 用**全部记录的抽样**（优先抽"同类参照最少"的类型 = 最分得清对错的那些）
   给每个候选打分，粗筛出前几名；
4. 只对前几名做**完整复核**（拿全部记录算），取胜者；
5. 再在胜者附近**用更小的阈值重新配对取平均**（把 25 厘米分格误差抹掉）。

合成数据验证（`python tools\snap_sim.py`，8 个场景全绿）:

| 场景 | 说明 | 结果 |
|---|---|---|
| 站中心附近（差 3.7 米） | 最常见用法 | 对上 152/152，偏差 **0.0 厘米** |
| 站基地边上（差 17.5 米） | 第一版在这里翻车 | 对上 152/152，偏差 **0.0 厘米** |
| 投影已被转过 90° | 该把朝向也纠回来 | 朝向 **90° → 0°**，偏差 0.0 厘米 |
| 关掉朝向搜索 | 只平移 | 偏差 0.0 厘米 |
| 现场被拆掉三成 | 蓝图是旧样子 | 对上 115/152，偏差 **0.0 厘米** |
| **纯格状基地**（刻意去掉所有独特件） | 已知局限 | 落在"整数格"偏移上（**信息本身不足以定位**，见 35-4） |
| 附近只有别的建筑 / 一个都没有 | 该明确失败 | 明确失败，投影**一动没动** |

### 35-4 诚实地承认"我也不知道对不对"

格状基地那一行说明: **有些布局下根本没有足够信息定位**。
所以吸附结果会带两个"信心指标"，屏幕上直接说出来:

* **匹配率** = 对上的件数 / 蓝图总件数，低于 80% 提示 `（匹配 46%，看一眼）`
  （两种可能: 基地真被拆过，或者没对准）；
* **歧义** = 第一名比第二名只多对上很少的件 ⇒ 提示 `（有歧义，看一眼）`
  （好几个位置都说得通）。

宁可让玩家"看一眼确认"，也不要让投影**悄无声息地挪到错的地方** ——
后者比"功能没做"更糟，因为他会照着错的位置盖。

> **通用教训（本项目第 N 次验证）**：
> **能被离线验证的算法，就别拿到游戏里去试。**
> 这一版如果直接进游戏，玩家的反馈会是"吸附不准/吸歪了"，
> 而我得靠猜；写成合成数据自检后，**第一次跑就指出了根因**，
> 还顺手把"已知局限"固化成了一条断言。
> 另外: 复刻有走样风险 ⇒ `snap_sim.py` 会**反向读 Lua 源码**
> 校验常量与关键结构（改了 Lua 不同步就报错）。

## 36. 🟡 两个"静态检查器当场拦住"的低级错误（都发生在同一次改动里）

### 36-1 局部变量起名 `pairs`，遮蔽了 Lua 的全局 `pairs()`

```lua
...
```

  吸不到（空地上放投影 / 附近没有原建筑）才报"投影已放置"，而且**不弹错误**
  —— 那不是错误；
* 加键的限制也写清楚: `snap_key` 可改，改完**重启游戏**（键位只在启动时注册）；
* 文档里凡是提小键盘的地方，都补一句"**没有小键盘就用 X**"
  （例: 小键盘 `5` 清偏移 = 主键 `H`）。

### 37-4 为什么"挪投影时自动吸"没做（也是设计决定，要写下来）

看着像"更自动更好"，但:
1. 方向键/小键盘是**按键重复速率**触发的 —— 按住一秒来十几次，
   而吸一次要读几千个 actor 的位置 ⇒ **每按一下卡一下**，根本没法精调；
2. 它会和手动微调**互相打架**（刚挪开一格就被吸回去）。

⇒ 定成"**放下那一刻吸一次**"，之后偏移一直保留（走动不影响投影），
需要再对齐时按 `U`。这条写进了配置注释和 `已知限制.md`。

> **通用教训（这次要真正记住）**：
> **"玩家用什么键 / 什么键盘"属于需求，不是实现细节。**
> 这个项目已经为 84 配列做过一次改造（方向键 + 模式），
> 结果新功能又默认挂到小键盘上 —— 说明光"文档里写过"不够，
> **新增任何按键时，第一件事是回去看那份键位表，并问一句"这个键盘上按得到吗"。**
> 同理: 新增按键前先问"**这个功能真的需要玩家多学一个键吗**" ——
> 能塞进"放下投影"这种**已有动作**里，就别多给一个键。
