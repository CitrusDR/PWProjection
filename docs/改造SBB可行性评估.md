> 用户提出的方向：**"SBB 已有功能可能覆盖我们大部分需求，
> 只要给一键生成加个选项允许自行放置就行了。可以改改单独放一个目录试试，不发布影响不大。"**
>
> 本文档是对这个方向的**务实评估**，基于对 SBB 架构的只读分析。
>

> 结论不变: 我们**没有**改 SBB、也没有复用它的代码。

## 一、用户的判断对不对？—— 对了一大半

SBB **确实覆盖了我们最初列的大部分需求**：

| 我们的原始需求 | SBB 是否已有 | 说明 |
|---|---|---|
| 添加蓝图 | ✅ | `BlueprintLibraryImporter` + 分享码 |
| 加载蓝图 | ✅ | `BlueprintLibraryStore` / `Manager` |
| **半透明投影** | ✅ | `BlueprintGhostRenderer`（110KB） |
| 移动投影 | ✅ | 有锚点探测 + 相机模式 + 吸附 |
| 可放/不可放着色 | ✅ | 浅蓝 `Highlight` / 浅红 `Error`，**材质直接取自游戏** |
| 按类别过滤 | ✅ | `BlueprintPlacementFilter` |
| **分层展示** | ❌ | **91 个模块里没有 layer 相关** |

**结论：除了"分层展示"，其余都已有。** 用户的判断基本正确。

## 二、但"加个自行放置选项"这件事，比听起来难

### 2.1 配置层做不到

SBB 有 **61 个配置项**（`BlueprintResearch.modconfig.json`）。

我逐项检查了所有"开关"类配置：

```
blueprint_camera_requires_base            相机是否需要基地
blueprint_overlap_gate_enabled            重叠校验门
blueprint_support_connection_gate_enabled 支撑/连接校验门
blueprint_material_gate_enabled           材质条件门
blueprint_force_submit_invalid_enabled    强制提交无效件
blueprint_instant_build_only_enabled      只放可瞬建的（排除工作台等）
blueprint_slanted_roof_replacement_enabled
blueprint_slanted_roof_restore_enabled
blueprint_save_connectivity_gate_enabled
```

其余全是：性能预算（`frame_*_budget_ms`）、延迟（`*_delay_ms`）、
容量上限（`*_max_items`）、日志开关。

**没有任何一项能关掉"自动建造"、或切换成"只显示投影"。**

### 2.2 也没有隐藏的"手动模式"

配置里的 `manual` 类别**不是"手动放置模式"**，而是指
**"必须人工建造的设施"**（工作台、箱子、家具这类不能瞬建的）。证据：

```
"Instant-build-only filter: %d manual structures excluded."
"Cannot place blueprint: every structure requires manual construction."
```

所以 `blueprint_build_priority_rules` 里的 `manual=terminal:900`
是"这些人工设施排到最后处理"，不是"让玩家手动放"。

### 2.3 行为是硬编码在逻辑里的

自动建造流程的结构：

```
main.lua:L4063
  blueprint_construction_coordinator =
      BlueprintConstructionCoordinator.new({
          get_world_generation = ...,
          log = log,
      })
```

- 这是一个**启动时创建、活到世界结束的长驻服务对象**
- 接口只接受 3 个 option（`id` / `log` / `world_generation`），
  **没有"仅预览"这类模式开关**
- 放置流程在玩家"确认放置"时调用这个服务，服务内部按波次（wave）提交建造

要改成"手动放置"，需要**拦截这个服务的调用**——
即：让幽灵照常渲染（`BlueprintGhostRenderer` 部分），
但**不把计划交给 `blueprint_construction_coordinator` 执行**。

### 2.4 影响面不小

| 指标 | 数值 |
|---|---|
| Lua 模块数 | 91 |
| 代码总量 | 约 2.4 MB |
| `require` 调用 | **152 处，涉及 47 个模块** |
| 入口 `main.lua` | **527 KB**（单文件） |
| 放置相关模块 | `PlacementInput`(43KB)、`ConstructionCoordinator`(32KB)、`WavePlanner`(33KB)、`BuildSessionRuntime`(30KB)、`PlacementRuntimeBackend`(27KB) … |

**自动建造不是一个孤立功能，而是一条贯穿多个模块的流程**：
输入 → 锚点探测 → 分波规划 → 原生校验 → RPC 提交 → 进度跟踪 → 失败重试。

"只投影不建造"意味着要在这条链上找到**唯一正确的切断点**，
并且切断后不能让依赖它的模块（进度 UI、失败可视化、替换流程等）出错。

**这是可行的，但需要精读 2.4MB 代码找到那个点，然后反复实测。**
风险：改错一处可能引发连锁问题（就像我之前崩你游戏那样）。

## 三、三条路对比

| | 路 A：改 SBB | 路 B：自己写"只投影"mod | 路 C：先用 SBB 不改 |
|---|---|---|---|
| **工作量** | 中—高（读 2.4MB 找切断点 + 实测） | **中**（只做投影，约 300-600 行 Lua） | **零** |
| **能拿到分层展示** | ❌ 还要另外加 | ✅ **从设计开始就带** | ❌ |
| **风险** | 改动大，连锁问题 | 可控（代码量小） | 无 |
| **版权** | 自己用可行，但"修改需授权"；给作者发个说明更稳 | 完全干净（我们自己的代码） | 无 |
| **稳定性** | 依赖 SBB 更新（它迭代很快） | 独立，不受影响 | 不受影响 |
| **能借鉴的** | — | **可以直接用 SBB 的架构思路**（锚点复用、材质复用） | — |

## 四、我的建议：**路 B（自己写"只投影"mod）**

理由：

### 1. 现在我们知道"该写什么"了，成本大幅下降

之前 7 轮探测之所以失败，是因为**不知道该怎么做**。
现在从 SBB 的架构里拿到了完整的"做法清单"（思路层面）：

| 需要的东西 | 已知答案 |
|---|---|
| 怎么渲染半透明 | `world:SpawnActor` + `host:AddComponentByClass`（纯 Lua） |
| 用什么材质 | `manager.BuildingSurfaceMaterialSet.Highlight` / `.Error`（游戏自带） |
| 怎么省 Actor | **锚点复用**：借一个已放置建筑当宿主，多组件挂上去 |
| 用完怎么收 | `restore_transform` + 恢复原材质 / `destroy` |
| mesh 从哪来 | 类型映射表（`SM_<部件>_<材质>`，从 ImposterChunk 的 HISM 采） |

**这些全是"思路"，不是代码。** 我们独立实现，法律和技术都干净。

### 2. 我们要的功能范围比 SBB 小得多

SBB 要解决的是"**自动批量建造**"这个难题，所以它必须处理：
建造顺序/依赖（`WavePlanner` 33KB）、原生重叠校验（`NativeOverlapGate` 46KB）、
支撑传播（`SupportGate` 45KB）、RPC 提交与失败重试（`BuildSessionRuntime` 30KB）、
材质条件、替换流程、进度 UI……

**我们只要"把幽灵画出来 + 分层显示 + 移动旋转"。**
不需要建造顺序、不需要精确校验、不需要 RPC。
**范围小了可能 10 倍。**

### 3. 分层展示必须自己做

这是用户最初明确要求的功能，SBB 没有。
如果走"改 SBB"路线，还是得自己写分层——那不如一开始就自己写，
把分层做成第一等公民，而不是往 2.4MB 里塞。

### 4. 版权更省心

SBB 作者明确要求"**修改需授权**"。
即使自用，**完全不碰它的代码**是最干净的做法。
我们可以把它的**行为**当参考（架构思路），但实现完全独立。

### 5. 我之前的教训要求"小步可控"

我因为改动大、验证不足，崩了 3 次游戏。
**自己写 300-600 行、每个 API 调用都单独验证**，
比在一个 2.4MB 的黑盒里找切断点要可控得多。

## 五、如果仍想试路 A，最小实验建议

如果你还是想先试试改 SBB（也合理，因为它的投影+吸附已经很完善），
建议**先做不改代码的验证**：

1. **先用原版 SBB**：确认它的投影、吸附、库管理确实满足你
2. 如果确认只差"不自动建造"，再决定：
   - 找 `main.lua:L4063` 附近，看 `blueprint_construction_coordinator`
     被哪些地方调用（这是唯一的建造发起者）
   - **先加日志**（不改变行为）打印每次调用的调用栈与参数，
     确认"确认放置"的那一次调用长什么样
   - 再尝试**只让那一次调用空转**（返回假成功），看会发生什么
3. 每一步都要能**随时回退**（保留原版目录，改动的放另一个目录）

### 目录隔离约定（用户已提出，很对）

```
D:\dsh-workspace\
├─ SimpleBuildingBlueprints 4073 0.16.1 ...   ← 原版（保留，不修改）
└─ SBB-mod-手动放置测试\                        ← 改动版（单独目录）
    └─ Pal\... （从原版复制后修改）
```

**只在游戏里装改动版，原版目录保持干净**，便于对比和回退。

## 六、结论

| 问题 | 答案 |
|---|---|
| SBB 覆盖我们大部分需求吗？ | **是**，除"分层展示"外都有 |
| 加个"自行放置"选项容易吗？ | **不容易**。配置层做不到，行为硬编码在长驻服务里，影响面涉及 47 个模块 |
| 改它值得吗？ | **不如自己写"只投影"mod**：范围小 10 倍、能带分层、版权干净、可控性强 |
| 但先试用原版 | **强烈建议**。可能结论是"它够用了"，那就省下全部开发 |

**推荐顺序**：
1. 先跑 `tools/cleanup.ps1` 清掉我们的 PWRecon（避免抢键）
2. 装原版 SBB，用一段时间
3. 然后用它/不用它的结论，决定要不要写我们自己的"只投影 + 分层"mod

**无论走哪条路，SBB 的架构分析都已经让我们省下了几个月的摸索。**
