### 待办 2b —— ★ **建造吸附**（玩家真正要的那个"吸附"）—— 2026-09-29

**要什么**：照着投影盖房子时，手里那块建筑摆到投影里对应那一件的附近，
**放下去的那一刻**自动落到投影的精确位置上。

**状态**：🟢 **可用（在用）** —— 2026-09-29 玩家实测认可手感并定稿。
`align` 模式下"大致摆一下就能对齐"；**默认灵敏度已按玩家实测放宽**
（半径 **2000** 厘米 / 高度跟投影 / 朝向总是跟投影 / 最远 **3000** 厘米 / 类型放宽 **1000**）；
`buildsnap_min_cm = 5`（差得比 5 厘米还准就**完全不插手** ⇒ 放置瞬间不卡）；
放置时的屏幕提示默认**不弹**（`buildsnap_notify = false`，弹提示是卡顿主因）。

**怎么用**：不用按键 —— 加载蓝图 + `K` 放出投影 + 进建造模式正常摆，
放下时自动判断（类型/距离对得上才吸，否则**原样放行**）。

>   `blueprint` 模式"提示成功但没放" = 目标在 11~25 米外 + 高度差 47 厘米（§44）；
> * 第四次: 跑的是**上一版**（部署没生效）⇒ 加 `Util.BUILD` 构建标记（§45）；

**两种模式**（配置 `buildsnap_mode`）—— ★ **2026-09-29 定稿: 只有 `align` 是"在用"的**:

| 模式 | 状态 | 选目标的方式 / 用途 |
|---|---|---|
| `align`（默认） | ✅ **在用**（玩家实测认可手感） | 与"这次放置的坐标"最近的**同类型**记录；你自己选好那一块、对着投影摆过去，放下时精确落位 |

#### 探测方法（★ 这一段已被实机推翻并重写，保留原文只为记录思路变化）

**原计划**（2026-09-27 上午写的）：**先枚举，再调用** ——
用反射（`ForEachFunction` / `ForEachProperty`）把函数名连同参数签名读出来，
"参数个数没看清之前绝不去调那个函数"。

**❌ 这个计划的第一步就把游戏打崩了**（第 2 步，崩溃栈 80 帧全在 UE4SS）。
而且 `踩坑记录` 3c-3 / 3f-2 **早就记过 `ForEachProperty` 不可用**。
→ 详见 `docs\踩坑记录.md` 第 17 节。**反射枚举已永久禁用**（`luacheck` 第 11 项会拦）。

**现在的方法**：**先确认存在，再调用** —— 用两种本项目安全用了几个月的操作：
`FindAllOf("精确类名")` 和 `obj.方法名` 存在性查询（`type == "function"` 才算存在）。

`O` 键跑 S9（**7 步**，顺序 = 风险从低到高，每步**先写盘再调用**）：

| 步 | 内容 | 风险 |
|---|---|---|
| `s9_player_controller` | 拿 `PlayerController` | 零 |
| `s9_ftext` | `FText` ASCII + **中文** 构造与回读 | 零 |
| `s9_widgetlib` | UMG 函数库 CDO | 零 |

### 待办 2 —— 放置时**吸附到蓝图位置**

> ## ⚠️ 做吸附之前必须知道的特殊情况（2026-09-28 玩家要求记下来）
>
> 蓝图的"一件建筑 = 一个网格 + 一个朝向"这个模型**对下面这些东西是不准的**，
> 吸附时**不能把它们当成普通的一件**来处理：
>
> | 情况 | 例子 | 现状 |
> |---|---|---|
> | **多件拼装**（游戏里一个 actor 由多个网格拼成） | 伐木场 = `SM_Loggingcamp_Tree` + `_Fence` + `_Acce`；采石场 = `RockA/B/C` + `_Fence` + `_Acce`；简约门 = 门框 + 两片门扇 | 覆盖表里只能给**主件的单网格近似**（看起来就是"一棵树 + 几块石头"）—— **完整拼装要等「待办 3：组件的相对变换」** |
> | **多个类型共用同一套外观资产** | 金属采矿场2 `CopperPit_2` 与采石场 `StonePit` **共用** `StonePitLarge` | 看起来很像，**不是 bug** |
> | **Pit 类资源节点**（矿场/采石场/煤矿/硫磺矿） | `StonePit` / `CoalPit` / `SulfurPit` / `CopperPit_2` | 资产名与类型名不一致，靠覆盖表固定；吸附阈值要考虑它们**占地比一格大得多** |
> | **表示为零散碎件** | 伐木场的树、采石场的岩石 | 吸附时"最近的一件"可能落在碎件上 ⇒ 需要一个**"以整个蓝图包围盒/网格对齐"**的兜底策略，而不是只按单件吸 |
> | **骨骼网格建筑**（`SK_` 开头） | 粉碎机 `SK_Pulverizer`、磨粉机 `SK_StoneMill`、碎冰机 `SK_FrozenCrusher`、古代工厂等 | 它们**不能实例化**，`Ghost` 里是"一件一个组件"单独处理；吸附/变换要单独走那条路（`Ghost.skel_list`） |
>
> 详见 `mod\PWProjection\已知限制.md` 第一、二节，以及 `docs\踩坑记录.md` §26/§28。

**要什么**：投影大体挪到"应该放的位置"附近时，**自动吸附**对齐，
不用一格一格微调。

**为什么需要**：现在的流程是手动方向键平移（`move` 模式），
对齐一栋大建筑要按很多下。如果玩家站在**原基地**上放投影，
"正确位置"其实就是原基地的位置 —— 吸附能一步到位。

**参考做法（Litematica 的思路，只借思路不抄代码）**：
- 取**玩家当前所在位置**（或玩家看向的点）最近的"原建筑位置"，
  在阈值内就把投影的偏移设成让那一件正好重合。
- 阈值要可配置（`snap_radius_cm`），太大会乱吸，太小没用。
- 吸附后应该**给一行反馈**（正好和待办 1 一起做）。

**实现要点**：
- 蓝图里每件建筑都有相对包围盒中心的坐标（`p`，米），
  所以"某一件的世界位置" = 投影偏移 + 该件的相对坐标。
- 反推：想让第 k 件落在世界点 `W`，则偏移 = `W - rel[k]`。
- 候选锚点：玩家脚底位置 / 玩家视线与地面的交点 / 当前投影里最近的那一件。
  选哪个要实测手感。
- 加按键（例如 `F10`）+ 配置项；**吸附不改蓝图数据，只改投影偏移**。

**验收**：站在原基地里按吸附键，投影一步对齐到原建筑位置。

#### 待办 2 实现记录（2026-09-29）

**状态**：🟡 **已实现 + 离线验证通过（8/8 场景）；等实机验证**。

**怎么用**（给玩家的两步）：
1. 站到基地里（**越靠基地中心越准**，见下面的阈值说明）；
2. 按 `K` 放出投影 → **放下那一刻就自动对齐**到真实的原建筑上，屏幕出现

**代码**：新模块 `pwpr_snap.lua`；配置 `snap_enabled` / `snap_on_place` /

**算法一句话**：用"最不可能认错的那几对同类型建筑"给出候选偏移 →

### 待办 3 —— 支持**组件的相对变换**（装配体建筑）—— 2026-09-27 凌晨新增

**起因**：玩家反馈「观赏笼投影成了一根超长的柱子」，我换了个资产又被指出
**那是野外盗猎团关帕鲁的笼子（世界道具，玩家用不了）**。

**查出来的真相**（`pwpr_meshes.txt` 第 5 节）：
`DisplayCharacter` 这个 Actor 的组件是

| 组件 | 个数 |
|---|---|
| `SM_PalBox_Pillar` | **8** |
| `Cube_LowHeight`（单位方块） | **8** |
| `SM_Pointer` | 1 |

**也就是说：观赏笼是用「单位方块 + 柱子」缩放拼出来的**，
游戏里**根本没有一个叫"笼子"的网格** —— 注册表里搜
`Viewing`（paldb 给的 id 是 `Viewing_Cage`）/ `Display` 都是**零命中**，
搜 `Cage` 只有盗猎团的 `SM_PalCage` 和海盗据点的 `/Stage/b05/PiratesAge/`。

**8 根柱子和 8 个方块各有自己的相对位置和缩放**，而我们的蓝图格式每件建筑只存
**「一个网格 + 一个朝向」**（建筑原点 + 原始尺寸）。
于是把其中一根柱子按原始尺寸放在正中，就成了那根超长柱子。

**这不是观赏笼独有的问题。** 任何"由一个 Actor 上的多个子件拼出来"的建筑
（门框+门扇、底座+雕像、8 根柱子…）都会失真。我们已经用**多网格映射**挡掉了
一部分（简约门、装扮机），但那只解决了"哪几个网格"，
**没解决"每个网格各自摆在哪、缩放多少"**。

**要做什么**：
1. 采集时除了网格名，再记录组件的**相对变换**（`RelativeLocation` /
   `RelativeRotation` / `RelativeScale3D`）。
2. 蓝图格式扩展：一件建筑可以带一组"部件" `{mesh, loc, rot, scale}`。
   （格式要向后兼容 —— 老蓝图没有这个字段时按现在的方式画。）
3. 投影渲染时逐部件还原。
4. **这是格式改动，要同步更新 `docs\蓝图格式.md` 和
   `tools\blueprint.py` 的校验器。**

**注意**：这是**唯一一个会动蓝图格式**的待办，改之前先想清楚兼容性。
优先用多网格映射顶一阵子。

**验收**：观赏笼出来是 8 根柱子 + 8 块面板各就各位，而不是一根超长柱子。

**观赏笼现在的处理**：映射写成 `"-"`（**不画**），并登记到 `mod\PWProjection\已知限制.md`。
理由见映射表 `_g12_why_not_draw` —— 在能画对之前，
画一根超长柱子或盗猎团的笼子都是**主动误导**。

## 1. 项目目标

做一个 **Litematica 式的建筑投影模组**，目标平台 Palworld 1.0（单人/自建房）。

需求（用户原始描述）：

| # | 功能 | 定位 |
|---|---|---|

## 2. 技术选型（已定，且已被现实验证）

### 走 UE4SS + Lua，不走 PMK + C++/Blueprint

理由：

| 方案 | 前置工作 | 编译 | 迭代 | AI 能参与吗 |
|---|---|---|---|---|
| **UE4SS Lua**（选定） | 已装好 | 不需要 | 改完重进游戏 | ✅ 纯文本 |
| PMK + Blueprint | UE5.1 + VS2022 + Wwise | 需要 | 打包 pak | ❌ 二进制 uasset |
| UE4SS C++ | 完整 UE C++ 环境 | 需要 | 分钟级 | ⚠️ 但版本脆弱 |

**决定性理由**：Blueprint 的 `.uasset` 是二进制，AI 无法编辑；

所以这条路是唯一可行的。

**额外验证**：Nexus 上的 Simple Building Blueprints (mod 4073) 也是纯 UE4SS Lua，

**原写法** `RegisterKeyBind("F7", fn)` 确实失败（字符串键名不行），

**教训**：按了键没看到反馈 ≠ 没生效。这个扫描要 2~3 秒，
期间游戏会卡顿但没有任何提示，很容易误判成"没反应"。
**先看日志再下结论。**

### ⛔ 新卡点：`ForEachUObject` 不可用（已定位，策略已调整）

**这是本项目排查过程中最重要的一条发现。**

F10 全类名普查的结果：

```
普查完成: 遍历 414600 个 UObject, 不同类名 298930 个
类名                                                         实例数
FNameUserdata: 00000275ACC59868                                       8
FNameUserdata: 00000275ACF54D58                                       8
...
```

**21 MB 输出、29 万行，每一行的"类名"都是 `FNameUserdata:<内存地址>`。**

**原因**：`obj:GetClass():GetFName()` 返回的**不是 UObject 类名**，
而是 **UE4SS 的 Lua 包装对象名**（格式 `<类型>:<地址>`）。
每个包装对象地址都不同 → "类名"全都唯一。

**反证**：同一次运行里 `FindAllOf("PalBaseCampModel")` **完全正常**，
返回 5 个真实实例，`GetFullName()` 格式正确。

### ✅ 结论

| API | 可靠性 | 决策 |
|---|---|---|
| `FindAllOf(类名)` | ✅ 可靠 | **所有功能都用这个** |
| `FindFirstOf(类名)` | ✅ 可靠 | 取单例 |
| `ForEachUObject(cb)` | ❌ 不可用 | **放弃，不要再试** |

**策略调整**：从"枚举全部再筛选"改成 **"从已知对象往下挖"**。

已知起点（实测能拿到）：

```
PalBaseCampModel  x5
  Outer 链: BP_PalGameStateInGame_C -> PalBaseCampReplicator -> PalBaseCampModel
  地图: /Game/Pal/Maps/MainWorld_5/PL_MainWorld5
```

下一步就是从 `PalBaseCampModel` 的属性里找到**建筑列表**，
或者对候选类名逐个试 `FindAllOf`（每次都很便宜）。

**`PalBaseCampModel` 存在，但 `PalBaseCamp` 和 `BP_PalBaseCampModel_C` 都不存在。**

后两个名字**看起来完全合理**——按 UE 的常规命名习惯，`BP_XXX_C` 是蓝图生成的类，
`PalBaseCamp` 去掉 Model 后缀也很自然。但实测都是 0 个实例。

**结论：不要靠命名习惯猜类名。**

**但"怎么发现类名"最后证明不是靠 `ForEachUObject`**（那条路已实测是死路，
返回的全是 Lua 包装对象名）。**真正有效的是"候选名单 + 逐个 `FindAllOf`"**——
一轮就拿到了 `PalBuildObject`、`PalMapObjectManager` 等关键类。
代价是遍历要 2~3 秒、期间游戏卡顿，但这远比反复试错便宜。

**工作流应该是**：
1. 用 FindAllOf(候选类名) 逐个精确查询 → 拿到真实类（每次毫秒级，成本极低）
2. 从已找到对象的 GetClass():GetFullName() / Outer 反推命名规律
3. **不要**再用 ForEachUObject 做类名发现（已实测是死路）

## 8. 工作约定

1. **AI 不在游戏目录写文件**（沙箱也不允许）。所有产出放工作区，用户手动部署。
2. **每次开工先跑 `diag\diag-ue4ss.ps1`**，5 秒确认环境健康。
3. **改 `.ps1` 后必须补 UTF-8 BOM + 静态语法检查**（见踩坑记录第 6 节）。
4. **出问题先按 F6**，区分环境层和 mod 层。
5. **所有踩到的坑写进 `docs\踩坑记录.md`**，防止会话丢失后重复踩。
6. ★★ **配置类改动必须同时改文档/注释（2026-09-28 定，玩家要求）** ——
   只要动了配置，就在**同一次改动**里把这些补齐，不要留到以后：
   * **改了某个键的默认值** ⇒ `CONFIG_VERSION` 加一版 + `MIGRATIONS` 迁移
     （否则老配置里的旧值永远压住新默认值 —— 这个坑踩过 4 次）+ 注释写明原因；
   * **新增参数** ⇒ `DEFAULTS`（带注释）+ `Config.KEY_GROUP` 归组（新参数一律 1）
     + `docs\配置说明.md` 对应文件/分组下加一行；
   * **修改参数语义** ⇒ 改代码注释 + 改文档里的默认值与说明；
   * **作废参数** ⇒ **不要删键**，标 `【已不生效】/【已废弃】/【永久禁用】`、
     归到 `KEY_GROUP` 第 3 组、并在 `docs\配置说明.md` 的 1.3 节写"曾经用途 + 现在被谁取代"；
   * 收尾跑 `python tools\check_config_doc.py`（强制"每个键都在文档里"+"每个配置文件都被点名"）。
