## 0. 一句话

**你照着投影盖房子时，手里那一块会精确落到投影上** —— 不用再一格一格蹭。
两种玩法（配置 `buildsnap_mode` 切）：

| 模式 | 你要做什么 | 结果 |
|---|---|---|
| **`align`（默认）吸附** | 在建造菜单里选好那一块，对着投影里对应那件摆过去（大致对上即可），**正常放下** | 它会落到投影里那一件的精确位置与朝向 |
| **`blueprint` 蓝图建造** | 手里拿什么都行，**准星指着投影里的哪一件**，然后**正常放下** | 就建**投影里的那一件**（类型也跟着投影走） |

两种都**不用按任何键** —— 用的是你**本来就按的那一下"放下"**。

★ 与"投影对齐"（`U` 键）**不是同一件事**:

| 功能 | 做什么 | 触发 |
|---|---|---|
| **建造吸附**（本文） | 把**你正在放的那一块建筑**落到投影对应的位置 | 自动（每次放下时） |
| 投影对齐（待办 2 的另一半） | 把**整个投影**挪到"已有建筑"上（叠图对比用） | **没有键**（默认不绑；想用就在配置里设 `snap_key`，例 `"G"`）。<br>★ 2026-09-29: 原来的 `U` 让位给「换一处记录」（有位置记忆后对齐基本用不上） |

## 1. 怎么用（玩家侧）

1. 按 `Y` 采集 → 按 `J` 加载蓝图 → 按 `K` 把投影放到你要盖的地方
   （**投影放在哪就吸到哪**，所以先把投影摆到正确位置，再开始盖）；
2. 进游戏建造模式:
   * `align` 模式: 选好那一块建筑，对着投影里对应那件摆过去 —— **大致对上就行**；
   * `blueprint` 模式: 手里拿什么都行，**把准星指到投影里你想建的那一件上**；
3. 放下去。

**预期**：建筑出现在投影里那一件的位置上（正好重合），屏幕出现一行

```
建造吸附: 已落到投影位置（差 34 厘米）
```

**不需要按任何键**（用的是你本来按的那一下"放下"）。

> ⚠️ **半透明的预览方块不会跟着跳** —— 它还是跟着你的准星走，
> 只有"真正放下去的那一件"会精确落在投影上。
> 原因见第 3 节：游戏那个预览对象 Lua 抓不到（实测结论）。
>
> ★ 想要"放之前就能看到它吸到位"（预览也变色/跟着吸）:
> 那需要**我们自己画一个高亮标记**在目标点上（复用投影的渲染能力），
> 属于下一步的增强项（玩家 2026-09-29 提的"选中那件用蓝/红标出来"）。

## 3. 原理（为什么只能这么做）

### 游戏放一块建筑的链路

```
建造菜单/预览  ──►  PalNetworkPlayerComponent:RequestBuild_ToServer(
                        buildObjectId (FName),
                        location      (FVector),   ← 最终放置坐标就在这
                        rotation      (FQuat),     ← 以及朝向
                        extraParams, debugParam )
```

**要改的"放置位置"就是这个 RPC 的参数。** 所以做法是:

1. 用 UE4SS 的 `RegisterHook` 挂在这个函数上（**pre-hook** = 函数执行**之前**触发）；
2. 在回调里读 `location` / `rotation`，和投影里同类型的记录比距离；
3. 对得上就**改写这两个参数**（改完立刻回读校验），对不上就原样放行。

### 为什么不去动"那个半透明预览"

因为**动不了**。PWRecon 第四轮已经实测过（见 `踩坑记录.md` §3f-7）：

```
所有预览/建造菜单/UI 类（PalBuildPreview / PalBuildMenu / PalBuildObjectPreview /
BP_BuildObject_C / WBP_BuildMenu 等 ~19 个）→ 全部 0 个实例
PlayerController / Pawn 上的 BuildPreview / BuildSystem 等字段 → 全空
```

⇒ 游戏的预览幽灵**不在地图 Actor 枚举里**，Lua 抓不到、也改不了。
所以我们只能在"请求放置"这一环上做（也就是**放下那一刻**生效）。

> 接口事实（函数路径、参数顺序、"钩子参数可改写"）来自**只读参考** SBB
> （Simple Building Blueprints）—— 只看了它的做法和接口名，**没有复用它的代码**
> （它的许可明确要求修改/转载需授权，见 `AGENTS.md` 规矩 2）。

### 我们实际做的三步（全部只用"在同一环境里已被验证过"的原语）

```
1) 读:  解开参数包装（:get()）读出来 —— RemoteUnrealParam / LocalUnrealParam
        都必须先解开；直接读 .X **读不到**（2026-09-29 实测踩过，见 §40）
2) 拦:  idParam:set(FName("None")) 把原请求废掉，并**回读确认**真的成了 "None"
3) 发:  用吸附后的坐标自己再发一次请求（普通 Lua 表 + FName(...)）
```

**顺序不能反**（先拦、确认拦住了，再发）:

* 先发再拦 ⇒ 万一没拦住就是**一次点击放两块**（白费材料还得拆）；
* 先拦后发 ⇒ 最坏情况只是"这一次没放上"（再点一下即可）。

★ 为什么不是"就地改写 `location`/`rotation`": 那一次的实测日志显示这两个参数是
`LocalUnrealParam`，而**结构体参数的改写写法在本机没有先例**（参考实现里只改过
FName 参数）。上面这三步用的都是已被验证的原语 —— 风险更低，也更好排查。

### 3.5 ★ 类型名对不上怎么办（实测踩到的真事）

第二次实测的日志:

```
[bsnap] 请求 #5: id=Wooden_foundation 位置=(-98213.0,39973.4,742.8) 朝向=134.4 度
[bsnap] 匹配: id=Wooden_foundation(归一化 woodenfoundation) →
        投影里没有同类型的记录; 最近的一件=Wood_Foundation 距离=18.3 厘米
```

* **游戏给的 id 是 `Wooden_foundation`**，而蓝图里的类型是 **`Wood_Foundation`** ——
  只差一个 "en"（`woodenfoundation` vs `woodfoundation`）⇒ "同类型"永远匹配不上；
* 但**最近的那一件只有 7~21 厘米远** —— 说明**投影和游戏的网格其实对得非常准**，
  差的只是名字。

⇒ 两条对策（都在这一版里）:

1. **放宽阈值** `buildsnap_type_loose_cm`（默认 1000 厘米）: 没有同类型记录时，
   只要最近的**任意类型**记录比它更近，就认它；
2. **自动学映射**: 用放宽命中时，把 `游戏 id → 蓝图类型` 记下来
   （日志会打 `★ 学到映射: 游戏 id X → 蓝图类型 Y`），
   之后同一个 id **直接按同类型处理**（即使把放宽阈值设成 0 也能吸上）。

> ★ 也就是说: **你正常盖几次，它自己就把名字对上了**。
> 想让它一次就准，也可以在 `pwpr_config.json` 里把 `buildsnap_type_loose_cm`
> 临时调大（例如 `300`）让它先学一轮。

### 3.6 ★★ 放下之后它会自动做什么（三个机制，2026-09-29 定稿）

> 这一节是"**玩家什么都没按，它为什么动了/没动**"的答案。

**(1) 重发排到下一帧**（`buildsnap_defer`，默认开）

| | |
|---|---|
| 触发 | 你按放置，且投影正显示着、类型/距离对得上（要吸）|
| 做什么 | 拦下游戏的原请求（id → `None`）⇒ **下一帧**再按投影坐标发一次 |
| 为什么这样 | 原来是在**钩子回调里直接再调游戏自己**（嵌套/递归）；水面地基上四次事故的崩溃栈最内层都是"UE4SS 帧反复重复 = 深递归"⇒ 改成"下一帧、干净栈"之后**实测 3/3 成功、不再崩**（`踩坑记录.md` §68-13）|
| 代价 | 落位晚一帧、屏幕可能闪一下提示；请求第 4 个参数非空时不延后（原样放行）|

**(2) ★ 高度自适应 —— "吸附后的高度不被允许 ⇒ 自动把投影高度挪过去"**

| | |
|---|---|
| 触发 | 重发之后 1.2 秒内**没有新建筑出现**（游戏拒了这次放置）**且这次改过高度**，并且算得出 `dz = 游戏允许的高度 − 我们发的高度`（5 ~ 500 厘米）|
| 做什么 | `Session.offset.z += dz` ⇒ **整份投影按新高度重画** + **记进位置记忆**（下次还生效）+ **弹提示**说明是"高度不被允许"才自动调的 |
| 效果 | **再放一次就用修正后的高度**，而且**高度继续跟投影** —— 不是"以后不吸高度"|
| 日志 | `[bsnap] ★ 高度自适应: … 吸附的高度被游戏拒绝 ⇒ **投影 Z 偏移 +23 厘米** ⇒ 现在 偏移(…)`（`● 高度自适应: …` 那行是同步落盘的版本）|
| 手动改 | 和普通微调一样: 方向键 / 小键盘 `9`、`3`（`F9` 切到"移动"模式），或按 `H` 把投影拉回脚下重放 |

**(3) 崩溃 / 卡死记忆 —— 只记录，不限制功能**

| | |
|---|---|
| 触发 | 上一次会话在**重发那一步**卡死/崩溃（黑匣子 `● 重发前 …` 有登记、**没有** `● 重发返回`）|
| 做什么 | **只记录**: 启动时写一行 `★ 卡死记忆: …` 到日志，`F7` 里也显示；**不改任何行为** |
| 为什么不改行为 | 曾经用"整类拉黑 / 整片拉黑 / 限制修正量"三种方式**屏蔽功能**，全被玩家否掉（「跟没有这个 mod 有啥区别」）⇒ 定成规矩: **崩了就去修机制**（见工作区 `AGENTS.md` 规矩 3c）|
| 存在哪 / 怎么清 | 写在 `pwpr.log` 里（`● 记忆 frozen …` / `● 记忆 zone …`，每次启动重新登记）；**重置 = 删掉/移走 `pwpr.log`** |

## 4. 排查：怎么读日志

每次放置都会在 `pwpr.log` 里留痕（前 40 次打全，之后只记结果）:

```
  [bsnap] 请求 #12: id=Wood_Foundation 位置=(123456.7,234567.8,8901.2) 朝向=90.0 度
          | 参数形式 id=userdata RemoteUnrealParam: 0x... loc=userdata LocalUnrealParam: 0x...
  [bsnap] 匹配: 记录类型=Wood_Foundation 距离=34.2 厘米（阈值 300）
          记录朝向=90.0 请求朝向=90.0 差=0.0 度（容差 35）
  [bsnap] 结果: 已改发到投影位置（align 模式，Wood_Foundation，差 34.2 厘米）
          → (123423.0,234590.0,8901.2) 朝向 90.0 度
```

蓝图建造模式（`blueprint`）那两行长这样:

```
  [bsnap] 蓝图模式: 准星选中 Wood_Wall（前方 312 厘米，偏离准星 41 厘米）
  [bsnap] 结果: 已改发到投影位置（blueprint 模式，Wood_Wall，差 41.0 厘米）→ (...) 朝向 ...
```

| 症状 | 看哪一行 | 含义 / 怎么办 |
|---|---|---|
| 完全没有 `[bsnap]` 开头的行 | 启动日志里的 `建造吸附钩子:` | 钩子没注册上（把启动那几行发出来）。注册成功时会打 `pre_id=… post_id=…` |
| 有 `请求 #N` 但 `位置=(读不到)` | 同一行的"参数形式" | 参数包装的读法不对（`align` 模式会因此完全不动；`blueprint` 模式不依赖位置，仍可工作） |
| `匹配: … 投影里没有同类型的记录` | 同一行的"最近的一件" + "蓝图类型样本" | 游戏 id 与蓝图类型名写法不一致 ⇒ 看这两行就能定映射；或临时把 `buildsnap_type_match` 设 `false`（只看距离），或改用 `blueprint` 模式（类型由投影决定，不比对 id） |
| `结果: 太远（…）` | 数字 | 摆得还不够近 ⇒ 摆近点，或把 `buildsnap_radius_cm` 调大 |
| ★ **距离总是接近"一格"（约 300~400 厘米）** | `匹配: … 距离=…` | 说明**投影没有和游戏自己的建造网格对齐** —— 游戏把你那一块吸到了它的格点上，与投影差正好一格。先把 `buildsnap_radius_cm` 调到 400~500 让它能吸上；根治办法是"网格对齐投影"（路线图里的下一步） |
| `结果: 朝向差太多` | 数字 | 你的朝向和投影里那件差太多 ⇒ 转一下，或调大 `buildsnap_rot_tol_deg` |
| `blueprint 模式: 锥角里没有投影记录` | 数字 | 没瞄准/太远 ⇒ 把准星对准投影那件，或调大 `buildsnap_aim_cone_deg` / `buildsnap_aim_max_cm` |
| `!! 没能拦住原请求` | 回读值 | 拦不住 ⇒ **原样放行**（不会重复放，但这次没吸上）。把这几行发出来 |
| `!! 拦住成功但重发失败` | 错误信息 | 这一次等于没放上（再点一下即可）。把这几行发出来 —— 这是最需要知道的一种情况 |
| `干跑（…）: 本来会把这次放置改发到…` | 数字 | 干跑模式正常工作（判断逻辑对，只是没改） |

按 `F7` 也能看到一行状态:
`建造吸附: true | 模式=align | 钩子=已注册 | 请求 12 次（改发 9 / 干跑 0 / 放过 3 / 拦不住 0 / 重发失败 0）`

## 5. 已知限制 / 风险

| 限制 | 说明 |
|---|---|
| **预览方块不会跟着吸** | 见第 3 节（游戏预览对象 Lua 抓不到）。放下去才生效 |
| **只在"放下那一刻"生效** | 不能"一边瞄一边自动对齐" |
| **`align` 模式依赖"类型 + 位置 + 朝向"三件事都对得上** | 太远 / 朝向差太多 ⇒ 故意不吸（免得拧你的意图）。类型对不上时改用 `blueprint` 模式（它不看类型比对） |
| **`blueprint` 模式不看你在建造菜单里选了什么** | 类型完全由投影决定 ⇒ 如果你手上那件和投影这件不是同一种，材料消耗是**投影那种**的；材料不够时游戏会按它自己的规则拒绝 |
| **多人游戏未验证** | 逻辑挂在"客户端请求放置"上，单机（含自己开服）应当是同一链路；联机时服务器可能另有校验。**没测过** |
| **被游戏自己否掉时不会重试** | 如果投影那个位置本来就不合法（悬空/重叠），游戏会拒绝放置 —— 那是游戏在保护你的存档，本项目**不绕过任何合法性校验** |
| **不改变材料消耗/建造规则** | 只替换目标（类型/坐标/朝向），其他参数原样透传 |

## 6. 第一次实测怎么做（给玩家）

1. 部署（`deploy.ps1`）→ 进游戏（**这一版改了 Lua，必须重启游戏**）；
2. 按 `J` 加载蓝图、按 `K` 把投影放到一个空地/你要盖的地方；
3. **先试 `align` 模式**（默认）: 进建造模式，选一块**地基**，对着投影里的一块地基
   摆过去（差个一两米也行），放下去；
4. 看两件事: ① 建筑是不是正好落在投影那一块上；② 屏幕上有没有那一行提示；
5. 再试 `blueprint` 模式: 把 `buildsnap_mode` 改成 `"blueprint"` 按 `F8`，
   手里随便拿一块建筑，**准星指着投影里想建的那一件**，放下去；
6. 不管成不成，**把 `pwpr.log` 发出来**（重点看第 4 节那几行）。

> 想先零风险观察: 把 `buildsnap_dry_run` 改成 `true`（按 `F8`），
> 这时候摆放**完全不会**被改动，日志里只会写"本来会改发到哪"。

## 7. 实测记录

### ★★ 第十九次实测（2026-09-29，构建标记 2026-09-29.23 期间）—— 一次"吸附把地板挪到 9 米外"的事故

玩家反馈: 「重新 J+K 之后放建筑**对不上新的网格**，而且**只能放下第一块地板**，
后面的贴着第一块一直提示不让放，怀疑是上一次投影的残留」。

**日志否掉了"残留"**（投影确实是新的、旧的已收起），真正的过程是:

```
请求 = 放【地板】Wooden_foundation @ (-99593,39191)
匹配 = 记录类型【ItemChest_02】距离 918 厘米（阈值 4000）      ← 配到了 9 米外的箱子
结果 = 已改发 → (-100139.2,38454.0,694.7)                    ← 之后每一次都是这同一个坐标
⇒ 那位置已被第一块占住 ⇒ 后面每一块都被游戏拒绝
```

**三个原因叠在一起**: ① `buildsnap_demo` 还开着（半径 40 米 / 类型放宽 20 米）；
② `buildsnap_type_loose_cm` 默认给到 1000（它本该只桥接"名字写法不同"）；
③ **完全没有"修正量上限"**。

**修法（详见 `踩坑记录.md` §64）**:

* ★★ 新增 **`buildsnap_max_jump_cm = 600`**: 修正量超过它就**原样放行**（总保险）；
* `buildsnap_type_loose_cm` 默认 **1000 → 150**；演示模式里的类型放宽 **20 米 → 3 米**；
* 闸 ② **已经放上过的记录不再吸**（别把玩家按回已被占住的位置）；
* 闸 ③ **刚被游戏拒绝过的记录 8 秒内不再吸**（避免"每次都撞同一堵墙"）；
* 回归用例进了 `buildsnap_sim.py` 第 ⑩ 组（用当时真实数字）。

> ⚠️ **如果你还开着 `buildsnap_demo`，请把它改回 `false`**（那份配置是给"肉眼验证"用的，
> 默认值才是实测定稿的手感）。现在即使开着它，闸门①也会兜住这类误配。

### 第十八次实测（2026-09-29，构建标记 2026-09-29.19）—— ★ **又崩了 + 拆掉不恢复（同一个根因）**

> 玩家:「又崩了，而且实测过程中，现在**拆除后并没有恢复**」
> 崩溃: `EXCEPTION_ACCESS_VIOLATION reading 0x000001e3190a50`，栈里 **30 帧 UE4SS**。

**根因（一个原因解释两个症状）**: "拆掉恢复"要枚举本关卡建筑，用的是老路子
`level.Actors` —— 而这个数组**保留着已摧毁（pending-kill）的 actor**:

* 读那个死对象 ⇒ **原生访问违例**（pcall 抓不住）⇒ 崩溃；
* 同一个死对象**仍占着那条记录的位置** ⇒ 名单算出"还占着" ⇒ **永远不恢复** ✓

**处理（安全优先，不继续修它，而是关掉）**: 新增 `ghost_hide_enum`（默认 **false**），
关闭这个功能里**所有需要枚举关卡建筑的部分**:

| 部分 | 状态 |
|---|---|
| "放下一件 ⇒ 从投影里去掉它"（**精确通道**，靠已知记录序号，**完全不枚举**） | ✅ 保留（安全且有效） |
| 放投影时扫一遍标"已经放上的" / 每隔几秒扫一遍找"拆掉了" | ❌ 关闭（默认） |

⇒ **拆掉之后想让它重新画出来: 按 `K` 收起再放一次**（名单清空、重新画全部件）。

**★ 玩家纠正后的最终拆法**（见 `踩坑记录.md` §62）: 那两件事风险完全不同，
用一个开关关掉等于把玩家要的功能也砍了 ⇒ 拆成两个:

| 开关 | 默认 | 管什么 | 风险 |
|---|---|---|---|
| `ghost_hide_enum` | **true** | **按 `K`/`L` 放投影时扫一遍**，把已经放过的件标成不显示 | 低（从 .9 起一直在用、只在按键时跑一次，实测没崩过） |
| `ghost_hide_scan` | **false** | **每几秒自动扫**去发现"被拆掉了" | **高**（周期性 + 必然撞上"刚拆完、死对象还没清掉"的窗口 ⇒ 两次崩溃都在这条路） |

### 第十七次实测（2026-09-29，构建标记 2026-09-29.18）

> 玩家:「刷新有了，不过现在**每次刷新都会卡顿**诶，之前好像没这么明显？」

**原因**: 之前那个"兜底全扫"**从来没跑起来过**（`Placed.deps` 没注入，§59），
所以"功能生效"的同时**它的代价也生效了** —— 每个周期一次性读完整个关卡建筑列表
（600+ actor × 位置/类型/朝向），全挤在同一帧 ⇒ 周期性卡顿。

**三刀**（详见 `踩坑记录.md` §60）:

| 措施 | 效果 |
|---|---|
| ★ 只读"关心的类型"（已隐藏记录的类型） | 类型对不上的 actor 连位置都不读 ⇒ 省掉一半以上跨边界调用 |
| ★★ **分片**: 每 2.5 秒只读 150 个 actor，几帧扫完 | 单帧开销大降 ⇒ **卡顿消失**（总耗时不变） |
| ★ 没藏东西就不扫；**正在连放时也不扫** | 不和放置抢那一帧 |
| 顺带 | 完整全扫与分片全扫共用 `Placed.apply_anchors`，避免两套实现漂移 |

### 第十六次实测（2026-09-29，构建标记 2026-09-29.17）—— ★ **崩了一次**

> 玩家:「拆除后等了 30s 没反应，切出来准备看日志，**然后游戏崩了**」
> 崩溃报告: `EXCEPTION_ACCESS_VIOLATION reading address 0xffffffffffffffff`，
> **崩溃栈 44 帧全是 UE4SS** ⇒ 是 Lua→引擎桥在解引用坏对象。

两个问题（详见 `踩坑记录.md` §59）:

| 问题 | 根因 | 修法 |
|---|---|---|
| 拆除后不恢复（半分钟没反应） | ★ `Placed.deps` **从来没被赋值过** ⇒ 兜底全扫里 `if deps == nil then return` ⇒ **一次都没跑过** | 补上依赖注入 ⇒ 恢复回到 ~8 秒 |
| **崩溃** | "每 2.5 秒查引用还在不在"会对**已被摧毁的 actor** 调 `Util.valid()` ⇒ 原生访问违例（**pcall 抓不住**） | **默认关掉**这条快路径（`ghost_hide_alive_check = false`），恢复完全交给"兜底全扫"（重新枚举活对象，天然安全）；并给增量重灌加"同代/同世界/同宿主"硬门槛，`clear()`/`forget()` 连配方一起清 |

### 第十五次实测（2026-09-29，构建标记 2026-09-29.16）

> 玩家:「拆除建筑后 2.5-10 秒把取消的投影放回来的操作好像没触发了。」

**又是同一个 `min_cm` 提前 return 的后果**（§56 的兄弟问题，见 `踩坑记录.md` §58）:
拆掉恢复的**快路径**靠"actor 句柄"，而句柄来自**落地确认**回调；
那条分支既不拦也不重发 ⇒ 没排确认 ⇒ 没句柄 ⇒ 快路径没东西可查。
（兜底全扫还在，但我在同一轮把它从 7.5 秒拉到了 15 秒 ⇒ 体感就是"不触发了"。）

修法:

1. `min_cm` 分支**照样排落地确认** —— 同时拿到"真的建出来了"和 actor 句柄；
2. 兜底全扫间隔 **15 → 8 秒**；
3. 新增诊断: 没有句柄时明确写 `拆掉检查: **0 个句柄**（藏了 N 件…只能等兜底全扫）`。

### 第十四次实测（2026-09-29，构建标记 2026-09-29.15）

> 玩家: 不结算的 bug 修好了 ✓。并提出「不每次放置都写到文件，只记在内存，
> 满一定数量或隔多少秒再存一次」。

**核对结果（先查现状再动手）**: 放置路径上**已经没有写盘、也没有写控制台了**
（逐行都是内存缓冲；"结果:"那行上一轮已改成 `Log.hot`，放置提示也默认关了）。
⇒ 这个方案在性能上**已经没有可省的**；但策略值得显式化，于是做成配置:

* `log_flush_interval_s = 5`（隔这么久至少落一次盘）
* `log_flush_lines = 200`（攒够这么多行也落盘）
* 由一个**自续的 2.5 秒定时回调**驱动，不依赖按键/事件；没内容时什么都不做。

**丢失风险**: 崩溃最多丢最后一次落盘之后的几行**诊断日志**；
游戏数据/蓝图/配置不走这条通道 ⇒ 零风险（内存缓冲还有 8000 行上限）。

> 剩下的成本在**引擎重活**（"拦下原请求 + 重发一次"）。
> 下一刀只能砍那里: **就地改写参数**（省掉重发），需要先做一次能力探测
> （按 `N`）确认那两个结构体参数能不能写。

### 第十三次实测（2026-09-29，构建标记 2026-09-29.14）

> 玩家:「感觉好些了……还是有些卡。然后发现了另外的问题: 我先放了一个地板，
> 等 3 秒触发取消投影后，**再短时间放很多地板，停下后过了十多秒都没取消投影，也没有提示**。」

**根因是上一轮那个"够准就不插手"的提前 return**（详见 `踩坑记录.md` §56）:
它把**记账**（"这一条已经放上了"⇒入队）也一起跳过了，而记账跟"要不要改写坐标"
毫无关系 ⇒ 摆得准的件永远不入队 ⇒ 队列空 ⇒ 清算时无事可做（连提示都没有）。
**第一条地板正常**正好是反证: 它当时差 >5 厘米，走了改写那条路，顺带记了账。

修法:

1. `corr <= min_cm` 分支里**照样调用** `on_placing(res.idx)`（不改坐标，但记账）；
2. **清算的第二层保险**: 看门狗（每 2.5 秒）里加兜底 ——
   "队列安静 ≥ 批量窗口"就直接清算；并且看门狗现在**入队时**就启动，
   于是清算有了两个独立触发点（不再只靠一个延时回调）。

### 第十二次实测（2026-09-29，构建标记 2026-09-29.13）

> 玩家:「还是多少有一点呢，**卡顿类型是只在放置瞬间卡**。
> 另外提示这个不要影响到其他的（比如投影位置、高度调整这些），**只改放置的提示**哈。」

**① 只动了"放置"的提示**（已核对）: `buildsnap_notify` / `buildsnap_notify_confirm`
只包住吸附那两行；采集 / 投影微调 / 刷新 / 对齐等提示走的是原来的 `Notify.show`，
一个字都没改。`notify_trace` 只影响**日志的诊断跟踪**，不影响任何提示的显示。

**② "只在放置瞬间卡" ⇒ 仍然是我们这条路径**（站着不动不卡 ⇒ 不是渲染）。
继续削两刀:

| 措施 | 省掉 |
|---|---|
| ★★ `buildsnap_min_cm = 5`（默认）: 摆得比 5 厘米还准时**完全不碰这次请求**（不拦、不重发） | 这是最大的一笔 —— 原来无论多准都要"拦下 + 重发一次"，等于**游戏侧做两遍活**；而现在"摆得挺准"是常态（游戏自己也有地板吸附）⇒ 大部分放置变成零开销 |
| 成功路径那行改用 `Log.hot()`（只进缓冲，**不写控制台**） | 控制台 `print` 是"窗口 + 另一份日志"的双重 I/O，每次都发生 |

`F7` 里新增一个计数: `够准不插手 N` —— 能直接看出有多少次放置被完全放过了。

> 想要"每次都必须严格落到投影上"就把 `buildsnap_min_cm` 设回 `0`
> （代价: 每次放置都走"拦+重发"，也就是那个卡顿回来）。

### 第十一次实测（2026-09-29，构建标记 2026-09-29.12）

> 玩家:「连续放不清除投影，停 3 秒再清除的效果达成了，但是还是卡，
> **跟每次放置时的提示有关系吗，提示的性能消耗大吗**，还有没有其他优化方向。」

**有关系，它就是主因**（详见 `踩坑记录.md` §54）: 每条提示在引擎侧要 7 步
（找控件/写文本/沿父链显示），而**每一步都同步写一次日志文件**；
一次放置发两条提示 ⇒ **放一块地板写盘十几次**。

四刀:

| 措施 | 效果 |
|---|---|
| `mark()`（发提示的分步取证）默认**关**（`notify_trace = true` 才开）+ 只进缓冲 | 每条提示 7 次写盘 → 0 |
| 提示结尾改用 `Log.throttled_flush(1.0)` | 保留取证能力，不再每步写盘 |
| 新增 `buildsnap_notify` / `buildsnap_notify_confirm`（**默认 false**） | 放置时 2 次控件操作 → 0；批量清算那条保留（一批一次） |
| `ghost_hide_scan_interval_s`（默认 15 秒，原固定 7.5 秒） | 建造中的周期性小卡减半 |

> 觉得"没有反馈不踏实"就把 `buildsnap_notify` 改成 `true`
> —— 那会回到"每件都弹提示"，也会回到卡顿。

### 第十次实测（2026-09-29，构建标记 2026-09-29.11）

玩家反馈 + **玩家自己提的解法**:

> 「如果放置的比较快的话，还是偶尔会有一块的投影没被处理。然后还是会有一点卡顿，
> 我想想，不如改成如果在一段时间内（如 3 秒）一直在放置，**就只记录放置的建筑信息，
> 不触发清除投影的效果**，持续一段时间没有操作放置建筑了，**再把期间放置的建筑
> 都取消投影**，这样会不会对性能好点？」

### 第一次实测（2026-09-29）—— 钩子通了，但参数读不到

```
建造吸附钩子: true  pre_id=9 post_id=10          ← 钩子生效
  [bsnap] 请求 #1: id=nil 位置=(读不到) 朝向=(读不到)
          参数形式=userdata LocalUnrealParam: … / … / id形式=userdata RemoteUnrealParam: …
```

根因: UE4SS 把 hook 参数包成 `RemoteUnrealParam` / `LocalUnrealParam`，
