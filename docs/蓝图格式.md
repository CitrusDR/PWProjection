# Palworld 建筑蓝图格式规范 v1

> 状态：**已验证**
>
> **两个独立实现，互相交叉校验**：
>
> | 实现 | 位置 | 说明 |
> |---|---|---|
> | Python（工具链） | [`tools/blueprint.py`](blueprint.py) | 生成/校验/统计/筛选/拆分，自检 39 项 |
> | **Lua（游戏内）** | [`mod/PWBlueprint/Scripts/pwbp_bp.lua`](../mod/PWBlueprint/Scripts/pwbp_bp.lua) + [`pwbp_json.lua`](../mod/PWBlueprint/Scripts/pwbp_json.lua) | 游戏内直接导出/读取，**不再需要 TSV 中转** |
>
> Lua 侧的 `BP.validate()` 与 Python 侧的 `check` 规则**刻意写成一致** ——
> 任何一侧判为不合法的蓝图，另一侧也应该判为不合法。
> 这样"游戏里存出来的文件"和"电脑上生成的文件"可以互相导入。
>
> 字段序说明：Lua 的 JSON 编码器按**键名排序**输出，
> 所以 Lua 写出来的文件字段顺序与下面例子不同，但内容等价。

---

## 1. 设计目标

| 目标 | 做法 |
|---|---|
| 跨存档/跨版本可用 | 不存绝对世界坐标，只存**相对原点**的偏移 |
| 便于整体挪动/旋转 | 原点 = 包围盒中心且吸附到网格 |
| 支持"分层展示" | 每个建筑带 `layer` 索引 |
| 可读、可 diff、可手改 | JSON，字段名尽量短但保留自解释的 `meta`/`stats` |
| 类型可映射到游戏资产 | 用蓝图短类型名（`Wood_Foundation`） |
| 体积可控 | 单位为米 + 保留 3 位小数（毫米级精度，足够建造） |

## 2. 文件名约定

```
<名称>.blueprint.json
```

---

## 3. 顶层结构

```json
{
  "$format": "palworld-blueprint",
  "version": 1,
  "meta": { ... },
  "stats": { ... },
  "buildings": [ ... ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `$format` | string | ✅ | 固定 `"palworld-blueprint"`。用 `$` 前缀避免与数据字段冲突 |
| `version` | int | ✅ | 格式版本，当前 `1` |
| `meta` | object | ✅ | 元信息 |
| `stats` | object | 建议 | 预计算的类型/分层统计，便于快速预览而不用扫全表 |
| `buildings` | array | ✅ | 建筑实例列表 |

---

## 4. `meta` — 元信息

```json
"meta": {
  "name": "my-base",
  "createdAt": "2026-09-26T01:00:00+00:00",
  "source": "PWRecon (UE4SS)",
  "gameVersion": "Palworld 1.0.x",
  "total": 649,
  "typeCount": 79,
  "layerCount": 4,
  "units": "meter",
  "origin": [-1041.0, 417.0, 685.0],
  "size": { "x": 61.581, "y": 61.137, "z": 3.267 },
  "layerGapCm": 200,
  "meshCoverage": { "withMesh": 210, "total": 358 }
}
```

| 字段 | 说明 |
|---|---|
| `name` | 蓝图名称 |
| `createdAt` | ISO 8601（UTC） |
| `source` | 数据来源工具 |
| `gameVersion` | 导出时的游戏版本（版本不匹配时给用户提示） |
| `total` | 建筑实例总数，**必须等于 `buildings` 长度** |
| `typeCount` | 不同建筑类型数 |
| `layerCount` | 层数 |
| `units` | **固定 `"meter"`**。校验器会拒绝其它值 |
| `origin` | 导出时所在的世界坐标（米），仅作**参考记录**，导入时不依赖它 |
| `size` | 包围盒尺寸（米），**以原点为中心的 ±size/2** |
| `layerGapCm` | 分层时用的聚类阈值（厘米）。记录它是为了让别人知道"为什么这栋算第 2 层" | 
| `meshCoverage` | `{ withMesh = n, total = n }`，有多少件带 `mesh`。便于快速判断"结构件能不能画出来" |

> `layerGapCm` 与 `meshCoverage` 是**附加信息**，不是必填。
> 读取方遇到不认识的键一律忽略（规范第 5 节的向前兼容原则）。

### ⚠️ 坐标系：原点 = 包围盒中心

**这一点极易误解，务必看清：**

```
buildings[].p 是以【包围盒中心】为原点的偏移，
所以取值范围是 ±size/2，而不是 [0, size]。
```

实测样例（一个三层基地）：

```
x: rel min=-1756.0  max=+1756.0   size=3512.0     ← ±size/2
y: rel min=-3035.0  max=+3035.0   size=6070.0
z: rel min= -149.0  max= +150.0   size= 299.0
```

**为什么这样设计**：
- 蓝图可以围绕中心整体旋转，不会偏心
- 换算世界坐标很简单：`world = origin_当前 + p`
- 导入时把蓝图"放在玩家面前"只需指定新的中心点

**原点吸附**：`origin` 会**向下取整**到 1 米网格，所以相对坐标可能
出现略超出 ±size/2 最多 1 米的值——这是网格对齐的正常结果，不是 bug。

## 5. `buildings[]` — 建筑实例

```json
{
  "t": "Wood_Foundation",
  "p": [-12.0, 8.5, 0.0],
  "yaw": -28.69,
  "mesh": "SM_WoodFoundation",
  "mesh_path": "/Game/Pal/Model/Prop/Architecture/Architecture_Wood/SM_Floor_Wood.SM_Floor_Wood",
  "layer": 0
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `t` | string | ✅ | **建筑类型短名**（见第 7 节） |
| `p` | [number, number, number] | ✅ | 相对原点的位置（米），`[x, y, z]` |
| `yaw` | number | ✅ | 偏航角（度），归一化到 `-180..180` |
| `mesh` | string | 可选 | 静态网格资产**短名**；**结构件通常没有**，省略即可 |
| `mesh_path` | string | 可选 | ★ **网格资产的完整路径**（`/Game/.../X.X`）。2026-09-28 新增，**强烈建议保留** |
| `layer` | int | ✅ | 层索引，从 0 开始，由高度推算 |

### 为什么需要 `mesh_path`（跨存档投影的关键）

投影时要用"**网格名 → 资产**"：

* 只有 `mesh`（短名）时，得靠一张**运行时注册表**去查，而那张表是用
  `FindAllOf("StaticMesh")` 建的 —— **只包含当前世界里已经加载的资产**；
* 在**采集的那个存档**里，那些建筑都在场，资产自然全加载（能解析）；
* 换到**另一个存档**，蓝图里的大量资产根本没被加载 → 查不到 → **跳过不画**
  ⇒ 表现就是"投影缺件"（而"一个存档采集、另一个存档投影"正是本模组的主要用途）。

⇒ 采集时我们**本来就知道完整路径**（从 actor 的网格组件读到的全名），
把它存进 `mesh_path`，投影时直接 `LoadAsset(路径)` —— 与"当前加载了什么"完全无关。

> **旧蓝图**（没有 `mesh_path`）在别的存档里仍可能缺件 —— **在源存档重新采集一次**即可。
> 投影报告的 `缺网格: <类型> N 件` 会告诉你还缺哪些类型（可据此补 `pwbp_meshmap.json`）。


### 省略字段的原则

- 默认值不写：`yaw = 0`、`layer = 0` 也**照常写**（显式优于隐式，便于校验）
- `mesh` 为空时**省略该键**，不要写 `null`

### 为什么 `yaw` 只有偏航

Palworld 建筑放置只有绕 Z 轴旋转（`Yaw`），`Pitch`/`Roll` 实测恒为 0。
不过为了向前兼容，读取时**遇到未知键应忽略而不是报错**。

## 6. `stats` — 预计算统计

```json
"stats": {
  "types": {
    "Wood_Foundation": { "count": 351, "mesh": "SM_WoodFoundation" },
    "ItemChest":       { "count": 7,   "mesh": "SM_ChestWood" }
  },
  "layers": {
    "0": { "count": 400, "z_min": -1.2, "z_max": 2.1 },
    "1": { "count": 200, "z_min": 2.8,  "z_max": 6.0 }
  }
}
```

| 说明 |
|---|
| `types[类型].count` **必须**与该类型的实际条数一致（校验器会查） |
| `z_min`/`z_max` 是该层内**相对坐标**的 Z 范围 |
| `layers` 的键是字符串（JSON 限制），值是 int |

用途：蓝图列表页可以**不加载 `buildings`** 就显示"多少种类型、几层、材料概览"。

## 7. 类型名 ↔ 游戏资产映射

### 类型短名

游戏里的类名形如：

```
BlueprintGeneratedClass /Game/Pal/Blueprint/MapObject/BuildObject/BP_BuildObject_Wood_Foundation.BP_BuildObject_Wood_Foundation_C
```

提取规则（`tools/blueprint.py` 里实现）：

```
1. 取最后一个 '.' 之后的部分   → BP_BuildObject_Wood_Foundation_C
2. 去掉尾部 _C                → BP_BuildObject_Wood_Foundation
3. 去掉前缀 BP_BuildObject_   → Wood_Foundation
```

反向还原（导入时用）：

```
/Game/Pal/Blueprint/MapObject/BuildObject/BP_BuildObject_<t>.<...>_C
```

### 与存档侧 `MapObjectId` 的关系

从 [palworld-save-tools](https://github.com/cheahjs/palworld-save-tools) 源码
可看到存档里的 ID 是**小写下划线**形式：

| 蓝图短名（本格式） | 存档 ID |
|---|---|
| `Wood_Foundation` | `wooden_foundation` |
| `Wood_Wall_V2` | `wooden_wall` |
| `Wood_Roof` | `wooden_roof` |
| `Stone_Foundation` | `stone_foundation` |
| `ItemChest` | `itemchest` |

**注意**：两者**不是简单的大小写转换**（`Wood_Foundation` → `wooden_foundation`，
而 `Wood_Wall_V2` → `wooden_wall` 还带版本号消歧）。
所以需要一个映射表，不能靠算法转换。

映射表放在 `data/type_map.json`（待补全），格式：

```json
{
  "Wood_Foundation": { "mapObjectId": "wooden_foundation", "mesh": "SM_WoodFoundation" },
  "Wood_Wall_V2":    { "mapObjectId": "wooden_wall",       "mesh": "SM_WoodWall" }
}
```

## 8. 校验规则（`blueprint.py check`）

**错误**（会导致导入失败）：

1. 缺少 `$format` / `version` / `meta` / `buildings`
2. `$format` 不等于 `palworld-blueprint`
3. `meta.units` 不是 `"meter"`
4. `meta.total` 与实际条数不符
5. `buildings[i].p` 不是 3 个数字
6. `buildings[i].t` 缺失或非字符串
7. `stats.types[t].count` 与实际不符

**警告**（可导入，但提示）：

- `version` 与工具支持的不一致
- `buildings[i].yaw` 超出 `-180..180`
- 缺少 `layer`
- `stats.types` 里有 `buildings` 中不存在的类型

## 9. 已知限制

| 限制 | 说明 | 计划 |
|---|---|---|
| 无建筑父子连接 | 目前只有位置+朝向，没有"墙挂在哪个地基上"的关系。对**渲染投影**够用（按绝对位置摆放即可），对**结构校验**不够 | 待侦察 `Connector`（阶段 3） |
| 类型映射表未完成 | 79 种类型里只有部分能对应到 `MapObjectId` | `data/type_map.json` 待补 |
| 无材料清单 | 没有"需要多少木材/石头" | 可从类型映射推出，阶段 2 |
| 未做压缩 | 649 实例约 60KB，可接受；上万件需要压缩 | 按需再加（量化坐标 / 二进制） |
| `mesh` 覆盖不全 | 实测 26/79 有 mesh，结构件本来就没有 | **已有运行时解法**：见下 |

### 关于 `mesh` 覆盖不全（2026-09-26 深夜补充）

结构件（地基/墙/屋顶）在 `PalBuildObject` 上**读不到** mesh ——
它们由 `BP_PalStaticMeshImposterChunk` 的 HISM 批量绘制。

`mod/PWBlueprint/Scripts/pwbp_meshmap.lua` 的解法：

1. 运行时把已加载的 `UStaticMesh` 建成注册表（`FindAllOf("StaticMesh")`）
2. 蓝图里的 `mesh` 短名直接命中注册表 → 用
3. 结构件走**名字匹配**：`Wood_Foundation` 拆成 `wood` + `foundation`，
   在注册表里找同时含这两个词、且位于 `Architecture` 目录下的网格
4. 匹配结果导出到 `pwbp_meshes.txt`，可人工核对
5. 不满意的可以在 `pwbp_meshmap.json` 里手写死映射

**注意**：`mesh` 字段仍然是**可选的**，格式规范不变 ——
解析失败不影响蓝图文件的合法性，只影响能不能把那一件画出来。
